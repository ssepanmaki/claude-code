## Summary

The sandbox in this project does not replace the permission system. It adds an OS-level capability boundary around **shell commands**:

- The permission system decides whether a tool call runs at all.
- The sandbox decides what files and network targets the subprocess can touch even after it runs.

Together they form real defense in depth.

## Implementation layers: a repo adapter on top of an external runtime

The sandbox implementation has two layers:

- This repository owns policy, config conversion, enable/disable decisions, command wrapping, cleanup, and permission integration.
- The actual OS-level isolation is done by the external runtime `@anthropic-ai/sandbox-runtime`.

The boundary is visible in `src/utils/sandbox/sandbox-adapter.ts`: the project imports runtime objects such as `SandboxManager as BaseSandboxManager` and `SandboxViolationStore`, then wraps them in an adapter that matches Claude Code's own permission model.

The underlying isolation also differs per platform:

- macOS uses `sandbox-exec`.
- Linux / WSL2 use `bubblewrap + seccomp`.
- Native Windows does not support this shell sandbox.

Reading only this repository, it is easy to assume the sandbox is entirely home-grown. A more accurate description: the repository decides **whether to enable it, how to configure it, and how to plug it into the tool chain**, while the external runtime enforces the OS-level constraints.

## What problem does it solve?

With only an application-layer permission system, Claude Code would have to judge, before a command runs:

- whether the command is read-only
- whether it writes to dangerous paths
- whether it reaches the external network
- whether it bypasses checks through compound commands, redirects, subprocesses, or interpreter scripts

These checks are valuable, but they are still "inference before execution". The real side effects of a shell command often depend on runtime behavior:

- `bash script.sh`
- `python -c "..."`
- `make`
- `npm install`
- a command that spawns another subprocess

The sandbox confines that runtime behavior to a clear boundary. Even if an application-layer check misses something, the command cannot freely write to system directories or reach disallowed network targets.

## Why blocking is valuable in itself

A common first reaction to the sandbox is:

> If it won't even let me edit `/etc/hosts` by default, is the sandbox actually useful?

The project's answer is the opposite. The sandbox is not meant to let you edit `/etc/...` freely. It confines shell commands to an acceptable safety boundary:

- The permission system judges whether to run.
- The sandbox limits the most a command can do once it runs.

`/etc/...` being blocked by default shows that the boundary is working, not that the sandbox is pointless. Concretely, the sandbox covers at least four things the permission system cannot do well on its own.

### 1. An OS-level backstop for the shell

The top of `src/utils/bash/ast.ts` says it plainly: Bash AST analysis is not a sandbox. It only judges whether we can reliably understand the command structure; it cannot stop a dangerous command from actually running.

That is why application-layer cleverness alone can hardly cover the full risk surface. The real side effects of commands like these only unfold at runtime:

- `bash script.sh`
- `python -c "..."`
- `make`
- `npm install`
- a command that starts new subprocesses

This is where the sandbox earns its keep. Even if earlier analysis missed something, once the process reaches the OS layer it can still only write to allowed directories and reach allowed domains.

### 2. Fewer prompts, or none, for commands inside the safety boundary

The default sandbox allowlist includes the current working directory and Claude's temp directory, which is why most development commands inside the workspace run smoothly:

- `npm test`
- `rg`
- `git status`
- builds, tests, and generated files inside the workspace

The project provides `autoAllowBashIfSandboxed` for this. The idea is not to trust the model more boldly, but this: since the command is already confined by an OS-level boundary, there is no need to make users confirm many low-risk Bash commands over and over.

Without a sandbox, the system would usually have two unattractive options:

- Prompt frequently, which fragments the workflow.
- Trust application-layer judgment more aggressively, putting all the risk on static analysis.

### 3. Turning a mistake from system-level damage into a restricted failure

This is the most practical benefit of defense in depth. Models occasionally err, and application-layer rules can miss things. The sandbox does not assume the earlier layers are always right; it keeps the consequences bounded when they are occasionally wrong.

For example:

- `sudo tee /etc/hosts`
- `mv ... ~/.ssh/...`
- `curl <external url> | bash`

Without runtime constraints, these could directly modify the system or user config, or drop an unknown script onto the machine. Inside the sandbox, the more common result is simply a failure because write or network permission is missing. It is not "nothing happened", but a potential system-level incident is reduced to a restricted failure.

### 4. Blocking runtime bypass and escape paths

In `src/utils/sandbox/sandbox-adapter.ts`, the repository adds extra `denyWrite` entries for some high-risk paths, such as:

- `settings.json`
- `.claude/skills`
- certain bare git repo paths

It also specifically handles the bare git repo escape attack surface. The point is not to let more commands through, but to ensure that even a running command cannot tear down the guardrails themselves by editing config, skills, or git structure to widen later permissions.

So the accurate statement is not:

- "The sandbox blocks `/etc`, so it's useless."

but rather:

- "The sandbox shrinks the shell's default permissions to the workspace and an allowlist, so system paths are not writable by default. That is exactly why the project can auto-allow a large set of workspace commands."

## Design boundary: what it protects and what it does not

### Protected

- Bash / shell command execution
- PowerShell execution on supported platforms
- The filesystem write scope of shell subprocesses
- The network access scope of shell subprocesses
- Known high-risk paths and sandbox escape vectors

### Not directly protected

- Direct file tools such as `FileEditTool` / `FileWriteTool`
- Application-layer permission prompts and rule matching
- Bash AST parsing itself

Note in particular that Bash AST analysis is not a sandbox. The source says so explicitly: it only answers whether we can reliably extract the argv structure, and does not stop a dangerous command from running.

## When the sandbox is used

### 1. At startup, decide whether the sandbox is usable

The sandbox is not decided lazily at the first command. When the REPL / CLI starts, it first checks whether the environment really meets the conditions. The core checks:

1. Whether the current platform is supported by the underlying runtime
2. Whether dependencies are present
3. Whether `sandbox.enabled` is on
4. Whether the current platform is within `enabledPlatforms`

If the user explicitly enabled the sandbox but the environment does not qualify, startup shows a warning. If `sandbox.failIfUnavailable` is also configured, startup is refused instead of silently degrading to no sandbox.

Startup also does more than check availability: it runs the initialization flow, converts current settings into a runtime config, and hands it to the underlying `BaseSandboxManager.initialize(...)`. If settings change later, they are hot-updated through `updateConfig(...)` rather than requiring a session restart.

### 2. BashTool uses it by default

A Bash command enters the sandbox by default when all of these hold:

1. The platform supports the sandbox
2. Sandbox dependencies are present
3. `sandbox.enabled` is on
4. The platform is within `enabledPlatforms`
5. The command is not explicitly excluded
6. The call is not allowed to bypass via `dangerouslyDisableSandbox`

The entry points are `packages/builtin-tools/src/tools/BashTool/shouldUseSandbox.ts` and `src/utils/sandbox/sandbox-adapter.ts`.

### 3. PowerShell only on supported platforms

PowerShell is handled a bit more finely:

- Linux / macOS / WSL2: can be sandboxed.
- Native Windows: the sandbox is unsupported and `shouldUseSandbox: false` is returned directly.

So on native Windows, PowerShell relies on the permission system alone, with no OS-level sandbox backstop.

### 4. Hook commands reuse a network-only sandbox

Hooks do not fully reuse Bash's filesystem restrictions. They get an extra **network-only sandbox**:

- The focus is blocking network access.
- The filesystem is not tightened to the degree Bash's is.

This is because hooks are usually not Bash tool calls issued directly by the model, but external extension points of the system or plugins.

## When the sandbox is not used

### 1. FileEditTool / FileWriteTool

These tools do not modify files through the shell; they do file I/O directly in the application layer. They do not go through `Shell.exec()` and are never wrapped by `wrapWithSandbox()`.

They take a different path:

- `checkWritePermissionForTool()`
- `checkPathSafetyForAutoEdit()`
- working-directory checks
- allow/ask/deny rules

So:

- "A shell edit of `/etc/hosts`" is usually blocked by the sandbox at the OS layer.
- "A FileEdit edit of `/etc/hosts`" is usually blocked by the permission system at the application layer.

### 2. Explicitly excluded commands

A command that matches `sandbox.excludedCommands` skips the sandbox entirely.

Three kinds of patterns are supported:

- exact match
- prefix match
- wildcard match

### 3. Commands allowed an unsandboxed fallback

If:

- the call explicitly sets `dangerouslyDisableSandbox: true`
- and policy allows `allowUnsandboxedCommands`

the command may also run outside the sandbox.

This is intentional, and the name is deliberately heavy, `dangerouslyDisableSandbox`, to signal that it is an exception path and not a habit.

## Full execution flow

The process splits into two phases: at startup the sandbox is prepared, and at command time the system decides whether a given command goes in.

### Startup flow

```text
REPL / CLI startup
  -> isSandboxingEnabled()
  -> convertToSandboxRuntimeConfig(settings)
  -> BaseSandboxManager.initialize(runtimeConfig, callback)
  -> on settings change: BaseSandboxManager.updateConfig(newConfig)
```

This phase answers: does the current session have a usable, initialized sandbox runtime that can handle network authorization callbacks?

### Command flow

A typical Bash execution looks like this:

```text
User request
  -> BashTool.checkPermissions()
  -> shouldUseSandbox(input)
  -> Shell.exec(command, { shouldUseSandbox: true/false })
  -> SandboxManager.wrapWithSandbox(...)
  -> spawn(wrapped command)
  -> cleanupAfterCommand() after the run
```

The key point that actually wraps the command is `Shell.exec()`. Before the real `spawn(...)`, it calls `SandboxManager.wrapWithSandbox(...)` to rewrite the original command into a sandboxed command string the underlying runtime can execute. After the command finishes, if the run was sandboxed, `cleanupAfterCommand()` cleans up runtime leftovers.

Two decision points are easy to confuse:

### Decision point A: use the sandbox or not

This is the job of `shouldUseSandbox()`.

It answers:

> Should this command be wrapped in the OS-level sandbox?

### Decision point B: show a permission prompt or not

This is the job of the permission system and the Bash permission checks.

It answers:

> From the application layer's view, is this command `allow`, `ask`, or `deny`?

The two decision points cooperate side by side. Neither replaces the other.

## What the default sandbox restricts

The sandbox runtime config is produced by `convertToSandboxRuntimeConfig()`. It converts the project's own settings, permission rules, and hardening logic into the config the underlying runtime needs.

This step matters because the sandbox config is not a static table. It is "translated" from Claude Code's own permission system.

### How the restrictions derive from the permission system

- `WebFetch(domain:...)` and `sandbox.network.allowedDomains` are merged into the network allowlist.
- Permission rules such as `Edit(...)` / `Read(...)` are translated into filesystem read/write restrictions.
- `sandbox.filesystem.allowWrite` / `allowRead` / `denyWrite` / `denyRead` are layered on top of the final runtime config.

In other words, the sandbox does not maintain a fully parallel security policy. It turns "which paths or domains Claude considers allowed" into OS-level constraints.

### Default filesystem write scope

The default `allowWrite` has only two entries:

- the current working directory `.`
- Claude's temp directory

This means:

- Builds, tests, and temp files inside the workspace generally work.
- Root paths such as `/etc/...`, `/usr/...`, and `/var/...` are not in the write allowlist by default.

### Additional write sources

Extra writable paths come mainly from:

- `sandbox.filesystem.allowWrite`
- paths derived from `Edit(...)` rules
- directories added via `/add-dir` or `--add-dir`
- paths required by the main repository of a git worktree

One easily missed detail: the adapter specifically handles repository-level special paths such as a worktree's main repository and bare git repos, so that isolation does not break normal development flows or, conversely, leave an escape surface.

### Forced deny paths

Regardless of other config, the project hardens some high-risk paths, such as:

- settings files
- `.claude/skills`
- certain bare git repo paths

The reason: if these paths were writable, an attacker could modify Claude Code's own config, skills, or git behavior to widen permissions.

### Network restrictions

The network allowlist comes from two sources:

- `sandbox.network.allowedDomains`
- permission rules such as `WebFetch(domain:...)`

Allowed domains go into the sandbox network config. Access to anything not on the allowlist is blocked at runtime or triggers an extra network authorization flow.

## What `autoAllowBashIfSandboxed` really means

This is one of the most notable switches in the sandbox design.

It expresses this trust assumption:

> If a command is already confined to a safety boundary by the OS-level sandbox, the application layer does not need to prompt for each of many low-risk Bash commands.

So when this switch is on:

- The command first checks explicit `deny` / `ask` rules.
- If none of those hard rules match,
- and the command will actually run in the sandbox,
- BashTool can allow it to run automatically.

One boundary condition deserves emphasis: it only applies to commands that actually go into the sandbox. These cases do not get the shortcut:

- the command matched `excludedCommands`
- it explicitly used `dangerouslyDisableSandbox: true`
- the platform does not support the sandbox at all

These commands still follow the normal `ask` rules, because they do not get the safety backstop of the OS-level constraints.

This is also a core product value of the sandbox: not letting more dangerous operations through, but letting more **ordinary commands within a restricted scope** run without friction.

## Why "the sandbox blocked `/etc`" shows it is useful

The four core values above explain the principle. Here the conclusion returns to the most common doubt: why is a system that won't let you write `/etc` by default *more* trustworthy?

Because what Claude Code runs day to day is not system administration but development commands, for example:

- `npm test`
- `npm install`
- `cargo build`
- `pytest`
- `rg`
- `git status`

These should only operate inside the workspace and a few temp directories anyway. Once the sandbox narrows the shell's default capabilities to that scope, the project can afford to reduce prompts, enable `autoAllowBashIfSandboxed`, and raise the level of automation.

So the right question is not "why won't it edit `/etc` for me?" but "can it run lots of normal development commands more safely and smoothly without touching `/etc`?" From that angle, `/etc` being unwritable by default is not a flaw; it is the precondition for the whole automation experience.

## Platform differences

### macOS

- Uses `sandbox-exec` underneath.
- Path and network rules are implemented through a Seatbelt profile.
- Native OS-level process isolation.

### Linux

- Uses `bubblewrap + seccomp` underneath.
- Sets up mount / PID / network isolation.
- Glob path support is weaker than on macOS.
- Some post-run leftovers must be cleaned up in `cleanupAfterCommand()`.

### WSL

- Only WSL2 is supported.
- WSL1 is treated as an unsupported platform.

### Native Windows

- Native PowerShell/Bash is not covered by this sandbox system.
- Only the permission system and tool-level checks apply.

So for the question "does editing a file on the C: drive go through the sandbox?", the answer splits:

- Native Windows: usually not.
- Linux/macOS/WSL2: only shell commands may be sandboxed.

## Inside vs outside the workspace: how the layers cooperate

### Paths inside the workspace

Paths inside the workspace usually have two layers of protection:

1. Application-layer permission checks
2. The sandbox's default write access to the current working directory

This makes building, testing, formatting, and generating files inside the workspace the smoothest path.

### Paths outside the workspace

Paths outside the workspace are stricter:

- The application layer usually treats them as high risk, requiring confirmation or blocking.
- Even if the application layer allows it, a path outside the sandbox allowlist fails at runtime.

This gives double protection.

### Linux root paths like `/etc/...`

For root-level files on Linux there are usually two cases:

- **Shell path**: the command enters the sandbox, which has no `/etc` write access by default, so it is blocked at runtime.
- **File tool path**: no sandbox; the application-layer file permission check blocks it directly.

## What users actually see

Being blocked is not one single experience. There are at least three kinds.

### 1. A pre-execution permission prompt

If the application layer decides `ask` before execution, the user sees the standard permission dialog:

- Bash permission confirmation
- FileEdit / FileWrite permission confirmation
- Other tools' own permission UIs

This prompt appears before the command actually runs.

### 2. A sandbox violation during execution

If the command has already entered the sandbox and the runtime detects a violation:

- The command fails.
- A `<sandbox_violations>` tag is appended to stderr so the model can understand what happened.
- The UI strips these tags before showing output to the user.
- `SandboxViolationStore` records the violation events.

This means users can usually see:

- the command failure itself
- UI hints such as how many sandbox blocks happened recently

### 3. Out-of-bounds network requests

Network is a special case.

When access to a host outside the sandbox needs extra confirmation, the project shows a dedicated network authorization dialog, for example:

- `Network request outside of sandbox`

Unlike filesystem runtime blocks, this has an explicit interactive authorization UI.

## Why filesystem violations usually don't prompt "allow once more"

This is a deliberate design choice.

For the filesystem, the project prefers to:

- ask in the application layer before execution,
- or let the command fail because of the sandbox after execution.

It avoids popping up a new "allow writing this system path?" dialog halfway through a run.

Benefits:

- The boundary is more stable.
- The user's mental model is clearer.
- The shell runtime cannot be incrementally escalated into an ever looser environment.

Network access, on the other hand, suits temporary per-host authorization, so it has its own authorization dialog.

## Common misconceptions

### Misconception 1: The sandbox protects all file modifications

No. It mainly protects **shell subprocesses**.

Direct file editing tools go through the application-layer permission system, not the shell sandbox.

### Misconception 2: With the sandbox on, the permission system is no longer needed

No. The sandbox only limits process capabilities. It does not interpret user intent, path safety semantics, tool modes, or the approval experience.

That is why the project keeps its elaborate `allow / ask / deny` system: the two have different responsibilities.

### Misconception 3: If the sandbox blocks a dangerous operation, the application-layer checks are worthless

No. The value of application-layer checks is:

- earlier prompting
- a better user experience
- finer semantic judgment
- they also apply to tools that do not go through the shell

The sandbox is the final backstop.

## FAQ

### Q1: What happens with `echo hi > /etc/hosts` on Linux?

With BashTool:

- It usually enters the sandbox.
- The default sandbox does not allow writing `/etc`.
- So the command fails at runtime.

With FileEditTool:

- It does not enter the sandbox.
- It is usually blocked first by the application-layer file permission check.

### Q2: What happens when editing `C:\Windows\System32\drivers\etc\hosts` on Windows?

On native Windows there is usually no shell sandbox backstop, so protection relies mainly on the application-layer permission system and the tools' own checks.

### Q3: If the sandbox is so strong, why keep `dangerouslyDisableSandbox`?

Because some real development tasks genuinely need to cross the default boundary, for example:

- accessing toolchain directories not on the allowlist
- debugging the system-level environment
- exceptional operations an administrator explicitly allows

But the project makes this entry point very conspicuous and lets administrators disable it outright through policy, so it does not become the default path.

### Q4: When is the sandbox's value most noticeable?

When `autoAllowBashIfSandboxed` is on.

Then many workspace commands run with few or no prompts, yet even if the model occasionally produces an out-of-bounds command, system-level write and network capabilities remain confined by the boundary.
