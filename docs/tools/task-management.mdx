## Dual-track architecture: TodoWrite V1 and Tasks V2

Claude Code's task management is not a single system. It is two coexisting implementations that switch by run mode:

| Dimension | V1: TodoWrite | V2: TaskCreate / TaskUpdate / TaskList / TaskGet |
|-----------|---------------|---------------------------------------------------|
| **Enabled when** | Non-interactive (pipe/SDK) or `isTodoV2Enabled()` returns `false` | Interactive REPL (default) or `CLAUDE_CODE_ENABLE_TASKS=1` |
| **Storage** | In memory at `AppState.todos[sessionId]` (Zustand store) | File system at `~/.claude/tasks/<taskListId>/<id>.json` |
| **Data model** | `{content, status, activeForm}`, a flat triple | `{id, subject, description, activeForm, owner, status, blocks[], blockedBy[], metadata}`, a full entity |
| **Persistence** | Lost when the process exits | Survives across processes, supports concurrent access by multiple agents |
| **Concurrency safety** | None (one writer per session) | File locks + high-water mark + TOCTOU protection |

The switching logic lives in `isTodoV2Enabled()` (`src/utils/tasks.ts:133`): interactive sessions enable V2 by default, and SDK/pipe mode falls back to V1. The two are mutually exclusive: `TodoWriteTool.isEnabled` returns `!isTodoV2Enabled()`, while `TaskCreateTool.isEnabled` returns `isTodoV2Enabled()`.

## V1: the minimal design of TodoWrite

TodoWrite is essentially a **full replacement** operation. Each call passes the complete `todos[]` array and overwrites the previous state entirely:

```typescript
// packages/builtin-tools/src/tools/TodoWriteTool/TodoWriteTool.ts — core of call()
async call({ todos }, context) {
  const todoKey = context.agentId ?? getSessionId()
  const oldTodos = appState.todos[todoKey] ?? []
  const allDone = todos.every(_ => _.status === 'completed')
  const newTodos = allDone ? [] : todos  // clear the list when everything is done
  // ... write to AppState
}
```

### Smart clearing and the verification nudge

One subtle design point: when all tasks are `completed`, `newTodos` is set to an empty array (rather than keeping a list of `completed` items). This ensures the UI has no visual noise from finished work.

V1 also contains a **verification nudge** mechanism: when the main-thread agent finishes 3+ tasks and none of them is a verification step, the system appends a hint to the tool_result urging the agent to spawn a verification sub-agent:

```typescript
// Condition: main thread + all done + ≥3 items + no verification task
if (allDone && todos.length >= 3 && !todos.some(t => /verif/i.test(t.content))) {
  verificationNudgeNeeded = true
}
// Appended to the tool_result:
// "NOTE: You just closed out 3+ tasks and none was a verification step..."
```

This is a defensive design that keeps the agent from "declaring itself done". It works through a structural nudge rather than a hard constraint.

## V2: the file-system-persisted task system

### Data model

Each task is a separate JSON file at `~/.claude/tasks/<taskListId>/<id>.json`:

```typescript
// src/utils/tasks.ts — TaskSchema
{
  id: string,           // auto-incrementing integer (1, 2, 3...)
  subject: string,      // imperative title (e.g. "Fix auth bug")
  description: string,  // detailed description
  activeForm?: string,  // present-continuous form (e.g. "Fixing auth bug"), used by the spinner
  owner?: string,       // ID/name of the agent that claimed the task
  status: "pending" | "in_progress" | "completed",
  blocks: string[],     // IDs of the tasks this task blocks
  blockedBy: string[],  // IDs of the tasks that block this task
  metadata?: Record<string, unknown>  // arbitrary extra data
}
```

### Priority for resolving the task list ID

`getTaskListId()` resolves task ownership with five levels of priority:

1. `CLAUDE_CODE_TASK_LIST_ID` environment variable (explicit override)
2. The teamName from the in-process teammate context (shares the leader's task list)
3. `CLAUDE_CODE_TEAM_NAME` environment variable (process-level teammate)
4. The teamName the leader set through `setLeaderTeamName()`
5. `getSessionId()` (fallback for standalone sessions)

This means that in multi-agent team mode, all teammates automatically share one task list with no extra coordination.

### ID allocation and the high-water mark

Task IDs are simple incrementing integers, but concurrent scenarios need protection against races:

```typescript
// src/utils/tasks.ts — createTask() simplified
async function createTask(taskListId, taskData) {
  release = await lockfile.lock(lockPath, LOCK_OPTIONS)  // acquire the exclusive lock
  const highestId = await findHighestTaskId(taskListId)   // read the current max ID
  const id = String(highestId + 1)                        // increment
  await writeFile(path, JSON.stringify({ id, ...taskData }))
  return id
}
```

The lock configuration retries 30 times with exponential backoff (about 2.6 seconds in total), which suits swarm scenarios with 10+ concurrent agents.

The high-water mark file `.highwatermark` ensures IDs are never reused after a deletion: even if task #5 is deleted, the next new task is still #6.

## Dependency management: blocks / blockedBy

Dependencies between tasks are implemented with doubly linked `blocks` / `blockedBy` fields:

- `taskA.blocks = ["3"]` means "task 3 cannot start until task A is done"
- `task3.blockedBy = ["A"]` means "task 3 must wait for task A to complete"

The `blockTask()` function maintains both ends:

```typescript
// src/utils/tasks.ts — blockTask()
// A blocks B → add B to A.blocks, and also add A to B.blockedBy
if (!fromTask.blocks.includes(toTaskId)) {
  await updateTask(taskListId, fromTaskId, { blocks: [...fromTask.blocks, toTaskId] })
}
if (!toTask.blockedBy.includes(fromTaskId)) {
  await updateTask(taskListId, toTaskId, { blockedBy: [...toTask.blockedBy, fromTaskId] })
}
```

When a task is deleted, the system automatically cleans up every dependency reference pointing to it (`deleteTask()` walks all tasks and removes the references from `blocks` and `blockedBy`).

## Task claiming and concurrency control

`claimTask()` is V2's core concurrency primitive and supports two lock granularities:

### 1. Task-level lock (default)

Locks only the target task file, which suits single-agent scenarios:

```
getTask → check owner → check status → check blockedBy → write owner
```

### 2. List-level lock + agent-busy check

With `checkAgentBusy: true`, the whole task list directory is locked (a `.lock` file), and the following is done atomically:

```
listTasks → check task status → check dependencies → check whether the agent already owns another unfinished task → write owner
```

A claim can fail for 5 reasons:

| `reason` | Meaning |
|----------|---------|
| `task_not_found` | The task ID does not exist |
| `already_claimed` | Already claimed by another agent |
| `already_resolved` | The task is already marked completed |
| `blocked` | The blockedBy list contains an unfinished task |
| `agent_busy` | The agent already owns another unfinished task (only in `checkAgentBusy` mode) |

## Task lifecycle in agent teams

In swarms mode, the lifecycle of the task system looks like this:

```
Leader creates the team
  ↓
Leader creates tasks with TaskCreate (status=pending, owner=undefined)
  ↓
Leader sets dependencies with TaskUpdate (addBlocks/addBlockedBy)
  ↓
Teammate calls TaskList → finds a claimable task
  ↓
Teammate calls TaskUpdate(taskId, {status: "in_progress"})
         → owner is set to the teammate's name automatically
         → Leader receives a task_assignment notification through the mailbox
  ↓
Teammate finishes the work → TaskUpdate(taskId, {status: "completed"})
         → tool_result says "Call TaskList to find your next available task"
         → other tasks that depend on this one are unblocked automatically
  ↓
Teammate exits abnormally → unassignTeammateTasks()
         → unfinished tasks are reset to pending + owner=undefined
         → Leader is notified and reassigns them
```

### Hooks integration

TaskCreate and TaskUpdate both integrate with the hooks system:

- **On creation**: `executeTaskCreatedHooks`. An external hook can block task creation (a blockingError causes the task to be deleted immediately)
- **On completion**: `executeTaskCompletedHooks`. An external hook can block a task from being marked completed

This lets external systems (CI, approval flows) take part in the task state machine.

## activeForm: a terminal UX detail

Each task has two text fields:

- `subject`: an imperative sentence, used in the task list display ("Fix auth bug")
- `activeForm`: the present-continuous form, used by the spinner animation ("Fixing auth bug...")

When `activeForm` is absent, the spinner falls back to showing `subject`. This seemingly small design ensures that while waiting, the user sees "what is being done" rather than "what is to be done".

## How Plan Mode works with the task system

Plan Mode and the task system are complementary but independent mechanisms:

1. Plan Mode restricts the toolset to read-only operations (search, read), forcing the AI to understand before acting
2. In Plan Mode the AI builds a task list with TaskCreate
3. After the user approves, Plan Mode is exited
4. The AI executes items in `blockedBy` topological order, marking progress with TaskUpdate on each one

The `shouldDefer: true` property ensures these tool calls do not trigger permission confirmation dialogs. Task management operations are always auto-approved because they have no side effects.
