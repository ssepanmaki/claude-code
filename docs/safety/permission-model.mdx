## Three permission behaviors

For every tool call, the system reaches one of three verdicts:

| Behavior | Meaning | Return type | Typical scenario |
|------|------|---------|---------|
| **Allow** | Allowed automatically, the user does not notice | `{ behavior: 'allow', updatedInput, decisionReason }` | Read reads a file inside the project |
| **Ask** | Shows a confirmation dialog | `{ behavior: 'ask', message, suggestions, metadata }` | Bash runs an unknown command |
| **Deny** | Rejected outright | `{ behavior: 'deny', message, decisionReason }` | Trying to run a forbidden command |

These behaviors are defined by the `PermissionResult` type (`src/utils/permissions/PermissionResult.ts`).

## Where permission rules come from

Rules are gathered from 8 sources (`PERMISSION_RULE_SOURCES`, `permissions.ts:109`), in order of priority from low to high (later ones override earlier ones):

```
1. userSettings   — ~/.claude/settings.json (across projects)
2. projectSettings — .claude/settings.json (shared with the team)
3. localSettings  — .claude/settings.local.json (gitignored, personal overrides)
4. flagSettings   — the --settings command-line argument
5. policySettings — policy delivered by enterprise admins (users cannot override)
6. cliArg         — the --allow/--deny command-line arguments
7. command        — the allowedTools allowlist of the Skill tool
8. session        — manually granted by the user in the current conversation ("Always allow")
```

Each source maintains three arrays: `alwaysAllowRules[source]`, `alwaysAskRules[source]`, `alwaysDenyRules[source]`.

The rule data structure is `PermissionRule`:
```typescript
{
  source: PermissionRuleSource      // which layer it came from
  ruleBehavior: 'allow' | 'ask' | 'deny'
  ruleValue: {
    toolName: string                // e.g. "Bash", "mcp__server1"
    ruleContent?: string            // e.g. "git *", "src/**"
  }
}
```

## The rule matching engine

### Three matching dimensions

`permissions.ts` implements three matching dimensions:

**1. Tool name matching** (`toolMatchesRule()`, line 238)

Matches the whole tool, only when the rule has no `ruleContent`:
```typescript
// Exact match
rule "Bash" → matches BashTool
rule "mcp__server1" → matches all tools of that MCP server (server level)
rule "mcp__server1__*" → wildcard match (same as above)
```

MCP tools use `getToolNameForPermissionCheck()` to get the match name, supporting both prefixed (`mcp__server__tool`) and unprefixed forms.

**2. Command pattern matching** (`checkPermissions()` of BashTool)

BashTool parses the command pattern through `preparePermissionMatcher()` (`Tool.ts:520`):
```json
{"tool": "Bash", "ruleContent": "git *"}  → matches "git commit -m 'fix'"
```

Commands are parsed through the AST (`readOnlyValidation.ts` uses tree-sitter bash), and the first subcommand is extracted for matching.

**3. Path matching** (`checkPermissions()` of the file tools)

The Read/Edit/Write tools extract the file path through `getPath()` and match it against the glob pattern in `ruleContent`:
```json
{"tool": "Edit", "ruleContent": "src/**"}  → matches "src/utils/foo.ts"
```

### The full permission check flow

Each tool call's permission check (`canUseTool()` → `checkPermissions()`) goes through these steps:

```
1a. Blanket deny check
    getDenyRuleForTool() → does the tool name fully match a deny rule?
    ↓ hit → deny (the tool is already filtered out at the getTools() stage)

1b. Blanket allow check
    toolAlwaysAllowedRule() → does the tool name fully match an allow rule?
    ↓ hit → allow

2. The tool's own checkPermissions()
    Each tool has custom logic:
    - BashTool: readOnlyValidation → sandbox decision → AST parsing → pattern matching
    - FileEditTool: path allowlist check
    - SkillTool: safe properties allowlist + exact/prefix matching
    ↓ returns PermissionResult

3. Hook system
    executePermissionRequestHooks() → a PreToolUse hook can override
    ↓ hook returns deny → deny
    ↓ hook returns ask → escalate to ask

4. Ask rule check
    getAskRules() → hit → ask

5. Default behavior
    The default is decided by the current permissionMode
    - 'default': most tools ask
    - 'plan': writes are denied, reads are allowed
    - 'bypass': everything is allowed
```

## Permission modes

| Mode | `PermissionMode` value | Use case | Behavior |
|------|---------------------|---------|------|
| **Default** | `'default'` | Everyday use | Sensitive operations are confirmed one by one |
| **Plan Mode** | `'plan'` | Exploration phase | Read only, no writes (`isReadOnly()` check) |
| **Accept Edits** | `'acceptEdits'` | Fast iteration | File edits inside the workspace are allowed automatically; other operations still need confirmation |
| **Don't Ask** | `'dontAsk'` | Fewer interruptions | Decides automatically where possible, with fewer confirmation dialogs |
| **Auto** | `'auto'` | Trust the AI | Decides automatically through the transcript classifier (needs the `TRANSCRIPT_CLASSIFIER` feature flag) |
| **Bypass** | `'bypassPermissions'` | Full trust | All operations are allowed automatically (needs an explicit `--dangerously-skip-permissions`) |

Switching to Plan Mode is triggered by `EnterPlanModeTool.call()`:
```typescript
// EnterPlanModeTool.ts:88
context.setAppState(prev => ({
  ...prev,
  toolPermissionContext: applyPermissionUpdate(
    prepareContextForPlanMode(prev.toolPermissionContext),
    { type: 'setMode', mode: 'plan', destination: 'session' },
  ),
}))
```

On exit, `ExitPlanModeV2Tool` restores the previous mode.

## Denial Tracking: preventing dead loops

`src/utils/permissions/denialTracking.ts` implements the denial tracking mechanism:

```typescript
const DENIAL_LIMITS = {
  maxConsecutive: 3,        // limit on consecutive denials of the same tool
  maxTotal: 20,             // total denial limit
}
```

When the AI has been denied the same kind of operation consecutively up to the limit:
1. `recordDenial()` records the denial and increments the counter
2. `shouldFallbackToPrompting()` detects the consecutive denials and returns true
3. The system injects a message into the AI: "Your previous tool call was rejected..."
4. The AI is forced to change strategy, avoiding the dead loop of "repeatedly requesting the same denied operation"

When an operation succeeds, `recordSuccess()` resets the counter.

## Updating rules at runtime

Permission rules can be updated dynamically at runtime (`applyPermissionUpdate()`, `PermissionUpdate.ts`):

```typescript
type PermissionUpdate =
  | { type: 'addRules', destination, rules, behavior }
  | { type: 'replaceRules', destination, rules, behavior }
  | { type: 'removeRules', destination, rules, behavior }
  | { type: 'setMode', destination, mode }
  | { type: 'addDirectories', destination, directories }
  | { type: 'removeDirectories', destination, directories }
```

When the user chooses "Always allow" in the Ask dialog, the system calls `persistPermissionUpdates()` to write the rule into the settings file of the corresponding layer (project/user/managed) and updates the in-memory `toolPermissionContext`.
