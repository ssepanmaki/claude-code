## Storage architecture of the memory system

Source paths: `src/memdir/paths.ts`, `src/memdir/memdir.ts`

Claude Code's memory system is **purely file-based**: no database, no vector store, only Markdown files and a directory structure.

### Directory layout

```
~/.claude/projects/<sanitized-git-root>/memory/
├── MEMORY.md                    ← entry index (loaded every conversation)
├── user_role.md                 ← user memory
├── feedback_testing.md          ← feedback memory
├── project_mobile_release.md    ← project memory
├── reference_linear_ingest.md   ← reference memory
└── logs/                        ← KAIROS mode: daily logs
    └── 2026/
        └── 04/
            └── 2026-04-01.md
```

Path resolution chain (`getAutoMemPath()`):
1. The `CLAUDE_COWORK_MEMORY_PATH_OVERRIDE` environment variable (full-path override for the Cowork SDK)
2. The `autoMemoryDirectory` setting (only from `policySettings`/`localSettings`/`userSettings`. `projectSettings` is **deliberately excluded**, to stop a malicious repository from pointing the memory path at `~/.ssh`)
3. Default: `<memoryBase>/projects/<sanitized-git-root>/memory/`

All worktrees of the same Git repository share one memory directory (`findCanonicalGitRoot()` finds the real `.git` root).

### The MEMORY.md index

`MEMORY.md` is the entry index of memory and is loaded into context in full every conversation:

```typescript
// memdir.ts:34-38
export const ENTRYPOINT_NAME = 'MEMORY.md'
export const MAX_ENTRYPOINT_LINES = 200
export const MAX_ENTRYPOINT_BYTES = 25_000
```

The index has **two caps**: 200 lines AND 25KB. Exceeding either gets it truncated by `truncateEntrypointContent()` with a warning appended. The reason: at p97 an index file fits within 200 lines, but some index entries are very long (p100 observed 197KB/200 lines), and the byte cap catches these long-line outliers.

Index entry format:
```markdown
- [Title](file.md) — one-line hook
```

One entry per line, within ~150 characters. `MEMORY.md` itself has no frontmatter. It is just a list of links, not memory content.

## The four-type taxonomy

Source path: `src/memdir/memoryTypes.ts`

Memories are constrained to a **closed four-type system**, and each type has explicit `<when_to_save>`, `<how_to_use>` and `<body_structure>` specifications:

| Type | What it stores | Typical trigger |
|------|----------------|-----------------|
| **user** | The user's role, preferences, technical background | "I'm a data scientist", "I've written Go for ten years" |
| **feedback** | The user's corrections and confirmations of AI behavior | "Don't mock the database", "a single PR is better" |
| **project** | Project context that cannot be derived from code | "Merge freeze starts Thursday", "the auth rewrite is a compliance requirement" |
| **reference** | Pointers to external systems | "Pipeline bugs are in the Linear INGEST project" |

Key design constraint: **store only information that cannot be derived from the current project state**. Code architecture, file paths and git history can all be fetched live and need no memory.

### Dual-channel capture for feedback

The `when_to_save` instruction of the `feedback` type stresses this in particular:

> Record from failure AND success: if you only save corrections, you will avoid past mistakes but drift away from approaches the user has already validated, and may grow overly cautious.

This means the AI saves not only when the user says "don't do this" but also when the user says "yes, exactly like that". The latter is harder to catch but equally important, since it keeps the AI's behavior from drifting over time.

### Frontmatter format of each memory

```markdown
---
name: {{memory name}}
description: {{one-line description — used to judge relevance in the future}}
type: {{user, feedback, project, reference}}
---

{{memory content — for feedback/project types, including **Why:** and **How to apply:** lines is recommended}}
```

The `description` field is the key: it is not a summary for humans but the search keywords the AI recall system uses to judge relevance.

## The smart recall mechanism

Source paths: `src/memdir/findRelevantMemories.ts`, `src/memdir/memoryScan.ts`

Not every memory fits every conversation. The system uses a **lightweight Sonnet side query** to pick the most relevant memories.

### Recall flow

```
User message → findRelevantMemories(query, memoryDir)
  ├── scanMemoryFiles() — scan the frontmatter of all memory files
  ├── selectRelevantMemories() — Sonnet side query, picks ≤5 from the manifest
  └── returns [{path, mtimeMs}, ...]
```

The core is the `selectRelevantMemories()` function, which calls `sideQuery()` (a separate lightweight API call):

```typescript
// findRelevantMemories.ts:98-121
const result = await sideQuery({
  model: getDefaultSonnetModel(),  // use Sonnet for selection (not the main model)
  system: SELECT_MEMORIES_SYSTEM_PROMPT,
  messages: [{
    role: 'user',
    content: `Query: ${query}\n\nAvailable memories:\n${manifest}${toolsSection}`
  }],
  max_tokens: 256,
  output_format: { type: 'json_schema', schema: { ... } },
})
```

### Denoising for recently used tools

When the AI is already using a tool, recalling that tool's usage documentation is noise (the working context is already in the conversation). The `recentTools` parameter lets the recall system skip those memories:

```typescript
// findRelevantMemories.ts:92-95
const toolsSection = recentTools.length > 0
  ? `\n\nRecently used tools: ${recentTools.join(', ')}`
  : ''
```

The system prompt states explicitly: "If a list of recently used tools is provided, do not select usage reference or API documentation for those tools. **Still select** warnings, gotchas or known issues about those tools. That is exactly the information that matters most when using them."

### Already-surfaced dedup

The `alreadySurfaced` parameter filters out file paths already shown in earlier turns, so Sonnet's 5-slot budget is spent on new candidates instead of recalling the same file again.

## How memory is injected into the system prompt

Source paths: `src/memdir/memdir.ts` → `src/context.ts`

`loadMemoryPrompt()` is the entry point for memory injection, called once per session (cached via `systemPromptSection('memory', ...)`):

```typescript
// memdir.ts:419-507
export async function loadMemoryPrompt(): Promise<string | null> {
  // Priority: KAIROS log mode → TEAMMEM combined mode → plain auto memory
  if (feature('KAIROS') && autoEnabled && getKairosActive()) {
    return buildAssistantDailyLogPrompt(skipIndex)
  }
  if (feature('TEAMMEM') && teamMemPaths!.isTeamMemoryEnabled()) {
    return teamMemPrompts!.buildCombinedMemoryPrompt(...)
  }
  if (autoEnabled) {
    return buildMemoryLines('auto memory', autoDir, ...).join('\n')
  }
  return null
}
```

Injection timing: when `getSystemContext()` is called in `context.ts`, the memory prompt is assembled as a section of the system prompt. The contents of `MEMORY.md` are injected as a **user context message** (not in the system prompt), which lets it benefit from Prompt Cache prefix sharing.

## KAIROS mode: daily logs

Source path: `src/memdir/memdir.ts` (`buildAssistantDailyLogPrompt`)

Long-running assistant sessions use a different memory strategy:

- **Standard mode**: the AI maintains `MEMORY.md` as a live index plus separate memory files
- **KAIROS mode**: the AI only appends logs to date files (`logs/YYYY/MM/YYYY-MM-DD.md`) and does no reorganization

```typescript
// Log path pattern (not a literal path, because the prompt is cached)
const logPathPattern = join(memoryDir, 'logs', 'YYYY', 'MM', 'YYYY-MM-DD.md')
```

A separate nightly `/dream` skill distills the logs into topic files plus the `MEMORY.md` index.

## Defense against memory drift

Source path: `src/memdir/memoryTypes.ts` (`TRUSTING_RECALL_SECTION`)

Memories can go stale. The system places a dedicated section in the prompt, "Before recommending from memory":

```
A memory that names a specific function, file, or flag is a claim
that it existed *when the memory was written*. It may have been
renamed, removed, or never merged. Before recommending it:

- If the memory names a file path: check the file exists.
- If the memory names a function or flag: grep for it.
```

The title of this section was validated by A/B testing: "Before recommending from memory" (action-oriented) outperformed "Trusting what you recall" (abstract description), 3/3 vs 0/3.

### Strict semantics for ignoring memory

```
If the user says to *ignore* or *not use* memory:
proceed as if MEMORY.md were empty.
Do not apply remembered facts, cite, compare against,
or mention memory content.
```

This addresses a common AI anti-pattern: the user says "ignore the memory about X", and the AI identifies the code correctly but still adds "unlike what memory says about Y". That is not "ignoring"; it is "acknowledging and then overriding".

## Linkage between Session Memory and compaction

Source path: `src/services/compact/sessionMemoryCompact.ts`

The memory system is deeply integrated with context compaction. When both the `tengu_session_memory` and `tengu_sm_compact` feature flags are on, compaction prefers Session Memory over a traditional summary:

```typescript
// sessionMemoryCompact.ts:57-61
const DEFAULT_SM_COMPACT_CONFIG = {
  minTokens: 10_000,           // keep at least 10K tokens after compaction
  minTextBlockMessages: 5,     // keep at least 5 text messages
  maxTokens: 40_000,           // keep at most 40K tokens
}
```

SM-compact does not call the compaction API (there is no summarization model). It uses the existing Session Memory directly as the summary, which is faster, cheaper, and loses no information.
