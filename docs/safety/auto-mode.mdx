## Overview

Auto mode is a Claude Code permission mode that puts the AI into **continuous autonomous execution**. Unlike the traditional modes, where every sensitive operation pops up a permission dialog and waits for the user's approval, auto mode uses an AI classifier (the transcript classifier) to decide automatically whether each tool call is safe, giving an uninterrupted execution experience.

```
Permission mode hierarchy:

default  →  auto  →  bypassPermissions
(confirm    (AI classifier   (allow
 each one)   approves)        everything)
```

## Core architecture

### 1. The AI classifier (yoloClassifier)

The classifier is the heart of auto mode and lives in `src/utils/permissions/yoloClassifier.ts`.

Every tool call is evaluated by the classifier, which returns one of three verdicts:

| Verdict | Meaning | Handling |
|------|------|---------|
| **allow** | The operation is safe | Runs directly, invisible to the user |
| **deny** | The operation is dangerous | Refused, with a denial message returned to the AI |
| **ask** | Cannot be determined | Falls back to the traditional permission dialog |

The classifier's judgment is based on the full conversation context (the transcript), not just a single command, so it can understand the intent and context of an operation.

### 2. The two-stage classification pipeline

The classifier supports two-stage XML classification (`classifyYoloActionXml`):

```
Stage 1 — "fast"
├── max_tokens=64, stop_sequences trigger an immediate yes/no
├── If allow → let it through directly (fastest path)
└── If block → go to Stage 2

Stage 2 — "thinking"
├── Chain-of-thought reasoning
├── Reduces false positives
└── Final decision: allow / deny / ask
```

Both stages share the same system prompt and user content, using the API's prompt caching (1-hour TTL) to optimize performance.

The mode can be chosen through configuration:
- `'both'` (default): run both stages
- `'fast'`: run only Stage 1
- `'thinking'`: run only Stage 2

### 3. Classifier result type

```typescript
// src/types/permissions.ts
type YoloClassifierResult = {
  thinking?: string          // The classifier's reasoning
  shouldBlock: boolean       // Whether to block
  reason: string             // Reason for the decision
  unavailable?: boolean      // Whether the classifier is unavailable
  transcriptTooLong?: boolean // Whether the conversation exceeds the context window
  model: string              // The classifier model used
  stage?: 'fast' | 'thinking' // Which stage made the decision
  // ... monitoring fields such as token usage and latency
}
```

## Safety mechanisms

### Dangerous-permission stripping

On entering auto mode, the system calls `stripDangerousPermissionsForAutoMode()` (`permissionSetup.ts:510`), which removes every allow rule that could bypass the classifier.

The rule types that get stripped (`dangerousPatterns.ts`):

| Rule type | Example | Why it is stripped |
|---------|------|---------|
| **Bash code execution** | `Bash(python:*)`, `Bash(node:*)` | Interpreters can run arbitrary code and bypass classifier review |
| **Shell entry points** | `Bash(bash:*)`, `Bash(sh:*)` | Direct shell access is effectively unrestricted |
| **Agent rules** | `Agent(*)` | Any Agent allow rule would bypass classifier approval of sub-agents |
| **PowerShell code execution** | `PowerShell(node:*)` | Same logic as Bash |
| **Privilege escalation** | `Bash(sudo:*)`, `Bash(eval:*)` | Can run arbitrary commands |

The stripped rules are held in `strippedDangerousRules` and restored on leaving auto mode through `restoreDangerousPermissions()`.

### Model support detection

Not every model supports auto mode. `modelSupportsAutoMode()` (`src/utils/betas.ts`) checks whether the current model has the safety-classification capability. Models that lack it cannot enter auto mode.

### Circuit breaker

`autoModeState.ts` maintains a circuit-breaker flag:

```typescript
let autoModeCircuitBroken = false  // Controlled by remote config
```

When the remote config (GrowthBook `tengu_auto_mode_config.enabled`) is set to `'disabled'`, the circuit breaker trips and blocks both entering and continuing to use auto mode. This gives Anthropic a remote emergency shutdown capability.

## Mode-switch state management

### Entering auto mode

`transitionPermissionMode()` (`permissionSetup.ts:597`) handles all mode switches:

```
1. Check whether the auto mode gate is on (isAutoModeGateEnabled)
2. Set autoModeActive = true
3. Call stripDangerousPermissionsForAutoMode() to strip dangerous rules
4. Inject the Auto Mode system prompt into the conversation
```

### Exiting auto mode

```
1. Set autoModeActive = false
2. Set needsAutoModeExitAttachment = true (triggers the exit notice)
3. Call restoreDangerousPermissions() to restore the stripped rules
4. Inject an "Exited Auto Mode" notice into the conversation
```

### Activation paths

Auto mode can be activated in these ways:
- The CLI flag `--enable-auto-mode`
- The `autoMode` setting in settings.json
- Plan mode uses auto mode semantics by default (`useAutoModeDuringPlan`, default true)
- SDK control messages
- Shift+Tab toggling in the REPL

## System prompts

### On entry (full instructions)

The instructions injected into the conversation (`messages.ts:3481`):

> Auto mode is active. The user chose continuous, autonomous execution. You should:
>
> 1. **Execute immediately**: implement directly and make reasonable assumptions
> 2. **Minimize interruptions**: use your own judgment on routine decisions and ask fewer questions
> 3. **Prefer action over planning**: write code directly by default and do not enter plan mode
> 4. **Expect course corrections**: the user can correct you at any time
> 5. **Do not take overly destructive actions**: deleting data or modifying production systems still needs confirmation
> 6. **Avoid data exfiltration**: do not proactively share secrets or internal documents

### While running (sparse instructions)

A short reminder is injected on later turns:

> Auto mode still active. Execute autonomously, minimize interruptions, prefer action over planning.

### On exit (exit instructions)

> You have exited auto mode. Ask clarifying questions when the approach is ambiguous rather than making assumptions.

## Working with plan mode

Plan mode uses auto mode semantics by default (`getUseAutoModeDuringPlan()`, default true). This means:

- When plan mode is entered and auto mode is available, the classifier is activated too
- `isAutoModeActive()` is the authoritative signal (`prePlanMode`/`strippedDangerousRules` are unreliable)
- Exiting plan mode also exits auto mode

## Fallback when the classifier is unavailable

When the classifier API is unavailable (`unavailable: true` or `transcriptTooLong: true`):

- It does not allow directly; it falls back to the traditional permission dialog (ask)
- A message is sent to the AI: "{model} is temporarily unavailable, so auto mode cannot determine the safety of {toolName} right now."
- Deterministic errors (such as a conversation that is too long) are not retried and degrade straight away

## Classifier prompt templates

The classifier's behavior is controlled by three prompt files in `src/utils/permissions/yolo-classifier-prompts/`. They are inlined as string constants through `require()` at build time and cannot be modified at runtime.

### auto_mode_system_prompt.txt

The main system prompt, defining the classifier's role, classification flow, and decision categories. It contains:

- **Classification flow**: understand the operation → check user intent → assess risk
- **BLOCK always**: external code execution, irreversible deletion, unauthorized persistence, security weakening, privilege escalation, network services
- **BLOCK unless explicit intent**: writes outside the CWD, system package management, git push, large-scale changes
- **ALLOW safe operations**: reading files, search, read-only git commands, tests/lint/build, edits inside the CWD
- The `<permissions_template>` placeholder, replaced at runtime with a concrete permissions template (external or anthropic)
- A closing line, `Use the classify_result tool to report your classification.`, which in XML mode is replaced with a description of the `<block>` tag format

### permissions_external.txt

The permissions template for external users. Default rules (in bullet format) are wrapped inside three `<user_*_to_replace>` tags, and user-defined rules **replace** the defaults wholesale:

```
<user_allow_rules_to_replace>
- Default allow rule 1
- Default allow rule 2
</user_allow_rules_to_replace>
```

- **allow**: 9 default rules (read-only commands, version checks, read-only git, tests/lint/build, package installs, file operations inside the CWD, and so on)
- **soft_deny**: 10 default rules (external code execution, recursive deletion, shell config modification, privilege escalation, network services, and so on)
- **environment**: 4 environment descriptions (terminal environment, auto mode context, dev tools available, any language/framework)

`getDefaultExternalAutoModeRules()` extracts the bullet items from this file for the output of the `claude auto-mode defaults` command.

### permissions_anthropic.txt

The permissions template for Anthropic's internal use. The default rules sit **outside** the tags, the tags are empty, and user-defined rules are layered on by **appending**:

```
- Default rule (outside the tag, always in effect)
<user_allow_rules_to_replace>
</user_allow_rules_to_replace>
```

Compared with the external version, it additionally contains:
- Read-only cloud CLI commands (aws describe, gcloud describe, kubectl get, and so on)
- Infrastructure-as-code plan commands (terraform plan, pulumi preview, and so on)
- Matching deny rules (cloud resource creation/modification/deletion, IaC apply, production access, and so on)

### Template substitution flow

```
buildYoloSystemPrompt()
  ├── BASE_PROMPT.replace('<permissions_template>', EXTERNAL/ANTHROPIC_TEMPLATE)
  ├── .replace(<user_allow_rules_to_replace>, userAllow ?? defaults)
  ├── .replace(<user_deny_rules_to_replace>, userDeny ?? defaults)
  └── .replace(<user_environment_to_replace>, userEnvironment ?? defaults)
```

- External template: a non-empty user setting **replaces** the content inside the matching tag; otherwise the default is kept
- Internal template: user settings are **appended** after the defaults (the tags are empty at the end)
