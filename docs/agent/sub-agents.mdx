## Four concepts to tell apart

What Claude Code loosely calls a "sub-agent" is actually four different execution paths:

| Type | Triggered by | Goes through the Tool protocol? | How the result returns | Typical entry |
|------|--------------|---------------------------------|------------------------|---------------|
| Named sub-agent | The main model calls `Agent(...)` with `subagent_type` | Yes, it is a `tool_use` | The current turn's `tool_result`, or a `<task-notification>` after background completion | `src/tools/AgentTool/AgentTool.tsx` |
| AgentTool fork | The main model calls `Agent(...)` without `subagent_type`, and the fork gate is on | Yes, still the `Agent` tool | Returns `async_launched` first, then comes back to the main model as a task notification | `src/tools/AgentTool/AgentTool.tsx`, `src/tools/AgentTool/forkSubagent.ts` |
| Slash command fork | The user runs a slash command / skill with `context: fork` | No, it is not an `Agent` tool_use issued by the model | Normal mode returns the command output synchronously; assistant mode re-injects a hidden prompt in the background | `src/utils/processUserInput/processSlashCommand.tsx` |
| `runForkedAgent()` | A runtime-internal service forks off an execution branch directly | No, internal API | The caller consumes the result internally | `src/utils/forkedAgent.ts` |

One-line summary:

AgentTool fork is tool semantics for the model; `runForkedAgent()` is an implementation detail for internal runtime features; slash command fork is an execution mode for skills / commands.

## AgentTool main flow

The `Agent` tool the model sees ends up in `AgentTool.call()`. A normal named sub-agent runs through this chain:

```text
assistant message
  -> tool_use: Agent({ prompt, subagent_type?, run_in_background?, ... })
  -> query.ts: runTools(...)
  -> toolExecution.ts: await tool.call(...)
  -> AgentTool.call(...)
  -> resolve selectedAgent / fork path / permission mode / tool pool
  -> runAgent(...)
  -> finalizeAgentTool(...)
  -> mapToolResultToToolResultBlockParam(...)
  -> user message with tool_result
  -> query.ts starts next model turn with that tool_result
```

Key source entries:

| Code | Role |
|------|------|
| `src/tools/AgentTool/AgentTool.tsx` | `Agent` tool definition, routing, sync/async lifecycle |
| `src/tools/AgentTool/runAgent.ts` | The sub-agent's query loop, system prompt, MCP, sidechain transcript |
| `src/services/tools/toolExecution.ts` | Outer tool executor, where `await tool.call(...)` happens |
| `src/query.ts` | Main agentic loop; collects tool results and starts the next model call |
| `src/tasks/LocalAgentTask/LocalAgentTask.tsx` | Registration, state updates, and completion notification for background local agent tasks |

## AgentTool input parameters

The input schema of the `Agent` tool is defined by `baseInputSchema()` and `fullInputSchema()` in `AgentTool.tsx`. Some fields are hidden from the model-visible schema by feature gates, but `call()` handles those optional fields through a single `AgentToolInput` type.

### Basic parameters

| Parameter | Type | Required | Purpose | Affected path |
|-----------|------|----------|---------|---------------|
| `description` | `string` | Yes | A 3-5 word task summary used in the UI, task list, logs, background notifications, and output summaries | Not part of the sub-agent's actual prompt reasoning, but affects task display and notifications |
| `prompt` | `string` | Yes | The full task description for the sub-agent | A normal agent receives it as its user message; the fork path embeds it in a fork directive; the remote path sends it as the remote initial message |
| `subagent_type` | `string` | No | Selects a named agent type | When set, a named agent runs; when omitted, AgentTool fork runs if the fork gate is on, otherwise it falls back to `general-purpose` |
| `model` | `'sonnet' \| 'opus' \| 'haiku'` | No | Model override for this call | For named agents it takes priority over the agent definition's `model`; ignored in coordinator mode; the fork path inherits the parent model |
| `run_in_background` | `boolean` | No | Request background execution | When `true`, runs as an async task; hidden from the schema if background tasks are disabled or the fork gate is on |

### Multi-agent / teammate parameters

| Parameter | Type | Required | Purpose | Affected path |
|-----------|------|----------|---------|---------------|
| `name` | `string` | No | Names the spawned agent so it can be addressed with `SendMessage({ to: name })` | Together with `team_name` or the current team context it triggers a teammate spawn; for ordinary background sub-agents it also registers `name -> agentId` to make later messaging easier |
| `team_name` | `string` | No | The team to join or use | Together with `name` it triggers `spawnTeammate()`; when omitted it can inherit the current `appState.teamContext.teamName` |
| `mode` | permission mode | No | Permission mode hint for a teammate spawn | Currently only used for the teammate's `plan_mode_required: spawnMode === 'plan'`; it does not override the `permissionMode` of an ordinary local sub-agent |

`name + team_name` is a separate branch: it does not enter the normal `runAgent()` local sub-agent path, but calls `spawnTeammate()` and returns `teammate_spawned`. Spawning another teammate with `name` from inside a teammate is rejected, because the team roster is flat.

### Isolation and working-directory parameters

| Parameter | Type | Required | Purpose | Affected path |
|-----------|------|----------|---------|---------------|
| `isolation` | `'worktree'`; internal builds also support `'remote'` | No | Overrides the agent definition's isolation mode | `worktree` creates a temporary git worktree; `remote` delegates to CCR and returns `remote_launched` directly |
| `cwd` | `string` | No | The directory the sub-agent runs in | Only exposed in the `KAIROS` schema; changes the cwd of file and shell operations through `runWithCwdOverride()` |

The `isolation` input takes priority over the `isolation` in the agent definition. The schema text for `cwd` says not to combine it with `isolation: "worktree"`; in the implementation, if both appear, `cwd` takes precedence as the run directory but a worktree may still be created, so callers should treat the two as mutually exclusive.

### Parameter visibility and actual effect

| Parameter | When it may be hidden | Notes |
|-----------|-----------------------|-------|
| `run_in_background` | `DISABLE_BACKGROUND_TASKS` is in effect, or `isForkSubagentEnabled()` is true | When the fork gate is on, every `AgentTool` spawn is forced async, so the model need not choose |
| `cwd` | Non-`KAIROS` build / mode | Omitted from the schema, though the implementation type keeps the field |
| `isolation: "remote"` | Non-internal builds | External builds accept only `worktree` |
| `model` | Coordinator mode or fork path | The coordinator clears the model override; fork must inherit the parent model to keep the request prefix and behavior consistent |

### Priority between call parameters and the agent definition

| Setting | Call parameter | Agent definition | Final rule |
|---------|----------------|------------------|------------|
| Agent type | `subagent_type` | Default / active agents | An explicit `subagent_type` wins; when omitted, the fork gate decides between fork and `general-purpose` |
| Model | `model` | `selectedAgent.model` | For named agents the call parameter wins; otherwise the definition; otherwise inherit the parent model |
| Background | `run_in_background` | `selectedAgent.background` | Either being true makes it async; coordinator, assistant, and fork gate also force async |
| Isolation | `isolation` | `selectedAgent.isolation` | The call parameter wins |
| Permission mode | No local override parameter | `selectedAgent.permissionMode` | A normal sub-agent uses the definition's `permissionMode`, default `acceptEdits`; fork uses `bubble` |
| Tool set | No call parameter | `selectedAgent.tools` | A normal sub-agent is filtered by the definition inside `runAgent()`; fork uses the parent's exact tools |

## Agent definition fields

The `AgentTool` call parameters only describe "how to spawn this time". What determines an agent's default capabilities is the agent definition. Custom agents can come from user / project directories, JSON config, plugins, or built-in definitions, and their core fields all normalize into `AgentDefinition`.

### Common frontmatter

| Field | Type | Purpose | Runtime effect |
|-------|------|---------|----------------|
| `name` | `string` | Agent type name | The model matches it through `subagent_type`; plugin agents may carry a namespace prefix |
| `description` | `string` | Description of when to use it | Appears in the available agents list to help the main model choose |
| `tools` | `string[]` | Allowed tool set | Filtered inside `runAgent()` via `resolveAgentTools()`; `['*']` means all available tools |
| `disallowedTools` | `string[]` | Disallowed tool set | Supported by JSON agents to exclude tools from the allowed set |
| `prompt` | `string` | Body of the agent system prompt | A named sub-agent uses it to build its own system prompt |
| `model` | `string` | Default model | Can be overridden by `Agent({ model })`; `inherit` means inherit the parent model |
| `effort` | effort level or number | Reasoning effort level | Passed to the agent run configuration |
| `permissionMode` | permission mode | Default permission mode | Used when assembling a normal sub-agent's tool pool; defaults to `acceptEdits` when omitted |
| `background` | `boolean` | Whether to always run in the background | When true, runs async even without `run_in_background` in the call |
| `isolation` | `'worktree'` / `'remote'` | Default isolation mode | Can be overridden by the `isolation` call parameter |
| `maxTurns` | positive integer | Maximum agentic turns | Passed to `query()` to keep the sub-agent from looping forever |
| `color` | agent color | UI color | Used in grouped UI, the task panel, and teammate display |
| `memory` | `'user' \| 'project' \| 'local'` | Persistent memory scope | Appends agent memory to the system prompt and reads/writes the directory for that scope |

Example:

```md
---
name: code-reviewer
description: Review a code change and find correctness risks
tools:
  - Read
  - Grep
  - Glob
model: sonnet
permissionMode: acceptEdits
background: true
maxTurns: 8
memory: project
---

You are a focused code reviewer. Prioritize bugs, regressions, and missing tests.
```

### MCP, hooks, skills

| Field | Purpose | Notes |
|-------|---------|-------|
| `requiredMcpServers` | MCP server patterns that must exist before startup | `AgentTool.call()` waits for pending servers for up to about 30 seconds; errors if no tools are available |
| `mcpServers` | Agent-specific MCP servers | Initialized by `runAgent()`; lifecycle follows the sub-agent |
| `hooks` | Hooks registered for the agent's lifetime | `runAgent()` registers frontmatter hooks; session hooks are cleaned up when the agent stops |
| `skills` | Names of skills to preload | `runAgent()` resolves and injects them; plugin skills support namespaced or suffix matching |
| `initialPrompt` | Content prepended to the first user turn | Can be used to inject extra instructions at startup |

These fields belong to the agent definition, not to the `Agent(...)` call parameters. A caller cannot pass `tools`, `hooks`, or `skills` in a single `Agent` tool_use to override the agent definition.

### runAgent() extension points

`runAgent()` does more than hand a prompt to the model. Before and after entering the query loop it attaches a set of agent-level extension points:

| Extension point | When | Purpose |
|-----------------|------|---------|
| `SubagentStart` hooks | Before the sub-agent's query loop starts | Lets hooks modify or add to the startup context |
| frontmatter `hooks` | Registered when the agent session is initialized | Effective only within this sub-agent's session, cleaned up afterward |
| preload `skills` | System prompt / skill resolution stage | Injects the specified skills' instructions and resources into the agent-visible context |
| agent `memory` | When the system prompt is built | Reads agent memory by `user` / `project` / `local` scope and appends it to the agent prompt |
| sidechain transcript | While the query loop runs | Records the sub-agent's independent message chain for recovery, debugging, and `SendMessage` continuation |

These extension points explain why, with the same `runAgent()`, different agent definitions show different tool boundaries, startup behavior, and long-term context.

## Routing rules

`AgentTool.call()` first decides which kind of agent this call should run:

```text
subagent_type set
  -> use the named agent

subagent_type omitted && isForkSubagentEnabled() is true
  -> use the fork agent

subagent_type omitted && fork gate off
  -> fall back to general-purpose
```

Named agents come from built-in agents, the user config directory, plugin agents, and similar definitions. The fork agent is a special built-in agent defined in `forkSubagent.ts`; it is not an ordinary specialist role but a "worker that inherits the parent context".

## Permission model

Sub-agent permissions are best viewed in three layers: whether this agent may be launched, which tools it has, and how permission requests are handled when tools run.

### Launch permissions

`AgentTool` is itself a tool call, so it first goes through the normal tool permission system. Then `AgentTool.call()` applies agent-level filtering:

| Check | Notes |
|-------|-------|
| `filterDeniedAgents()` | Filters out agent types forbidden by permission rules |
| `requiredMcpServers` | If an agent declares required MCP servers, waits for them to connect and stops on failure or timeout |
| Teammate restrictions | An in-process teammate cannot spawn further teammates or background agents |
| Fork recursion guard | A fork worker cannot fork again |

A named agent denied by permission rules fails with an error rather than falling back to another agent. This stops the model from bypassing deny rules from the user or configuration.

### Tool pool permissions

A normal named sub-agent does not directly inherit the parent agent's tool-pool restrictions for the current turn. It reassembles its tool pool using its own permission mode:

```ts
const workerPermissionContext = {
  ...appState.toolPermissionContext,
  mode: selectedAgent.permissionMode ?? 'acceptEdits',
}

const workerTools = assembleToolPool(
  workerPermissionContext,
  appState.mcp.tools,
)
```

Several implications follow:

| Dimension | Behavior |
|-----------|----------|
| Default permission mode | If the agent definition has no `permissionMode`, `acceptEdits` is used |
| Global allow / deny rules | Still come from `appState.toolPermissionContext` |
| The agent's own `tools` field | Further filtered inside `runAgent()` via `resolveAgentTools()` |
| MCP tools | Come from the MCP tools already connected in the current AppState; an agent may also declare its own MCP servers |

The fork agent is the exception. To keep the parent and child request prompt-cache prefix identical, it uses the parent's exact tools:

```text
useExactTools: true
availableTools: toolUseContext.options.tools
```

So the fork permission strategy is not "reassemble the tool pool" but "inherit the parent tool definitions and bubble permission requests up to the parent terminal using the `bubble` permission mode".

### Permission modes at a glance

| Mode | Meaning in a sub-agent |
|------|------------------------|
| `acceptEdits` | The default. Generally allows reads and edits on safe paths; dangerous operations still go through the permission system |
| `default` / other normal modes | Ask or allow according to the main permission system's rules |
| `bypassPermissions` | An explicit dangerous mode; should appear only when the user has enabled skipping permissions |
| `bubble` | Fork-specific: permission requests bubble up to the parent session |

## Synchronous sub-agents

A synchronous sub-agent is the default path: no explicit `run_in_background: true`, no `background: true` in the agent definition, and not forced async by the coordinator / assistant mode / fork gate.

The synchronous wait happens inside the normal tool call chain. The outer `toolExecution.ts` runs:

```ts
const result = await tool.call(...)
```

If the tool is `AgentTool`, then `AgentTool.call()` runs the whole sub-agent internally:

```text
AgentTool.call()
  -> agentIterator = runAgent(...)[Symbol.asyncIterator]()
  -> while true:
       await agentIterator.next()
       collect assistant / user messages
       forward progress to UI / SDK
       break if result.done
  -> finalizeAgentTool(agentMessages, ...)
  -> return { data: { status: "completed", ...agentResult } }
```

After it returns, `mapToolResultToToolResultBlockParam()` turns the `completed` result into the current turn's `tool_result`. Then `query.ts` puts that tool result into the message list and enters the next model call.

In other words, a synchronous sub-agent does not return its result through the unified queue. The main model waits on this `Agent` tool call until the final `tool_result` arrives.

### Backgrounding a synchronous sub-agent

A synchronous sub-agent is registered as a foreground task, so it can be moved to the background midway. The loop waits on both the next sub-agent message and a backgrounding signal:

```ts
const raceResult = await Promise.race([
  nextMessagePromise.then(result => ({ type: 'message', result })),
  backgroundPromise,
])
```

If the backgrounding signal arrives first, the current foreground iterator is cleaned up and a new background `runAgent(..., isAsync: true)` takes over the remaining work. At that point `AgentTool.call()` no longer waits for the final result; it returns `async_launched`, and the completion result later arrives through the task notification queue.

## Asynchronous sub-agents

Triggers for an asynchronous sub-agent:

| Condition | Notes |
|-----------|-------|
| `run_in_background: true` | The model explicitly asks for background execution |
| Agent definition `background: true` | This agent always runs in the background |
| coordinator mode | Workers are uniformly async to ease orchestration |
| fork subagent gate on | The current implementation forces every `AgentTool` spawn to use the async notification model |
| assistant / kairos mode | Keeps synchronous subtasks from blocking the input queue |
| proactive active | Async may also be forced under the proactive loop |

The async path does not wait for the sub-agent to finish:

```text
AgentTool.call()
  -> registerAsyncAgent(...)
  -> void runAsyncAgentLifecycle(...)
  -> return { status: "async_launched", agentId, outputFile }
```

The background lifecycle completes in `runAsyncAgentLifecycle()`:

```text
runAsyncAgentLifecycle()
  -> for await message of runAgent(...)
  -> updateAsyncAgentProgress(...)
  -> finalizeAgentTool(...)
  -> completeAsyncAgent(...)
  -> enqueueAgentNotification(...)
```

An async agent uses its own `AbortController`. A plain ESC that cancels the main thread does not automatically kill a background agent; background agents must be ended explicitly through task stop, bulk kill, or task management commands.

## Completion notifications and the unified queue

When a background agent finishes, `enqueueAgentNotification()` generates an XML-shaped `<task-notification>`:

```xml
<task-notification>
  <task-id>...</task-id>
  <tool-use-id>...</tool-use-id>
  <output-file>...</output-file>
  <status>completed</status>
  <summary>Agent "..." completed</summary>
  <result>...</result>
  <usage>...</usage>
</task-notification>
```

This message enters the unified command queue through `enqueuePendingNotification({ mode: 'task-notification' })`.

### When the queue is consumed

| Scenario | How it is consumed |
|----------|--------------------|
| REPL / TUI | `useQueueProcessor()` subscribes to the queue; when the query is idle and no local JSX UI is blocking, it calls `processQueueIfReady()` |
| CLI / SDK headless | `drainCommandQueue()` in `print.ts` keeps consuming between turns; if background tasks are still running, it keeps waiting and drains new notifications |
| Inside a sub-agent | `query.ts` consumes `task-notification` messages carrying the current `agentId`; the main thread consumes only messages with `agentId === undefined` |

A `task-notification` ultimately enters the next model turn's context as a user-role message or attachment. The model can therefore see the background result and decide whether to synthesize it, act further, or reply to the user.

### What else goes through the same queue

The unified queue is not only for background agents. Common sources include:

| Source | mode | Purpose |
|--------|------|---------|
| The user keeps typing before the current turn ends | `prompt` / `bash` | Queued for the next turn |
| Background shell / monitor finished or stuck reminder | `task-notification` | Tells the model the command status |
| Remote agent / ultraplan / ultrareview completed | `task-notification` | Hands remote results to the local model |
| Scheduled task / cron | `prompt` | Triggers a main-model task on a schedule |
| Chrome / MCP channel push | `prompt` | An external system injects a message |
| Hook blocking error | `task-notification` | Wakes the model to handle a stop hook error |
| Orphaned permission response | `orphaned-permission` | Handles a tool permission reply that arrives later than its original request |

Queue priority is `now > next > later`. `enqueue()` defaults to `next` and `enqueuePendingNotification()` defaults to `later`, so system notifications never jump ahead of user input.

## Continued communication and task control

After a background sub-agent returns `async_launched`, the main model should not pretend it already knows the final answer. It has three follow-up surfaces: send a message, read output, and stop the task.

### SendMessage

`SendMessage` appends a message to an agent that is running or has been started before. It can find a local background agent by two kinds of address:

| Address | Source | Behavior |
|---------|--------|----------|
| `name` | Registered in `agentNameRegistry` by `Agent({ name, ... })` | Resolved to an agentId first, then sent |
| raw `agentId` | Returned in the `async_launched` or `completed` tool result | Locates the task or transcript directly |

Sending a plain text message requires a `summary`, because the UI and permission summaries need a short description. `to: "*"` broadcasts to the teammate team; structured messages cannot be broadcast.

`SendMessage` behaves in three ways for a local background agent:

| Target state | Behavior | Result |
|--------------|----------|--------|
| Task still `running` | Calls `queuePendingMessage(agentId, message, ...)` | The message goes into the task's `pendingMessages` and is delivered at the sub-agent's next tool round / loop boundary |
| Task stopped but still in AppState | Calls `resumeAgentBackground(...)` | Resumes the agent in the background with this message; completion still comes back through a notification |
| Task already cleared from AppState | Still tries `resumeAgentBackground(...)` | If the sidechain transcript still exists, resumes from the transcript; otherwise returns a failure |

This means `SendMessage` is not limited to the time an agent is running. Long afterward, as long as the caller still knows the `name` or `agentId` and the transcript has not been cleaned up, the agent may be resumed and continued. Conversely, if both the task state and the transcript are gone, `SendMessage` cannot rebuild the context from nothing.

A few easily misunderstood points:

| Point | Notes |
|-------|-------|
| A running agent does not immediately interrupt its current tool call | The message is queued in `pendingMessages` and handled when the agent loop reaches a safe boundary |
| A stopped agent becomes a new background run | `resumeAgentBackground()` returns an output file, and completion notification re-injects the result later |
| `name` is reliable only while its registration lives | The name registry is runtime state; for a long-delayed resume the raw `agentId` is more stable |
| Cross-session send has extra limits | `bridge:` / `uds:` addresses support plain text only and may need explicit permission or a live connection |

### TaskOutput

`TaskOutput` is the legacy tool for reading background task output; the current prompt explicitly recommends using `Read` on the `output_file` returned by the task instead. It still works, with this behavior:

| Parameter | Behavior |
|-----------|----------|
| `task_id` | The id of the background task to read |
| `block: false` | Non-blocking read of the current status and existing output |
| `block: true` | Wait for the task to finish; the default |
| `timeout` | Maximum time to block |

If `block: true` waits until the task completes, `TaskOutput` marks the task as `notified` to avoid sending the completion notification again. Because this tool is deprecated, new code and model prompts both prefer reading `output_file` directly.

### TaskStop

`TaskStop` stops a running background task. It takes `task_id` and also accepts the legacy `shell_id`. The validation rule is simple: the task must exist and be `running`, otherwise it errors.

After stopping it calls the unified `stopTask()`, and each task type maps to its own kill logic: a local agent aborts its own `AbortController`, a shell task stops the process, and a remote task takes the remote stop path.

## Failure, cancellation, and cleanup

Sub-agent error paths split into sync and async.

### Synchronous path

When a synchronous sub-agent throws an `AbortError`, `AgentTool.call()` rethrows it to the outer tool framework, and the main turn goes through normal interrupt handling. A non-abort error is logged first; if assistant messages have already been collected, it tries to `finalizeAgentTool()` and return a partial result so the main model can see the progress made. If there are no assistant messages at all, the error is rethrown.

The synchronous `finally` performs this cleanup:

| Cleanup | Purpose |
|---------|---------|
| Clear background hint UI | Avoid leftover foreground hints |
| `stopForegroundSummarization()` | Stop the foreground summarization timer |
| `unregisterAgentForeground()` | If the sub-agent was not backgrounded, remove it from the foreground task registry |
| SDK task notification | Sends completed, failed, or stopped events to the SDK / VS Code panel |
| `clearInvokedSkillsForAgent()` | Clear agent-scoped skill state |
| `clearDumpState()` | Clear dump/transcript debug state |
| `cleanupWorktreeIfNeeded()` | Clean up or keep the worktree when not backgrounded |

### Asynchronous path

The async path catches exceptions in `runAsyncAgentLifecycle()`:

| Case | State update | Notification |
|------|--------------|--------------|
| Normal completion | `completeAsyncAgent(...)` | `enqueueAgentNotification(status: completed)` |
| `AbortError` | `killAsyncAgent(...)` | `enqueueAgentNotification(status: killed)`, with partial result |
| Other error | `failAsyncAgent(...)` | `enqueueAgentNotification(status: failed)`, with the error |

The code updates the task state first, and only then does potentially slow extras such as the handoff classifier or worktree cleanup. This order matters: `TaskOutput(block=true)` waits for the task to reach a terminal status and must not be stalled by the classifier or git cleanup that follows.

Notifications also have de-duplication. `enqueueAgentNotification()` atomically checks and sets `task.notified` first; if it was already notified, it does not enqueue again.

## AgentTool fork

AgentTool fork is a special route of the `Agent` tool, not a normal named agent.

### Gate

Fork is off by default. The `FORK_SUBAGENT` feature must be enabled at build/run time, for example by setting it explicitly during development:

```powershell
$env:FEATURE_FORK_SUBAGENT='1'; bun run dev
```

Even with the feature on, these scenarios force it off:

| Scenario | Reason |
|----------|--------|
| coordinator mode | The coordinator already has its own delegation model |
| non-interactive session | Avoids invisible fork nesting in pipe / SDK scenarios |

### Path

```text
main model
  -> Agent({ prompt }), no subagent_type
  -> AgentTool.call()
  -> isForkSubagentEnabled()
  -> selectedAgent = FORK_AGENT
  -> buildForkedMessages(...)
  -> runAgent(... useExactTools: true, forkContextMessages: parent messages)
  -> register task / transcript / notification
```

The goal of fork is to let multiple workers share the parent request's prompt-cache prefix. It does the following:

| Dimension | Fork behavior |
|-----------|---------------|
| system prompt | Uses the parent's already-rendered system prompt |
| Conversation history | Passes in the parent's full `toolUseContext.messages` |
| tools | Uses the parent's exact tools, with no re-filtering |
| thinking config | Inherits the parent's config so the cache key does not change |
| placeholder tool_result | Multiple forks use identical placeholder text; only the final directive differs |
| Permissions | `permissionMode: 'bubble'` |

This is why the fork path differs from the normal agent path in tool pool, prompt construction, and model inheritance.

### Recursion guard

A fork worker keeps the `Agent` tool so its tool definition bytes match the parent's, but the code rejects forking again inside a fork:

| Guard | Notes |
|-------|-------|
| `querySource === 'agent:builtin:fork'` | Directly detects that we are already inside a fork worker |
| `<fork-boilerplate>` scan | A fallback that detects a fork directive already present in the context |

A fork worker should complete its task directly rather than delegate further.

## Slash command fork

Slash command fork is an execution mode for skills / commands. It is controlled by skill frontmatter:

```md
---
name: code-review
context: fork
allowed-tools:
  - Read
  - Grep
  - Glob
---
```

When a skill is loaded, `frontmatter.context === 'fork'` is parsed into the command's `context: 'fork'`. When the slash command runs:

```text
user types /code-review
  -> processSlashCommand(...)
  -> command.context === 'fork'
  -> executeForkedSlashCommand(...)
  -> prepareForkedCommandContext(...)
  -> runAgent(...)
```

In normal interactive mode, `executeForkedSlashCommand()` runs the sub-agent to completion synchronously, shows a progress UI, and then returns the result to the main conversation as local command output.

In assistant / kairos mode it is fire-and-forget: when the background runner finishes, it wraps the result as a hidden prompt and puts it back into the command queue. This keeps multiple scheduled tasks from blocking user input serially at startup.

## `runForkedAgent()`

`runForkedAgent()` is the executor for internal services. It is not exposed to the model and produces no `Agent` tool_result.

Its inputs are runtime objects such as `cacheSafeParams`, `promptMessages`, and `canUseTool`, and it runs the query loop directly:

```text
internal service
  -> runForkedAgent({ promptMessages, cacheSafeParams, ... })
  -> createSubagentContext(...)
  -> query(...)
  -> return ForkedAgentResult
```

Common callers:

| Caller | Purpose |
|--------|---------|
| compact | Conversation compaction |
| extractMemories / sessionMemory | Memory extraction and maintenance |
| promptSuggestion / speculation | Prompt suggestions and prediction |
| sideQuestion | Ad-hoc Q&A that does not disturb the main context |
| agentSummary | Background agent summaries |
| autoDream | Background memory consolidation |

What it shares with AgentTool fork is "forked execution", but the boundaries are entirely different:

| Dimension | AgentTool fork | `runForkedAgent()` |
|-----------|----------------|--------------------|
| Caller | The model, through the `Agent` tool | Runtime services, directly |
| Protocol layer | Goes through Tool schema / tool_use / tool_result | Does not use the Tool protocol |
| Visibility | The main model first sees `async_launched`, then a notification on completion | The internal caller handles the result |
| Main goal | Parallel workers + prompt cache sharing | Internal helper tasks reusing the query loop |

## Worktree isolation

The `Agent` tool supports `isolation: "worktree"`. When enabled, the sub-agent runs in a temporary git worktree, which suits implementation or experimental tasks.

Lifecycle:

| Phase | Behavior |
|-------|----------|
| Creation | Derives a slug from the agent id and creates an independent worktree |
| CWD override | `runWithCwdOverride(worktreePath, fn)` makes tools execute inside the worktree |
| fork + worktree | Injects an extra path-translation hint to remind the worker to re-read files |
| Cleanup | If there are no changes the worktree is removed; if there are changes it is kept and its path is returned to the main model |

If the worktree is hook-based, the code keeps it, because VCS changes cannot be reliably determined.

## Result format

`AgentTool.mapToolResultToToolResultBlockParam()` returns a different tool result depending on status:

| Status | Result |
|--------|--------|
| `completed` | The sub-agent's output, optionally with `agentId`, worktree info, and usage |
| `async_launched` | The background agent id, the output file path, and a note to wait for the completion notification |
| `teammate_spawned` | teammate id, name, team name |
| `remote_launched` | remote task id, session URL, output file |

A synchronous sub-agent's `completed` result becomes the `tool_result` of the current `Agent` tool call directly. An async sub-agent's first tool result is `async_launched`, and the final output returns to the model through `<task-notification>`.

### Output fields

| Status | Key fields | Notes |
|--------|------------|-------|
| `completed` | `content`, `agentId`, `totalTokens`, `totalToolUseCount`, `totalDurationMs` | The sync sub-agent's final result; a normal agent includes an `agentId` for continued communication |
| `async_launched` | `agentId`, `description`, `prompt`, `outputFile`, `canReadOutputFile` | The background agent has started; the final result arrives later through a notification |
| `teammate_spawned` | `teammate_id`, `name`, `team_name` | The teammate has started; later collaboration goes through the mailbox / SendMessage |
| `remote_launched` | `taskId`, `sessionUrl`, `outputFile`, `description` | The remote CCR agent has started; completion goes through a remote task notification |

One-shot built-in agents can omit the `agentId` / `SendMessage` hint and the usage trailer, to avoid stuffing the context with information about communication that will never continue.

### outputSchema and tool_result

`AgentTool`'s `outputSchema` describes the structured data returned by `call()`; `mapToolResultToToolResultBlockParam()` then maps that data into the `tool_result` text block the model actually sees. When reading the code, follow this order:

```text
AgentTool.call()
  -> return { data: { status, ...fields } }
  -> mapToolResultToToolResultBlockParam(data, toolUseID)
  -> ToolResultBlockParam
  -> query.ts puts the tool_result into the next turn's messages
```

Focus fields of the four result kinds:

| status | data fields | What the model sees |
|--------|-------------|---------------------|
| `completed` | `content`, `agentId`, usage, optional worktree result | The sub-agent's final output; if it can continue communicating, a hint that `SendMessage` is available |
| `async_launched` | `agentId`, `description`, `prompt`, `outputFile`, `canReadOutputFile` | Started in the background; a hint to wait for a notification or read the output file |
| `teammate_spawned` | `teammate_id`, `name`, `team_name` | The teammate joined the team; later collaboration goes through the mailbox / `SendMessage` |
| `remote_launched` | `taskId`, `sessionUrl`, `outputFile`, `description` | The remote task has started; the local model waits for a remote task notification |

Here `status` is the main axis of result dispatch. The failed, killed, and cleanup logic in the later catch / finally does not rewrite a sync `tool_result` that has already been returned; the background paths hand the terminal state back to the main model through task state and notifications.

## Lifecycle state machine

Viewing a local sub-agent as a task, the core states can be understood like this:

```text
AgentTool.call()
  -> resolve route
  -> create optional worktree
  -> register foreground or register async task
  -> runAgent()
  -> completed / failed / killed
  -> tool_result or task-notification
  -> cleanup agent-scoped state
```

The difference between sync and async is not whether `runAgent()` is called, but who waits for `runAgent()`:

| Path | Who waits | When the main model continues |
|------|-----------|-------------------------------|
| Sync sub-agent | `AgentTool.call()` itself, via `for await` over the sub-agent message stream | After the sub-agent finishes and returns a `tool_result` |
| Auto-backgrounding | The foreground waits first; on timeout the foreground iterator exits and the background lifecycle takes over | After `AgentTool.call()` returns `async_launched` |
| Async sub-agent | `runAsyncAgentLifecycle()` waits in the background | Immediately after the main model receives `async_launched` |
| Slash command fork, normal interactive | `executeForkedSlashCommand()` waits | After the slash command completes |
| Slash command fork, assistant / kairos | A fire-and-forget background runner waits | The main input flow continues after launch; a hidden prompt is re-injected on completion |
| `runForkedAgent()` | The internal caller waits | Never enters the main model's tool_result protocol |

So the shortest answer to "how does a sync sub-agent wait for completion" is: the outer tool executor does `await tool.call()`, and inside `AgentTool.call()` keeps consuming the `runAgent()` async iterator until the iterator is `done` or throws.

## Comparing wait and re-injection mechanisms

A sub-agent result returns to the main model through three main mechanisms:

| Mechanism | Applicable path | Carrier | Blocks the current turn? |
|-----------|-----------------|---------|--------------------------|
| `tool_result` | Sync named sub-agent | The tool result for the current `Agent` tool_use | Yes |
| `<task-notification>` | Async / background local agents, remote tasks, background shells, etc. | A task notification in the unified command queue | No |
| hidden prompt / command queue prompt | Assistant / kairos slash command fork, scheduled tasks, etc. | A prompt-type message in the queue | No |

The easy confusion here: when a background sub-agent finishes, it does not "backfill" the original `tool_result`. The original `Agent` tool call already returned `async_launched`; the final result is a new queue message, and the model sees it in the next turn and decides how to integrate it.

## Progress, UI, and transcript

A sub-agent has three parallel "observable outputs": progress for the user, the final result for the model, and the transcript for system recovery.

| Output | Sync path | Async path | Purpose |
|--------|-----------|------------|---------|
| progress UI | `AgentTool.call()` forwards sub-agent messages to the UI / SDK in real time as it consumes them | `runAsyncAgentLifecycle()` updates the task progress state | Lets the user see what the sub-agent is doing |
| output file | The sync path also writes a side output for debugging and recovery | The main readable output of a background task; `async_launched` returns its path | The main model can view it with `Read(outputFile)` |
| sidechain transcript | `runAgent()` records an independent message chain | Recorded the same way, and used for background recovery | `SendMessage`, resume, debug, and summary all depend on it |
| task state | The foreground task registry records sync run state | LocalAgentTask records running / completed / failed / killed | The UI, `TaskOutput`, and notification de-dup all look here |

Sync progress is "display as it runs, return the tool_result all at once at the end". Async progress is "write task state as it runs, enqueue a task notification at the end". The sidechain transcript is not the same as user-visible output; it is the message log the system uses to rebuild the agent's context.

## Typical call examples

### Synchronous named sub-agent

```json
{
  "description": "review parser bug",
  "prompt": "Review the parser changes and identify correctness risks.",
  "subagent_type": "code-reviewer"
}
```

Suited to short tasks, or tasks whose result is needed before continuing. The main model waits until the sub-agent outputs `completed`.

### Background named sub-agent

```json
{
  "description": "run regression suite",
  "prompt": "Run the regression tests and summarize failures.",
  "subagent_type": "general-purpose",
  "run_in_background": true
}
```

Suited to long tasks. The main model first receives `async_launched`, which includes the `agentId` and `outputFile`. It can then wait for a `<task-notification>`, or proactively check existing results with `Read(outputFile)`.

### Background agent that can keep communicating

```json
{
  "description": "investigate flaky tests",
  "prompt": "Investigate flaky tests without editing files yet.",
  "subagent_type": "general-purpose",
  "name": "flaky-investigator",
  "run_in_background": true
}
```

You can follow up with:

```json
{
  "to": "flaky-investigator",
  "message": "Focus on the Windows-only failures and compare the last two runs.",
  "summary": "focus Windows failures"
}
```

If a long time passes, prefer the raw `agentId` returned in `async_launched` or `completed`, because the `name` registry is runtime state while the sidechain transcript is more likely to be recoverable through the `agentId`.

### Worktree isolation in practice

```json
{
  "description": "prototype parser fix",
  "prompt": "Implement a candidate fix in isolation and report the changed files.",
  "subagent_type": "general-purpose",
  "isolation": "worktree"
}
```

Suited to letting a sub-agent change code without polluting the main workspace. After getting the result, the main model must use the worktree path to decide whether to merge, review, or discard.

### AgentTool fork

```json
{
  "description": "scan auth paths",
  "prompt": "Analyze the auth flow and report likely race conditions."
}
```

It is a fork only when the fork gate is on and `subagent_type` is omitted. A fork worker inherits the parent context and exact tools; the goal is parallel analysis and prompt-cache reuse, and it is not suited to being written up as a long-lived, stable specialist role.

### Slash command fork

```md
---
name: audit-auth
context: fork
allowed-tools:
  - Read
  - Grep
  - Glob
---

Audit the authentication flow and return only correctness risks.
```

Result flow:

```text
user types /audit-auth
  -> processSlashCommand()
  -> executeForkedSlashCommand()
  -> runAgent()
  -> normal interactive: command output returns directly to the conversation
  -> assistant / kairos: a hidden prompt is enqueued on completion, consumed by the model next turn
```

## Troubleshooting checklist

| Symptom | Check first |
|---------|-------------|
| The model cannot see a background result | Whether the task has enqueued its notification; whether the queue is drained in the current mode; whether `task.notified` was already set early by `TaskOutput(block=true)` |
| `SendMessage` cannot find the target | Whether the `name` is still in the registry; whether you can switch to the raw `agentId`; whether the sidechain transcript still exists |
| The sub-agent lacks a tool | Whether the agent definition's `tools` filtered it out; whether the MCP server is connected; whether the fork path used exact tools |
| Sub-agent permissions differ from expectations | For a normal agent, look at `permissionMode`; a teammate's `mode` is not an ordinary sub-agent permission override; for fork, look at `bubble` |
| Fork did not trigger | Whether the `FORK_SUBAGENT` feature is on; whether you are in coordinator or non-interactive mode; whether `subagent_type` was passed |
| Slash command did not fork | Whether the skill frontmatter has `context: fork`; whether command.context is `fork` after loading |
| Worktree not cleaned up | Whether there are uncommitted changes; whether it is a hook-based worktree; whether cleanup was deferred until after the notification by a background task |
| `TaskOutput(block=true)` waits forever | Whether the task actually reached a terminal status; on the async path, confirm the state update happens before the classifier / cleanup |

## Choosing a path

| Need | Recommended path |
|------|------------------|
| A specialist role, limited context, an explicit tool set | Named sub-agent |
| A long task that must not block the main model | Async sub-agent |
| Multiple workers sharing the full parent context and maximizing the prompt cache | AgentTool fork |
| Run a slash command / skill in isolation | Slash command fork |
| The runtime needs a lightweight forked reasoning branch internally | `runForkedAgent()` |
| Isolate file changes | `isolation: "worktree"` |

## Common misconceptions

| Misconception | Correct understanding |
|---------------|-----------------------|
| `mode` can override a normal sub-agent's permissions | `mode` only affects plan mode for a teammate spawn; a normal sub-agent's permissions come from the agent definition's `permissionMode` |
| `SendMessage` only works on a running agent | When running it queues; when stopped / evicted it tries to resume from the transcript in the background |
| A finished background agent edits the current tool_result directly | Background completion goes through the `<task-notification>` queue, and the model only sees it next turn |
| Fork is on by default | Fork is off by default; it needs the `FORK_SUBAGENT` feature, and coordinator / non-interactive modes disable it |
| Fork is the internal `runForkedAgent()` | AgentTool fork goes through the Tool protocol; `runForkedAgent()` is an internal runtime API |
| `cwd` and `isolation: "worktree"` can be freely combined | The schema text requires them to be mutually exclusive; in the implementation `cwd` takes precedence as the run directory, so callers should avoid mixing them |
| Reading background output should prefer `TaskOutput` | The current prompt recommends `Read(output_file)` first; `TaskOutput` stays for compatibility and blocking waits |

## Source reading path

To verify a behavior against the source, start from a different entry depending on the question:

| Question | Reading order |
|----------|---------------|
