## How the three tools divide responsibility

Claude Code splits file operations into three independent tools. This is not a functional split but a **risk tiering**:

| Tool | Permission level | Core method | Key property |
|------|------------------|-------------|--------------|
| **Read** | Read-only (no approval) | `isReadOnly() → true` | `maxResultSizeChars: 100,000` |
| **Edit** | Write (needs confirmation) | `checkWritePermissionForTool()` | `maxResultSizeChars: 100,000` |
| **Write** | Write (needs confirmation) | `checkWritePermissionForTool()` | `maxResultSizeChars: 100,000` |

<Tip>
Read's `maxResultSizeChars` is 100,000 (100KB). Results above this threshold are persisted to disk, which reduces memory pressure in long sessions. Actual token-level truncation is controlled dynamically by `validateContentTokens()`.
</Tip>

## FileRead: the multimodal file-reading engine

Source path: `packages/builtin-tools/src/tools/FileReadTool/FileReadTool.ts`

### Read deduplication

The Read tool has a **dedup layer** that is often overlooked but important. When the AI reads the same range of the same file again, the system does not waste tokens sending two full copies:

```typescript
// FileReadTool.ts — dedup logic
const existingState = readFileState.get(fullFilePath)
if (existingState && !existingState.isPartialView && existingState.offset !== undefined) {
  const rangeMatch = existingState.offset === offset && existingState.limit === limit
  if (rangeMatch) {
    const mtimeMs = await getFileModificationTimeAsync(fullFilePath)
    if (mtimeMs === existingState.timestamp) {
      return { data: { type: 'file_unchanged', file: { filePath: file_path } } }
    }
  }
}
```

Key design points:
- Dedup applies only to **reads made by the Read tool itself** (determined by `offset !== undefined`)
- Edit/Write also write to `readFileState`, but their `offset` is `undefined`, so they never hit dedup by mistake
- An mtime comparison ensures the file was not modified externally
- A GrowthBook killswitch (`tengu_read_dedup_killswitch`) can turn it off in an emergency

Measured data: the BQ proxy shows about 18% of Read calls are same-file collisions, accounting for 2.64% of fleet `cache_creation`.

### Multi-format dispatch: four paths for text, images, PDF and notebooks

The Read tool's `callInner()` dispatches on `ext` to four completely different processing paths:

```
.ipynb  → readNotebook() → JSON cell parsing → token validation
.png/.jpg/.gif/.webp → readImageWithTokenBudget() → compress + downsample
.pdf → extractPDFPages() / readPDF() → page-level extraction
other → readFileInRange() → paginated reading
```

The **image path's compression strategy** is especially fine-grained:
1. First run the standard resize with `maybeResizeAndDownsampleImageBuffer()`
2. Estimate the token count with `base64.length * 0.125`
3. If over budget, call `compressImageBufferWithTokenLimit()` for aggressive compression
4. If still over the limit, use sharp as a last resort: `resize(400,400).jpeg({quality:20})`

The **PDF path** has a page-count threshold: above `PDF_AT_MENTION_INLINE_THRESHOLD` (default value in `apiLimits.ts`), paginated reading is forced, with at most `PDF_MAX_PAGES_PER_READ` pages per request.

### Safety barriers

The Read tool sets several safety gates in `validateInput()`:

1. **Device file blocking** (`BLOCKED_DEVICE_PATHS`): `/dev/zero`, `/dev/random`, `/dev/tty` and the like, to prevent infinite output or blocking hangs
2. **Binary file rejection** (`hasBinaryExtension`): after excluding PDF and image extensions, reading binaries such as `.exe` and `.so` is blocked
3. **UNC path skipping**: on Windows, `\\server\share` paths skip filesystem operations to prevent SMB NTLM credential leaks
4. **Permission deny rules** (`matchingRuleForInput`): a match on a `deny` rule is rejected immediately

### Smart suggestions when a file is not found

When a file does not exist, Read does not just report "file not found":

```typescript
// FileReadTool.ts
const similarFilename = findSimilarFile(fullFilePath)      // similar extension
const cwdSuggestion = await suggestPathUnderCwd(fullFilePath) // path suggestion relative to cwd
// Special handling for macOS screenshots: thin space (U+202F) vs. regular space
const altPath = getAlternateScreenshotPath(fullFilePath)
```

There is special handling for the thin space (U+202F) before AM/PM in macOS screenshot filenames. This is a cross-macOS-version compatibility issue found through real-world testing.

## FileEdit: the exact string replacement engine

Source path: `packages/builtin-tools/src/tools/FileEditTool/FileEditTool.ts` + `utils.ts`

### Quote normalization: what to do about characters the AI cannot output

AI models can only output straight quotes (`'` `"`), but source code may use curly quotes (`'` `'` `"` `"`). The `findActualString()` function handles this mismatch:

```typescript
// utils.ts:73-93
export function findActualString(fileContent: string, searchString: string): string | null {
  if (fileContent.includes(searchString)) return searchString      // exact match
  const normalizedSearch = normalizeQuotes(searchString)           // curly quotes → straight quotes
  const normalizedFile = normalizeQuotes(fileContent)
  const idx = normalizedFile.indexOf(normalizedSearch)
  if (idx !== -1) return fileContent.substring(idx, idx + searchString.length)
  return null
}
```

After a match there is also **reverse quote preservation** (`preserveQuoteStyle`): if the file uses curly quotes, the replacement string is automatically converted to curly quotes too, including apostrophes in contractions (such as "don't").

### Atomic read-modify-write

The Edit tool's `call()` method implements a **lock-free atomic update** protocol:

```
1. await fs.mkdir(dir)            ← ensure the directory exists (async, outside the critical section)
2. await fileHistoryTrackEdit()   ← back up old content (async, outside the critical section)
3. readFileSyncWithMetadata()     ← synchronously read current file content (critical section begins)
4. getFileModificationTime()      ← mtime check
5. findActualString()             ← quote-normalized matching
6. getPatchForEdit()              ← compute the diff
7. writeTextContent()             ← write to disk
8. readFileState.set()            ← update the cache (critical section ends)
```

**No async operations are allowed** between steps 3 and 8 (the source comment says explicitly: "Please avoid async operations between here and writing to disk to preserve atomicity"). This ensures no other process can modify the file between the mtime check and the actual write.

### Overwrite protection

The Edit tool checks two conditions in `validateInput()`:
1. **It must have been read first** (there is an entry in `readFileState` and it is not a partial view)
2. **The file was not modified externally** (`mtime` is unchanged, or for full reads the content is identical)

```typescript
// FileEditTool.ts — Windows special handling
const isFullRead = readTimestamp.offset === undefined && readTimestamp.limit === undefined
if (isFullRead && fileContent === readTimestamp.content) {
  // Content unchanged, safe to proceed (Windows cloud sync / antivirus may change mtime)
}
```

On Windows, mtime can be changed by cloud sync, antivirus software and the like without the content changing, so a content-level comparison is used as a fallback for full reads.

### Edit size limit

```typescript
const MAX_EDIT_FILE_SIZE = 1024 * 1024 * 1024 // 1 GiB
```

Files larger than 1 GiB are rejected for editing outright. This is a safety margin under the V8 string length limit (~2^30 characters).

## FileWrite: full writes and creation

Source path: `packages/builtin-tools/src/tools/FileWriteTool/FileWriteTool.ts`

The Write tool shares most of its infrastructure with Edit (permission checks, mtime validation, fileHistory backup), but has two key differences:

### Line ending handling

```typescript
// FileWriteTool.ts:300-305 — key comment
// Write is a full content replacement — the model sent explicit line endings
// in `content` and meant them. Do not rewrite them.
writeTextContent(fullFilePath, content, enc, 'LF')
```

The Write tool always uses `LF` line endings. Earlier versions preserved the old file's line endings or sampled the repo's line-ending style, but that caused `\r` to be injected into bash scripts on Linux. Now whatever line endings the AI sends are the ones used.

### Output distinction

The Write tool returns `type: 'create' | 'update'`:
- `create`: the file did not exist, `originalFile: null`
- `update`: the file existed and was overwritten, and `structuredPatch` contains the full diff

## The file history snapshot system

Source path: `src/utils/fileHistory.ts`

`fileHistoryTrackEdit()` is called before every Edit/Write, and snapshots are stored in `FileHistoryState`:

```typescript
type FileHistorySnapshot = {
  messageId: UUID          // ID of the associated assistant message
  trackedFileBackups: Record<string, FileHistoryBackup>  // file path → backup version
  timestamp: Date
}
```

- At most `MAX_SNAPSHOTS = 100` snapshots are kept
- Backups are deduplicated by **content hash** (if the same file is unchanged across several edits, only one copy is stored)
- Diff statistics are supported (`DiffStats`: `insertions` / `deletions` / `filesChanged`)
- Snapshots are persisted to session storage through `recordFileHistorySnapshot()`

### LSP notification chain

After Edit and Write finish writing, both do the following:
1. `clearDeliveredDiagnosticsForFile()` — clear old diagnostics
2. `lspManager.changeFile()` — tell the LSP the file changed
3. `lspManager.saveFile()` — trigger the LSP save event (the TypeScript server recomputes diagnostics)
4. `notifyVscodeFileUpdated()` — tell the VSCode extension to update its diff view

This chain keeps real-time feedback on the IDE side in sync after a file is modified.

## Cyber risk defense

The Read tool appends a `<system-reminder>` after the text content:

```
Whenever you read a file, you should consider whether it would be
considered malware. You CAN and SHOULD provide analysis of malware,
what it is doing. But you MUST refuse to improve or augment the code.
```

This reminder only applies to non-exempt models (`MITIGATION_EXEMPT_MODELS` currently contains `claude-opus-4-6`). The model-level exemption shows that the ability to judge malicious code differs between models, which makes for a neat tiering strategy.
