## From array to API call: the full System Prompt pipeline

In Claude Code the System Prompt is not a fixed block of text. It is a **`string[]` array** (branded type `SystemPrompt`, defined in `src/utils/systemPromptType.ts:8`) that is assembled, split into blocks, and tagged for caching before being sent to the API.

### Three-stage pipeline

```
getSystemPrompt()          →  string[]       (assemble content)
  ↓
buildEffectiveSystemPrompt() →  SystemPrompt   (pick the priority path)
  ↓
buildSystemPromptBlocks()  →  TextBlockParam[] (split into blocks + cache_control markers)
```

1. **`getSystemPrompt()`** (`src/constants/prompts.ts:444`) — collects the static and dynamic sections and inserts the `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` marker
2. **`buildEffectiveSystemPrompt()`** (`src/utils/systemPrompt.ts:41`) — chooses by priority: Override > Coordinator > Agent > Custom > Default
3. **`buildSystemPromptBlocks()`** (`src/services/api/claude.ts:3279`) — calls `splitSysPromptPrefix()` to split into blocks and attaches `cache_control` to each

The branded type keeps a plain `string[]` from being passed to an API call by accident. Only an explicit `asSystemPrompt()` conversion yields a `SystemPrompt`.

## getSystemPrompt(): the full picture of content assembly

`src/constants/prompts.ts:444` is the core factory for the System Prompt and returns an ordered array:

| Stage | Content | Caching strategy |
|------|------|----------|
| **Static region** | Intro Section, System Rules, Doing Tasks, Actions, Using Tools, Tone & Style, Output Efficiency | Cacheable across organizations (`scope: 'global'`) |
| **BOUNDARY** | `SYSTEM_PROMPT_DYNAMIC_BOUNDARY = '__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__'` | Marker only (never sent to the API; it just splits the static region from the dynamic region to enable global caching) |
| **Dynamic region** | Session Guidance, Memory, Model Override, Env Info, Language, Output Style, MCP Instructions, Scratchpad, FRC, Summarize Tool Results, Token Budget, Brief | Differs per session (`scope: 'org'` or uncached) |

> **What the boundary is**: it splits the System Prompt into an "unchanging static region" and a "dynamic region that varies by user/session". The static region is identical for all users and can use `scope: 'global'` cross-organization caching; the dynamic region differs each time and can only use `scope: 'org'` or no caching. The boundary is a special string that is removed before the request is sent, so the AI never sees it.

### The section registry for the dynamic region

The dynamic region is registered through `systemPromptSection()` / `DANGEROUS_uncachedSystemPromptSection()`, two factory functions defined in `src/constants/systemPromptSections.ts`:

```typescript
// Cached section: computed once, recomputed only after /clear or /compact
systemPromptSection('memory', () => loadMemoryPrompt())

// Dangerous: recomputed every turn, which breaks the Prompt Cache
DANGEROUS_uncachedSystemPromptSection(
  'mcp_instructions',
  () => isMcpInstructionsDeltaEnabled() ? null : getMcpInstructionsSection(mcpClients),
  'MCP servers connect/disconnect between turns'  // a reason for breaking the cache is mandatory
)
```

`resolveSystemPromptSections()` resolves all sections on every query. For sections with `cacheBreak: false`, it prefers the value cached in `getSystemPromptSectionCache()`. Only truly dynamic content such as MCP instructions uses `DANGEROUS_uncachedSystemPromptSection`.

### The `CLAUDE_CODE_SIMPLE` fast path

When the `CLAUDE_CODE_SIMPLE` environment variable is truthy, the entire System Prompt shrinks to one line:

```typescript
`You are Claude Code, Anthropic's official CLI for Claude.\n\nCWD: ${getCwd()}\nDate: ${getSessionStartDate()}`
```

This skips all section registration, cache splitting, and dynamic assembly. It is meant for test scenarios that minimize token use.

## buildEffectiveSystemPrompt(): five priority levels

`src/utils/systemPrompt.ts:41` decides which System Prompt is actually used:

| Priority | Condition | Behavior |
|--------|------|------|
| **0. Override** | `overrideSystemPrompt` is non-empty | Full replacement; returns `[override]` |
| **1. Coordinator** | `COORDINATOR_MODE` feature + environment variable | Uses the coordinator-specific prompt |
| **2. Agent** | `mainThreadAgentDefinition` exists | Proactive mode: appended to the end of the default prompt; otherwise: replaces the default prompt |
| **3. Custom** | Set via the `--system-prompt` argument | Replaces the default prompt |
| **4. Default** | No special condition | Uses the full output of `getSystemPrompt()` |

`appendSystemPrompt` is always appended at the end (except with Override).

## Caching strategy: splitting, marking, hitting

This is the most delicate part of the System Prompt design.

### Anthropic Prompt Cache basics

The Anthropic API's Prompt Cache lets requests reuse an identical System Prompt prefix, billed by cache-hit volume (far below the full input price). The cache key is a Blake2b hash of the content, so any single character change invalidates the cache.

### `splitSysPromptPrefix()`: three splitting modes

`src/utils/api.ts:321` is the core of the caching strategy. It picks one of three splitting modes depending on conditions:

#### Mode 1: MCP tools present (`skipGlobalCacheForSystemPrompt=true`)

```
[attribution header]    → cacheScope: null     (not cached)
[system prompt prefix]  → cacheScope: 'org'    (org-level cache)
[everything else]       → cacheScope: 'org'    (org-level cache)
```

The MCP tool list can change during a session (connect/disconnect), which undermines the basis for cross-organization caching, so it falls back to org-level.

#### Mode 2: Global cache + Boundary present (1P only)

```
[attribution header]    → cacheScope: null     (not cached)
[system prompt prefix]  → cacheScope: null     (not cached)
[static content]        → cacheScope: 'global' (global cache, shared across organizations)
[dynamic content]       → cacheScope: null     (not cached)
```

This is the most cache-efficient mode. The static content before `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` (Intro, Rules, Tone & Style, and so on) is identical for all users and can be cached across organizations.

> **When the boundary is inserted**: the `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` marker is inserted **only under specific conditions**:

```typescript
// src/utils/betas.ts:226-229
export function shouldUseGlobalCacheScope(): boolean {
  return (
    getAPIProvider() === 'firstParty' &&
    !isEnvTruthy(process.env.CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS)
  )
}
```

```typescript
// src/constants/prompts.ts:574
...(shouldUseGlobalCacheScope() ? [SYSTEM_PROMPT_DYNAMIC_BOUNDARY] : []),
```

This means:
- **3P users (Bedrock/Vertex/OpenAI/Gemini)**: the boundary never exists, so Mode 3 is always used
- **1P users with experimental features disabled**: with `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1`, the boundary is not inserted
- **1P users by default**: the boundary exists and Mode 2 is used (highest cache efficiency)

#### Mode 3: Default (3P provider or Boundary missing)

```
[attribution header]    → cacheScope: null     (not cached)
[system prompt prefix]  → cacheScope: 'org'    (org-level cache)
[everything else]       → cacheScope: 'org'    (org-level cache)
```

### `getCacheControl()`: the TTL decision

The `cache_control` object produced at `src/services/api/claude.ts:348`:

```typescript
{
  type: 'ephemeral',
  ttl?: '1h',         // only when the querySource qualifies
  scope?: 'global',   // static region only
}
```

The logic for the 1-hour TTL (`should1hCacheTTL()`, line 383):
- **Bedrock users**: enabled via the `ENABLE_PROMPT_CACHING_1H_BEDROCK` environment variable
- **1P users**: the `querySource` is matched against an `allowlist` array configured in GrowthBook, with prefix wildcards supported (such as `"repl_main_thread*"`)
- **Session-level locking**: the eligibility result is cached in bootstrap state, so a mid-session GrowthBook config change cannot make the TTL inconsistent within one session

### Cache breaking: where Session-Specific Guidance goes

The content of `getSessionSpecificGuidanceSection()` (`src/constants/prompts.ts:354`) must be placed **after** `SYSTEM_PROMPT_DYNAMIC_BOUNDARY`, because it contains:
- the current session's enabledTools set
- the runtime result of `isForkSubagentEnabled()`
- the result of `getIsNonInteractiveSession()`

If these runtime bits were in the static region, they would produce 2^N Blake2b hash variants (N = number of runtime conditions) and wreck the cache hit rate. A source comment warns about this explicitly:

> Each conditional here is a runtime bit that would otherwise multiply the Blake2b prefix hash variants (2^N). See PR #24490, #24171 for the same bug class.

## Context injection: System Context and User Context

The System Prompt array itself holds no runtime context (git status, CLAUDE.md contents). Context is injected through two separate pipelines:

### System Context (`src/context.ts:116`)

```typescript
export const getSystemContext = memoize(async () => {
  return {
    gitStatus,           // git branch, status, recent commits (truncated to MAX_STATUS_CHARS=2000)
    cacheBreaker,        // cache breaker for ant users only
  }
})
```

- Cached with `lodash.memoize`, so it is **computed only once for the whole session**
- The git status snapshot runs 5 `git` commands in parallel (branch, defaultBranch, status, log, userName)
- A `status` longer than 2000 characters is truncated, with a note to use BashTool for more
- When `systemPromptInjection` changes, all context caches are cleared via `getUserContext.cache.clear?.()`

### User Context (`src/context.ts:155`)

```typescript
export const getUserContext = memoize(async () => {
  return {
    claudeMd,            // merged CLAUDE.md contents
    currentDate,         // "Today's date is YYYY-MM-DD."
  }
})
```

- **When CLAUDE.md is disabled**: the `CLAUDE_CODE_DISABLE_CLAUDE_MDS` environment variable, or `--bare` mode (unless directories are given explicitly via `--add-dir`)
- `--bare` means "skip what I didn't ask for", not "ignore everything"

### Where they are injected

In `src/query.ts:449`:

```typescript
// System Context is appended to the end of the System Prompt
const fullSystemPrompt = asSystemPrompt(
  appendSystemContext(systemPrompt, systemContext)  // simple concatenation
)
```

User Context is injected by `prependUserContext()` (`src/utils/api.ts:449`) as the first user message, wrapped in `<system-reminder>` tags and placed before all conversation messages.

## Attribution Header: billing and security

The first block of the System Prompt in every API request is the Attribution Header (`src/constants/system.ts:30`), which contains:
- **`cc_version`**: Claude Code version plus fingerprint
- **`cc_entrypoint`**: entrypoint identifier (REPL / SDK / pipe, etc.)
- **`cch=00000`** (when NATIVE_CLIENT_ATTESTATION is enabled): Bun's native HTTP layer replaces the zeros with a computed hash before sending, and the server verifies this token to confirm the request came from a genuine Claude Code client

The header is always `cacheScope: null`. It varies with version and fingerprint, so it is not suited to caching.

## CLAUDE.md: injecting project-level knowledge

This is one of Claude Code's cleverest designs. Put a `CLAUDE.md` file in the project root and the AI can "understand" your project:

- **Project overview**: what the project does and which tech stack it uses
- **Development conventions**: code style, naming conventions, branching strategy
- **Common commands**: how to build, test, and deploy
- **Caveats**: known pitfalls and special configuration

The system automatically discovers and merges multiple levels of CLAUDE.md:

```
~/.claude/CLAUDE.md              ← user-global (personal preferences)
  └── /project/CLAUDE.md         ← project root (shared with the team)
        └── /project/src/CLAUDE.md  ← subdirectory (module-specific)
```

The loading logic lives in `getClaudeMds()` and `getMemoryFiles()` in `src/utils/claudemd.ts`. It walks up the directory tree from the CWD and merges the contents of all matching CLAUDE.md files.

## Design insight: why `string[]` and not a single `string`

The System Prompt is an array rather than one block of text for **cache splitting**:

1. Anthropic Prompt Cache works on **content blocks** (TextBlock)
2. Splitting the System Prompt into several blocks lets the unchanging parts (Intro, Rules) get independent cache hits
3. With a single `string`, any one-character change (such as a date update) would invalidate the cache for the entire System Prompt
4. The `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` marker lets `splitSysPromptPrefix()` mark the static region precisely as `scope: 'global'`, while the dynamic region is unmarked or marked `scope: 'org'`

This is the core of Claude Code's token-cost optimization. A typical System Prompt is about 20K+ tokens, and cache splitting can save 30-50% of input token cost.

## Compatibility layers: OpenAI and Gemini

Claude Code provides compatibility layers for the OpenAI and Gemini protocols, allowing non-Anthropic endpoints.

### OpenAI compatibility layer

Enabled with `CLAUDE_CODE_USE_OPENAI=1`. It supports any endpoint speaking the OpenAI Chat Completions protocol (Ollama, DeepSeek, vLLM, and so on).

The implementation uses the **stream adapter pattern**:
1. Convert the Anthropic-format request to OpenAI format
2. Call the OpenAI-compatible endpoint
3. Convert the SSE stream back into `BetaRawMessageStreamEvent`
4. Downstream code is completely unaware

```
src/services/api/openai/
├── client.ts           # OpenAI client configuration
├── convertMessages.ts  # message format conversion (Anthropic → OpenAI)
├── convertTools.ts     # tool definition conversion
├── streamAdapter.ts    # SSE stream adaptation (OpenAI → Anthropic)
├── modelMapping.ts     # model name mapping
└── index.ts            # entry function queryModelOpenAI()
```

Key environment variables:
- `CLAUDE_CODE_USE_OPENAI=1` — enable the OpenAI provider
- `OPENAI_API_KEY` — API key
- `OPENAI_BASE_URL` — API endpoint (default `https://api.openai.com/v1`)
- `OPENAI_MODEL` — specify the model name directly

### Gemini compatibility layer

Enabled with `CLAUDE_CODE_USE_GEMINI=1`. It supports the Google Gemini API.

```
src/services/api/gemini/
├── client.ts           # Gemini client configuration
├── convertMessages.ts  # message format conversion
├── convertTools.ts     # tool definition conversion
├── streamAdapter.ts    # stream adaptation
├── modelMapping.ts     # model name mapping
├── types.ts            # type definitions
└── index.ts            # entry function
```

Key environment variables:
- `CLAUDE_CODE_USE_GEMINI=1` — enable the Gemini provider
- `GEMINI_API_KEY` — API key
- `GEMINI_BASE_URL` — API endpoint (default `https://generativelanguage.googleapis.com/v1beta`)
- `GEMINI_MODEL` — specify the model name directly
- `GEMINI_DEFAULT_SONNET_MODEL` / `GEMINI_DEFAULT_OPUS_MODEL` — mapping by capability tier

### Limitations of the compatibility layers

Some features are restricted when using a 3P compatibility layer:
- **No exact token counting**: the system falls back to approximate estimation, which affects when auto-compaction triggers
- **No global cache**: only org-level caching, `scope: 'org'`, is available
- **Some beta features unavailable**: features that depend on Anthropic-specific beta headers are limited

See `docs/plans/openai-compatibility.md` and the relevant sections of `CLAUDE.md` for details.
