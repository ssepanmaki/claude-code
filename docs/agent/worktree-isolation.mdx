## Why file-level isolation is needed

When multiple agents work in parallel, sharing one working directory causes three kinds of conflict:

1. **Write conflicts**: two agents edit `config.ts` at the same time, and the later write overwrites the earlier one
2. **State interference**: agent A's tests depend on some environment state, and agent B's changes break it
3. **Indistinguishable changes**: half-finished edits get mixed together, and you cannot tell which agent made which

Git worktree is git's native solution: it creates multiple independent working directories in the same repository, each on its own branch.

## Directory layout and naming rules

Worktree files are stored under `.claude/worktrees/` in the repository root:

```
<repo-root>/
├── .claude/
│   └── worktrees/
│       ├── fix-auth-bug/          # worktree working directory
│       │   ├── .git               # link file pointing to the main repository
│       │   └── src/...            # independent view of the file system
│       └── add-dark-mode/         # another worktree
│           └── ...
├── src/                           # main working directory (unaffected)
└── .git/                          # main repository
```

Branches are named `worktree/<slug>`, and the slug is validated by `validateWorktreeSlug()`: each `/`-separated segment may contain only letters, digits, `.`, `_` and `-`, and the total length must be ≤64 characters. When no slug is given, one is generated from the plan slug.

## Creation flow: EnterWorktreeTool

The execution path of `EnterWorktreeTool` (`packages/builtin-tools/src/tools/EnterWorktreeTool/EnterWorktreeTool.ts`):

```
EnterWorktreeTool.call({ name? })
  ↓
1. Check whether already inside a worktree (prevents nesting)
  ↓
2. Resolve to the main repository root (findCanonicalGitRoot)
   If currently inside a worktree, chdir to the main repository
  ↓
3. Generate the slug (user-provided or plan slug)
  ↓
4. createWorktreeForSession(sessionId, slug)
   ├── Is there a WorktreeCreate hook?
   │   └── Run the hook and return the path it specifies (supports non-git VCS)
   └── No hook → native git path:
       a. getOrCreateWorktree(repoRoot, slug)
          ├── Fast resume: check whether the worktree directory already exists
          │   └── Read the HEAD SHA from the .git pointer file (no subprocess)
          └── Create new:
              i.   mkdir .claude/worktrees/ (recursive)
              ii.  fetch origin/<default-branch> (skipped if cached)
              iii. git worktree add -b worktree/<slug> <path> <base>
              iv.  performPostCreationSetup() (sparse checkout, etc.)
  ↓
5. Update process state:
   - process.chdir(worktreePath)
   - setCwd(worktreePath)
   - setOriginalCwd(worktreePath)
   - saveWorktreeState(session) → persisted to the project config
   - clearSystemPromptSections() → recompute the cwd info in the system prompt
   - clearMemoryFileCaches() → reload CLAUDE.md from the worktree
  ↓
6. Return worktreePath and worktreeBranch
```

### Hook-first architecture

`createWorktreeForSession()` first checks `hasWorktreeCreateHook()`. If the user configured a `WorktreeCreate` hook in settings.json, the system does not call git at all. It runs the hook command and uses the returned path as the worktree path. This lets non-git version control systems (such as Pijul or Mercurial) plug in through a hook.

### Fast resume path

`getOrCreateWorktree()` has a key optimization: if the target path already exists, it reads the `.git` pointer file directly to get the HEAD SHA (pure file I/O, no subprocess) and skips the whole `fetch` + `worktree add` flow. In a large repository `fetch` takes 6-8 seconds, and this optimization brings the latency of the resume case close to zero.

## Exit flow: ExitWorktreeTool

`ExitWorktreeTool` (`packages/builtin-tools/src/tools/ExitWorktreeTool/ExitWorktreeTool.ts`) supports two exit strategies:

### keep: preserve the worktree

```
keepWorktree()
  ↓
1. chdir back to originalCwd
2. Clear currentWorktreeSession
3. Update the project config (activeWorktreeSession = undefined)
4. The worktree directory and branch stay on disk
```

The user can keep working with `cd <worktreePath>`, or merge manually later.

### remove: delete the worktree

This has strict **safety guards**:

```
validateInput() — first line of defense
  ↓
1. Check whether this is a session created by EnterWorktree
   (manually created worktrees are never deleted)
  ↓
2. countWorktreeChanges(worktreePath, originalHeadCommit)
   ├── git status --porcelain → count uncommitted files
   ├── git rev-list --count <originalHead>..HEAD → count new commits
   └── Returns null (when git fails) → fail-closed (refuse to delete)
  ↓
3. Any uncommitted files or new commits?
   → Refuse, and require discard_changes: true as confirmation
```

```
call() — actual execution
  ↓
1. Recount changes (new edits may have appeared between validateInput and call)
2. If there is a tmux session → killTmuxSession()
3. cleanupWorktree()
   ├── hook-based → run the WorktreeRemove hook
   └── git-based → git worktree remove --force + git branch -D
4. restoreSessionToOriginalCwd()
   - setCwd(originalCwd)
   - setOriginalCwd(originalCwd)
   - Only restores if projectRoot is the worktree (guards against accidents)
   - Update the hooks config snapshot
   - Clear the system prompt and memory caches
```

### Fail-closed design

`countWorktreeChanges()` returns `null` ("unknown, assume unsafe") in these cases:
- `git status` or `git rev-list` exits non-zero (lock file, corrupted index)
- `originalHeadCommit` is undefined (hook-based worktrees do not set a baseline commit)

When it returns `null`, `validateInput` refuses to delete. It is better to let the user handle it manually than to risk losing work.

## Integration with the Agent tool

The `isolation` parameter of the Agent tool (`AgentTool`) decides whether a sub-agent runs in a worktree. Note that the Agent tool uses a **dedicated** `createAgentWorktree()` (`src/utils/worktree.ts`), not the `createWorktreeForSession()` used for user sessions. The two differ in key ways:

| Dimension | `createWorktreeForSession` (user session) | `createAgentWorktree` (sub-agent) |
|-----------|-------------------------------------------|-----------------------------------|
| Caller | EnterWorktreeTool | AgentTool |
| Session management | Sets `currentWorktreeSession` | **Does not set** `currentWorktreeSession` |
| Resuming an existing worktree | Reuses it directly | Reuses it and bumps the mtime (prevents deletion by periodic cleanup) |

When a sub-agent finishes, `cleanupWorktreeIfNeeded()` handles cleanup automatically. It does not go through `ExitWorktreeTool`, because an agent worktree has no session state and `ExitWorktreeTool`'s `validateInput` would reject it:
- **Has changes** → keep the worktree and return `worktreePath` so the main agent can merge later
- **No changes** → delete automatically
- **Hook-based** → always keep

## Session state persistence

The `WorktreeSession` object is persisted to disk through `saveCurrentProjectConfig()` and contains:

```typescript
{
  originalCwd: string,         // working directory before entering the worktree
  worktreePath: string,        // absolute path of the worktree
  worktreeName: string,        // slug
  worktreeBranch?: string,     // branch name (e.g. worktree/fix-auth)
  originalBranch?: string,     // branch before entering
  originalHeadCommit?: string, // HEAD commit before entering (used for change counting)
  sessionId: string,           // ID of the session that created this worktree
  tmuxSessionName?: string,    // associated tmux session
  hookBased?: boolean,         // whether it was created by a hook
  creationDurationMs?: number, // creation time (for analytics)
  usedSparsePaths?: boolean,   // whether sparse checkout was used
}
```

This lets session resume (`--resume`) restore the worktree context correctly. Even after a process restart, `getCurrentWorktreeSession()` reads the state from the project config.

## Sparse checkout optimization

For large monorepos, worktrees support a `sparsePaths` setting that checks out only specific directories instead of the whole repository. In a repository with 210K files, this cuts worktree creation time from tens of seconds to a few seconds.

The setting lives at `getInitialSettings().worktree?.sparsePaths` and is applied in `performPostCreationSetup()`.
