## Why runtime A/B testing

Build-time `feature()` is all-or-nothing: either every user has a feature or none do. But a product team needs finer control:

- Roll out a new feature to only 5% of users
- Differentiate the experience by subscription type (Free / Pro / Team)
- Quietly enable experimental capabilities for specific organizations
- Switch off a misbehaving feature remotely at any time, without shipping a release

That is what **GrowthBook** is for: a runtime, user-attribute-based feature gating and A/B testing system.

## Integration architecture

The full GrowthBook implementation lives in `src/services/analytics/growthbook.ts` (1258 lines). It works like this:

<Steps>
  <Step title="Fetch remote config at startup">
    When the CLI starts, the GrowthBook SDK fetches the current feature config and experiment bucketing rules from an API endpoint on `https://api.anthropic.com/`. It uses `remoteEval: true` mode: bucketing is computed on the server and the client only gets the result.
  </Step>
  <Step title="Compute user attributes">
    The SDK collects the current user's attributes (device ID, subscription type, organization UUID, and so on), which decide which experiments the user belongs to and which group they land in.
  </Step>
  <Step title="Cache locally">
    The results are cached in the `cachedGrowthBookFeatures` field of `~/.claude.json`. Refresh interval: 20 minutes for Anthropic employees, 6 hours for external users.
  </Step>
  <Step title="Query flags in code">
    Business code queries feature state by `tengu_*`-prefixed flag name, and the GrowthBook SDK returns the current user's group value.
  </Step>
</Steps>

## User targeting attributes

GrowthBook uses these user attributes to decide experiment groups:

| Attribute | Type | Source | Purpose |
|------|------|------|------|
| `id` | string | Session ID | Per-session bucketing |
| `deviceID` | string | Persisted device identifier | Consistency across sessions |
| `sessionId` | string | Current session ID | Session-level experiments |
| `platform` | enum | `process.platform` | Per-OS differentiation |
| `organizationUUID` | string | API auth info | Per-organization rollout |
| `accountUUID` | string | API auth info | Per-account rollout |
| `subscriptionType` | string | API auth info | Free / Pro / Team differentiation |
| `rateLimitTier` | string | API auth info | Per rate-limit tier |
| `email` | string | API auth info | Precise targeting of specific users |
| `appVersion` | string | `MACRO.VERSION` | Per-version rollout |
| `github` | object | GitHub Actions metadata | Special handling for CI environments |

<Note>
This targeting system lets Anthropic run very fine-grained experiments, for example "enable the new feature for 10% of Pro subscribers on Mac".
</Note>

## Codename culture: the world of tengu_*

All runtime flags are prefixed with `tengu_`. "Tengu" is Claude Code's internal project codename. Flag names follow an **animal/plant/mineral + adjective** convention and are deliberately opaque.

<AccordionGroup>
  <Accordion title="tengu_kairos — Kairos assistant mode">
    The runtime switch for the KAIROS feature. Even when the build-time `feature('KAIROS')` passes, this flag must also hit to activate it. The double gating lets new features roll out in stages.
  </Accordion>
  <Accordion title="tengu_amber_stoat — Explore Agent A/B test">
    Controls behavior variants of the built-in Explore subagent. "amber stoat" is a randomly generated codename unrelated to the feature, so the feature cannot be guessed from the flag name.
  </Accordion>
  <Accordion title="tengu_auto_background_agents — background agent automation">
    Controls whether certain tasks are automatically handed to background agents instead of blocking the user in the foreground.
  </Accordion>
  <Accordion title="tengu_onyx_plover — Auto-Dream background memory">
    Controls the "auto-dream" feature: tidying up and consolidating the agent's memory in the background while idle. "onyx plover" is another opaque codename.
  </Accordion>
  <Accordion title="tengu_glacier_2xr — tool search behavior">
    Controls behavior variants of Tool Search, possibly an A/B test of the search algorithm or ranking strategy.
  </Accordion>
  <Accordion title="tengu_birch_trellis — Bash permission policy">
    Controls policy variants for BashTool permission decisions, possibly testing looser or stricter permission rules.
  </Accordion>
  <Accordion title="tengu_scratch — scratchpad feature">
    Controls an experimental "scratchpad" feature, possibly an intermediate staging area the AI uses on complex tasks.
  </Accordion>
  <Accordion title="tengu_quartz_lantern — diff computation strategy">
    Controls how diffs are computed when files are written and edited. It may be an A/B test of how different diff algorithms affect the user experience.
  </Accordion>
</AccordionGroup>

## The Ant-only override mechanism

Anthropic employees have two ways to bypass GrowthBook's remote evaluation:

### Environment variable override

```bash
# Only takes effect in builds with USER_TYPE=ant
CLAUDE_INTERNAL_FC_OVERRIDES='{"tengu_kairos": true}' claude
```

A JSON object passed through the `CLAUDE_INTERNAL_FC_OVERRIDES` environment variable directly overrides the value of any flag.

### Config UI override

In internal builds, the Gates tab of the `/config` command offers a graphical flag management UI where any GrowthBook flag can be toggled live.

## Experiment tracking

GrowthBook is integrated with full experiment exposure tracking:

- An experiment exposure event is recorded each time a flag is queried
- Events are reported as protobuf `GrowthbookExperimentEvent` messages
- They carry `variation_id` (0 = control, 1+ = treatment) and an `in_experiment` marker
- The data is used to analyze the causal effect of features on user behavior

<Note>
GrowthBook is being migrated from Statsig; the code still keeps a compatibility layer such as `checkStatsigFeatureGate_CACHED_MAY_BE_STALE()`.
</Note>
