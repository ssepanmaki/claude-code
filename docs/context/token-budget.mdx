## The context window: 200K is not all yours

Claude Code's default context window is 200K tokens (`MODEL_CONTEXT_WINDOW_DEFAULT = 200_000`), but the space actually usable for conversation is much smaller:

```
Context window (200K)
├── System prompt (~15-25K, cheap once cached)
├── Tool definitions (~10-20K, including MCP tools)
├── User context (CLAUDE.md, git status, etc.)
├── Output reservation (maxOutputTokens)
│   ├── Default cap: 64K
│   ├── Effective default: 8K (slot-reservation optimization)
│   └── Auto-escalation on hitting the cap: one 64K retry
└── Remainder: room for conversation history (grows with the conversation)
```

`getContextWindowForModel()` (`src/utils/context.ts:51`) resolves the window size with five levels of priority:

1. `CLAUDE_CODE_MAX_CONTEXT_TOKENS` environment variable override
2. Model name with a `[1m]` suffix → 1M tokens
3. `getModelCapability(model).max_input_tokens`
4. 1M beta header + a supported model (claude-sonnet-4, opus-4-6)
5. Fallback: 200K

**Effective context** = window size - min(maxOutputTokens, 20K), because the compaction summary needs reserved output space.

## Token counting: approximate vs. exact

The system uses a two-level token counting strategy:

### Approximate estimation (milliseconds)

```typescript
// src/services/tokenEstimation.ts
function roughTokenCountEstimation(content: string, bytesPerToken = 4): number {
  return Math.round(content.length / bytesPerToken)
}
```

Different content types get special handling:
- **JSON/JSONL**: `bytesPerToken = 2` (dense `{`, `:`, `,` symbols are only 1-2 tokens each)
- **Images/documents**: a fixed 2000 tokens (a conservative estimate based on a 2000×2000px cap)
- **thinking block**: actual text length / 4
- **tool_use**: serialized `name + JSON.stringify(input)` / 4

### Exact counting (API call)

This uses Anthropic's `beta.messages.countTokens` endpoint. The path differs by provider:

| Provider | Method |
|----------|--------|
| Anthropic direct | `anthropic.beta.messages.countTokens()` |
| AWS Bedrock | `CountTokensCommand` from `@aws-sdk/client-bedrock-runtime` |
| Google Vertex | Anthropic SDK + beta filtering |
| Fallback (Bedrock unsupported) | Send a request with `max_tokens=1` to Haiku and read `usage.input_tokens` |

Exact counting is used at key decision points (before/after compaction comparison, warning decisions), and approximate estimation is used on the hot path (the `shouldAutoCompact` check on every loop iteration).

### Token counting differences on 3P providers

Providers implement exact token counting differently, and some do not support it at all:

| Provider | Counting method | Notes |
|----------|-----------------|-------|
| **Anthropic direct** | `anthropic.beta.messages.countTokens()` | Standard API, most accurate |
| **AWS Bedrock** | `CountTokensCommand` | Requires dynamically loading the 279KB AWS SDK |
| **Google Vertex** | Anthropic SDK + beta filtering | Requires specific beta headers |
| **OpenAI compatibility layer** | No exact counting | **Falls back to approximate estimation** |
| **Gemini compatibility layer** | No exact counting | **Falls back to approximate estimation** |
| **When Bedrock is unsupported** | Send a `max_tokens=1` request to Haiku | Read `usage.input_tokens` |

The OpenAI and Gemini compatibility layers **do not support exact token counting**, so the system falls back to approximate estimation. This affects:
- **Auto-compaction trigger timing**: may be slightly off
- **Before/after compaction token comparison**: estimates only, not exact
- **Warning/error threshold decisions**: based on estimates rather than exact counts

## Auto-compaction trigger thresholds

```
src/services/compact/autoCompact.ts — core thresholds
```

| Constant | Value | Meaning |
|----------|-------|---------|
| `AUTOCOMPACT_BUFFER_TOKENS` | 13,000 | Window minus this value = auto-compaction trigger point |
| `WARNING_THRESHOLD_BUFFER_TOKENS` | 20,000 | Show a warning at the trigger point + 20K |
| `ERROR_THRESHOLD_BUFFER_TOKENS` | 20,000 | Show an error at the trigger point + 20K |
| `MANUAL_COMPACT_BUFFER_TOKENS` | 3,000 | Blocking limit for manual /compact |
| `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES` | 3 | Stop trying after 3 consecutive failures |

For a 200K window:
- **~167K**: the warning flashes, and the user sees a prompt suggesting compaction
- **~180K**: auto-compaction triggers (200K - 20K output reservation = 180K effective, minus the 13K buffer)
- **~197K**: the blocking limit is reached and new messages are blocked

`shouldAutoCompact()` has several escape conditions:
- Queries from the `compact` / `session_memory` sources never trigger it (prevents recursive deadlock)
- `DISABLE_COMPACT` / `DISABLE_AUTO_COMPACT` environment variables
- The user setting `autoCompactEnabled = false`
- Suppressed while Context Collapse mode is active (collapse manages context itself)
- Proactive compaction is suppressed in the Reactive Compact experimental mode
- Exceeding the consecutive failure limit (circuit breaker)

## Micro-compact: progressive compression of tool results

Before triggering a full compaction, the system first tries **micro-compact**, which compresses only old tool call results:

```
Compactable tool list (COMPACTABLE_TOOLS):
FileRead, Bash, Grep, Glob, WebSearch, WebFetch, FileEdit, FileWrite
```

The strategy is time-based:
- Tool results older than a threshold (controlled by `timeBasedMCConfig`) are replaced with a short placeholder
- Image/document results are replaced with `[image]` / `[document]` text
- Each replacement frees tokens and may postpone full compaction

Tools also have a hard `maxResultSizeChars` limit (typically 100K), and oversized results are truncated before being written into messages.

## The full compaction flow

```
autoCompactIfNeeded() / compactConversation()
  ↓
1. Run PreCompact hooks (external code can inject custom instructions)
  ↓
2. Try Session Memory compaction (lighter, tried first)
  ↓
3. Session Memory failed → full compaction
   a. Strip images/documents from messages (replaced with [image]/[document])
   b. Strip skill_discovery/skill_listing attachments (re-injected after compaction)
   c. Send the summary request through a forked agent (reuses the main thread's prompt cache)
   d. If the summary request itself triggers prompt-too-long → truncateHeadForPTLRetry()
      deletes from the oldest API round and retries up to 3 times
   ↓
4. After a successful compaction, rebuild the context:
   - compactBoundaryMarker (records compaction type, prior token count, etc.)
   - Summary message (an invisible user message)
   - Re-read of the 5 most recent files (POST_COMPACT_TOKEN_BUDGET = 50K)
   - Plan file attachment (if any)
   - Plan mode instructions (if in plan mode)
   - Content of invoked skills (≤5K per skill, ≤25K total)
   - Incremental re-injection of deferred tools / agent listing / MCP instructions
   - SessionStart hooks run again
   - PostCompact hooks run
  ↓
5. Update the cache baseline so it is not misjudged as a cache break
```

### Prompt cache sharing

The compaction API call is one of the most expensive operations in a whole session. The system reuses the main thread's cache prefix (system prompt + tools + context messages) through `runForkedAgent`, raising the cache hit rate from 2% to nearly 100%. This optimization alone saves roughly 0.76% of fleet-wide `cache_creation` tokens.

## The output token slot optimization

An often overlooked optimization: **dynamic adjustment of maxOutputTokens**.

```typescript
// src/services/api/claude.ts — getMaxOutputTokensForModel()
const defaultTokens = isMaxTokensCapEnabled()
  ? Math.min(maxOutputTokens.default, 8_000)  // default lowered to 8K
  : maxOutputTokens.default                     // original default 32K/64K
```

Why? The API's slot mechanism reserves inference capacity according to `max_tokens`. The BQ p99 output is only 4,911 tokens, so a 32K default wastes 8-16x of slot capacity. After lowering to 8K, fewer than 1% of requests are truncated, and those automatically get one clean 64K retry.

The effect of this optimization on the token budget is indirect: more slot capacity means less queueing delay, which indirectly reduces timeouts and retries.

## Partial compact: selective compression

Besides full compaction, the user can pick a position in the message history and compress only what comes before or after it:

- **`up_to` direction**: compress what comes before the selected message and keep the recent conversation
- **`from` direction**: compress what comes after the selected message and keep the early conversation

The `from` direction preserves the prompt cache (the prefix is unchanged), while the `up_to` direction breaks the cache (the summary is inserted before the retained content).

Both directions use the same PTL (prompt-too-long) retry strategy: delete from the oldest API round, making sure at least one group of messages remains for the summary.
