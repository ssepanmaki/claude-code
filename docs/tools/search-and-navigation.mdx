## Two search dimensions

| Dimension | Tool | Underlying implementation | Use cases |
|-----------|------|---------------------------|-----------|
| **Find files by name** | Glob | ripgrep `--files` + glob filtering | "Find all test files", "find files starting with config" |
| **Find code by content** | Grep | ripgrep regex search | "Where is this function defined", "who calls this API" |

Both share the same ripgrep engine and get different search modes through different parameter combinations.

## How ripgrep is embedded

Claude Code does not depend on a system-installed ripgrep. `src/utils/ripgrep.ts` implements a three-level fallback strategy:

```
Priority 1: system ripgrep (USE_BUILTIN_RIPGREP=false)
  → use the rg binary on PATH
  → security: use only the command name 'rg', not a full path, to prevent PATH hijacking

Priority 2: embedded mode (bundled/native build)
  → process.execPath itself, argv0='rg'
  → Bun statically compiles rg into the binary and dispatches through argv0

Priority 3: vendor directory (npm build)
  → vendor/ripgrep/{arch}-{platform}/rg
  → macOS needs codesign signing + removal of the quarantine xattr
```

Platform layout example:
```
vendor/ripgrep/
  ├── x86_64-darwin/rg      # macOS Intel
  ├── arm64-darwin/rg        # macOS Apple Silicon
  ├── x86_64-linux/rg        # Linux Intel
  ├── arm64-linux/rg         # Linux ARM
  └── x86_64-win32/rg.exe    # Windows
```

### macOS code signing

In vendor mode the rg binary needs an ad-hoc signature to pass Gatekeeper (`codesignRipgrepIfNecessary()`):

```typescript
// Runs on first use:
// 1. Check whether it already has a valid signature
codesign -vv -d <rg-path>
// 2. If it is only linker-signed, re-sign it
codesign --sign - --force --preserve-metadata=entitlements,requirements,flags,runtime <rg-path>
// 3. Remove the quarantine attribute
xattr -d com.apple.quarantine <rg-path>
```

## Design considerations for search results

### head_limit and the token budget

Search results in a large project can run to hundreds of thousands of entries. By default at most 250 matches are returned. This is not an arbitrary choice but a **token budget** constraint:

- Each matching line is about 50-100 tokens
- 250 entries ≈ 12,500-25,000 tokens
- That is roughly 6-12% of a 200k context window
- Beyond that share, the AI's reasoning quality degrades

The Grep tool's `head_limit` parameter lets the AI adjust this on demand, using a larger value when searching a small project.

### Sorting by modification time

Glob puts **recently modified files first** by default. This is not the default filesystem ordering but a deliberate design decision:

```
Design assumption: recently modified files are the most likely to be relevant to the current task
Practical effect: the AI sees "live" code first, not dormant historical files
```

In `packages/builtin-tools/src/tools/GlobTool/`, ripgrep's output is sorted by mtime before being returned to the AI.

### ripgrep error handling

ripgrep execution has a dedicated error recovery chain (`src/utils/ripgrep.ts`):

| Error | Handling |
|-------|----------|
| **EAGAIN** (insufficient resources) | Automatically retry in single-threaded mode with `-j 1` |
| **Timeout** (default 20s, 60s on WSL) | Return partial results gathered so far and drop the possibly incomplete last line |
| **Buffer overflow** | Truncate to 20MB and return the results collected |
| **SIGTERM ignored** | Escalate to SIGKILL after 5 seconds |

## ToolSearch: finding the target among 50+ tools

When more than 50 tools are available (including external tools provided by MCP), the AI may not know which to use. **ToolSearch** (`packages/builtin-tools/src/tools/ToolSearchTool/`) provides a tool discovery mechanism.

### Search algorithm

ToolSearch implements keyword-based weighted search (`searchToolsWithKeywords()`):

```
Input: query = "database connection"
     ↓
1. Exact match: check whether any tool name matches exactly (fast path)
2. MCP prefix match: "mcp__postgres" → matches all postgres-related tools
3. Keyword splitting: ["database", "connection"]
4. Tool name parsing:
   - MCP tools: "mcp__server__action" → ["server", "action"]
   - Regular tools: "FileEditTool" → ["file", "edit", "tool"]
5. Weighted scoring:
   - Exact tool name match: 10 points (MCP: 12)
   - Partial tool name match: 5 points (MCP: 6)
   - searchHint match: 4 points
   - Description match: 2 points
6. Required-term filtering: a "+database" prefix means the term must be present
7. Sort by score and return the top N
```

### `select:` direct selection

The AI can also use `select:ToolName` to pick a known tool exactly. This is faster than searching and supports comma-separated batch selection (`select:A,B,C`).

### Deferred loading (Deferred Tools)

Not every tool stays resident in memory. MCP tools and low-frequency tools are marked `isDeferredTool` and are only actually loaded after ToolSearch selects them. This reduces the token overhead of every API call (tool descriptions take up a lot of tokens).

### Caching strategy

Fetching tool descriptions is memoized, and the cache is cleared only when the set of deferred tools changes:

```typescript
// Sorted tool names joined as the cache key
function getDeferredToolsCacheKey(deferredTools: Tools): string {
  return deferredTools.map(t => t.name).sort().join(',')
}
```

## Web search and fetch

The AI's information gathering is not limited to local code:

- **WebSearch** (`packages/builtin-tools/src/tools/WebSearchTool/`): calls the Anthropic API's `web_search_20250305` server tool to search the internet
- **WebFetch** (`packages/builtin-tools/src/tools/WebFetchTool/`): fetches the content of a specific URL and converts it to Markdown for the AI to read

This lets the AI consult documentation, search Stack Overflow and read GitHub issues, the same way a human developer works.

### How WebSearch is implemented

WebSearch supports three search backends through the adapter pattern, chosen by the factory function `createAdapter()` in `packages/builtin-tools/src/tools/WebSearchTool/adapters/`:

```
Adapter architecture:
  WebSearchTool.call()
    → createAdapter() picks the backend
      ├─ ApiSearchAdapter — Anthropic API server-side search (needs an official API key)
      ├─ BingSearchAdapter — scrapes Bing search pages directly and parses them (no API key needed)
      └─ BraveSearchAdapter — calls the Brave LLM Context API and parses the result (needs a Brave API key)
    → adapter.search(query, options)
    → converted to a unified SearchResult[] format and returned
```

#### Adapter selection logic

The factory function in `adapters/index.ts` picks the backend in the following priority order:

| Priority | Condition | Adapter |
|----------|-----------|---------|
| 1 | Environment variable `WEB_SEARCH_ADAPTER=api` | `ApiSearchAdapter` |
| 2 | Environment variable `WEB_SEARCH_ADAPTER=bing` | `BingSearchAdapter` |
| 3 | Environment variable `WEB_SEARCH_ADAPTER=brave` | `BraveSearchAdapter` |
| 4 | API Base URL points to Anthropic's official endpoint | `ApiSearchAdapter` |
| 5 | Third-party proxy / unofficial endpoint | `BingSearchAdapter` |

Adapters are stateless and cached for reuse within a session.

#### ApiSearchAdapter — API server-side search

Delegates the search request to the Anthropic API's `web_search_20250305` server tool:

```
Call chain:
  ApiSearchAdapter.search(query, options)
    → queryModelWithStreaming() issues a separate API call
      → carries extraToolSchemas: [BetaWebSearchTool20250305]
      → the API server executes the search and returns streaming events
        → server_tool_use / web_search_tool_result / text come back interleaved
    → extractSearchResults() extracts SearchResult[] from the content blocks
```

| Feature | Implementation |
|---------|----------------|
| **Model selection** | Feature flag `tengu_plum_vx3` controls whether Haiku (forced tool_choice) or the main model is used |
| **Search cap** | At most 8 searches per call (`max_uses: 8`) |
| **Domain filtering** | Supports `allowedDomains` / `blockedDomains` |
| **Progress tracking** | Parses `input_json_delta` while streaming to extract the query and calls `onProgress` in real time |

#### BingSearchAdapter — Bing search page parsing

Scrapes the Bing search HTML directly and extracts results with regexes, with no API key:

```
Call chain:
  BingSearchAdapter.search(query, options)
    → axios.get(bing.com/search?q=...)  — uses browser-grade headers to get past anti-scraping
    → extractBingResults(html)
      → regex-match <li class="b_algo"> blocks
      → extract the <h2><a> title and URL
      → resolveBingUrl() decodes Bing redirect links
      → extractSnippet() extracts the snippet with a three-level fallback
    → client-side domain filtering (allowedDomains / blockedDomains)
    → return SearchResult[]
```

**Anti-scraping strategy**: Bing returns an empty page that needs JS rendering for non-browser user agents. The adapter uses the full Edge browser request headers (including modern browser headers such as `Sec-Ch-Ua` and `Sec-Fetch-*`) to make sure it gets the complete HTML. It also uses the `setmkt=en-US` parameter to fix the market, so Bing does not localize by the user's IP (for example redirecting to the German or Singapore market and returning irrelevant results).

**URL decoding**: URLs in Bing results are in redirect format (`bing.com/ck/a?...&u=a1aHR0cHM6Ly9...`), and `resolveBingUrl()` base64-decodes the real target URL from the `u` parameter (the `a1` prefix = https, `a0` = http).

**Snippet extraction** (`extractSnippet()`) tries three sources in priority order:
1. `<p class="b_lineclamp...">` — the line-clamped snippet paragraph
2. The `<p>` inside `<div class="b_caption">` — a regular snippet paragraph
3. The direct text content of `<div class="b_caption">` — the fallback

| Feature | Implementation |
|---------|----------------|
| **Timeout** | 30 seconds (`FETCH_TIMEOUT_MS`) |
| **Domain filtering** | Supports `allowedDomains` / `blockedDomains`, including subdomain matching |
| **Progress tracking** | Sends query_update and search_results_received callbacks |
| **Abort support** | An external AbortSignal propagates to the axios request |

### The unified WebSearchTool interface

`WebSearchTool` (`packages/builtin-tools/src/tools/WebSearchTool/WebSearchTool.ts`) is the tool definition the main loop sees, usable with every provider (`isEnabled()` always returns true). It converts the `SearchResult[]` returned by an adapter into the internal `Output` format, and `mapToolResultToToolResultBlockParam` formats the results as text with markdown hyperlinks and appends a "REMINDER" asking the main model to include Sources in its reply.

### How WebFetch is implemented

WebFetch is a full HTTP client plus content-processing pipeline:

```
Call chain:
  WebFetchTool.call({ url, prompt })
    → getURLMarkdownContent(url)
      → validateURL() — length ≤2000, no username/password, public domain
      → URL_CACHE hit check (15-minute TTL LRU, 50MB cap)
      → checkDomainBlocklist() — pre-check via api.anthropic.com/api/web/domain_info
      → getWithPermittedRedirects() — axios request with custom redirect handling
        → HTML → Turndown converts to Markdown (lazily loaded singleton, ~1.4MB)
        → non-HTML → raw text
        → binary (PDF etc.) → persistBinaryContent() saves to disk
    → applyPromptToMarkdown()
      → truncate to 100K characters
      → queryHaiku() uses a small model to extract information according to the prompt
    → return the processed result
```

Safety protection is layered:

| Layer | Mechanism | Description |
|-------|-----------|-------------|
| **Domain pre-check** | `checkDomainBlocklist()` | Calls `api.anthropic.com/api/web/domain_info?domain=…`, cached for 5 minutes |
| **Redirect control** | `isPermittedRedirect()` | Only same-host redirects (±www) are allowed; a cross-domain redirect returns a hint so the AI calls again |
| **Redirect depth** | `MAX_REDIRECTS = 10` | Prevents redirect loops from hanging forever |
| **Content size** | `MAX_HTTP_CONTENT_LENGTH = 10MB` | Cap for a single response |
| **Request timeout** | `FETCH_TIMEOUT_MS = 60s` | Main request timeout; domain pre-check is 10s |
| **URL validation** | `validateURL()` | Checks length, protocol, username/password and public domain |
| **Egress detection** | `X-Proxy-Error: blocked-by-allowlist` | Detects blocking by an enterprise proxy |

Pre-approved domains (`packages/builtin-tools/src/tools/WebFetchTool/preapproved.ts`):

A list of domains the user does not need to authorize manually, containing ~90 mainstream technical documentation sites (MDN, Python docs, React docs, AWS docs and so on). The list is split into hostname-only and path-prefix entries, with O(1) lookup.

For pre-approved domains, WebFetch skips the Haiku summarization step (if the content is Markdown and under 100K characters) and returns the original text directly, since technical documentation is already well structured.

For the permission model, WebFetch generates `domain:xxx` rules by hostname to match the user's allow/deny/ask rules, so users can configure permanent allow or deny for a specific domain.

### ripgrep streaming output

For interactive scenarios (such as QuickOpen), ripgrep supports **streaming output** (`ripGrepStream()`):

```
rg --files → chunks arrive one by one → split by line → onLines(lines) callback
```

There is no need to wait for ripgrep to finish the whole search. The first batch of results is shown while rg is still walking the directory tree. The caller can terminate the search early through an AbortSignal (for example once enough results are found).
