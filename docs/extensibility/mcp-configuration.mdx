## Configuration sources and scopes

Claude Code's MCP configuration comes from several sources, each tied to a `scope`. Configurations are merged by priority, and a same-named entry from a higher-priority source overrides one from a lower-priority source.

### Source list

| Source | Scope | File/interface | Notes |
|------|-------|----------|------|
| Enterprise-managed | `enterprise` | System-managed path `managed-mcp.json` | **Exclusive mode**: when present, all other sources are ignored |
| Local project | `local` | `<project>/.claude/settings.local.json` | Private project-level config (not committed to VCS) |
| Project config | `project` | `<project>/.mcp.json` | Shared project-level config (can be committed to VCS) |
| User global | `user` | `~/.claude/settings.json` | User-level config shared by all projects |
| Plugin | `dynamic` | `.mcp.json` / `.mcpb` in the plugin manifest | MCP servers provided by plugins |
| claude.ai | `claudeai` | Fetched through the API | Connectors configured in the claude.ai web app |
| Built-in dynamic | `dynamic` | Registered in code | Built-in servers such as Computer Use / Chrome |
| IDE SDK | `sdk` | Passed in by the IDE | VS Code / JetBrains embedded mode |

### Merge priority (low to high)

```
claude.ai connectors     ← lowest priority
    ↓ dedupe
Plugin servers
    ↓ dedupe
User global config
    ↓
Project config (.mcp.json)    ← requires user approval
    ↓
Local project config
    ↓
Dynamic config (built-in MCP)     ← highest priority
```

`Object.assign({}, dedupedPluginServers, userServers, approvedProjectServers, localServers)` does the merge: a same-named key that appears later overrides the earlier one.

## Enterprise-managed mode

When a `managed-mcp.json` file exists, Claude Code enters **exclusive mode**:

```typescript
// config.ts:1084
if (doesEnterpriseMcpConfigExist()) {
  // Return only the enterprise config; ignore all user/project/plugin/claude.ai configs
  return { servers: filtered, errors: [] }
}
```

Characteristics:
- The path is determined by system administration (`getManagedFilePath()` + `managed-mcp.json`)
- It overrides all user-level, project-level, plugin, and claude.ai configs
- Policy filtering (allowlist/denylist) is still applied
- New servers cannot be added through the CLI (`addMcpConfig` rejects them)

## Transport types and config schema

### stdio (default)

Starts a child process and communicates over stdin/stdout using JSON-RPC.

```json
{
  "my-server": {
    "command": "npx",
    "args": ["-y", "@my-org/mcp-server"],
    "env": { "API_KEY": "..." }
  }
}
```

The `type` field can be omitted (it defaults to `stdio`). Environment variables are passed to the child process through `env` and merged with the current process environment.

**Windows note**: `npx` must be wrapped as `cmd /c npx`, otherwise it fails.

### SSE (Server-Sent Events)

Connects to a remote MCP server over HTTP SSE.

```json
{
  "my-remote": {
    "type": "sse",
    "url": "https://mcp.example.com/sse",
    "headers": { "Authorization": "Bearer ..." },
    "oauth": {
      "clientId": "...",
      "authServerMetadataUrl": "https://auth.example.com/.well-known/oauth-authorization-server"
    }
  }
}
```

OAuth authentication is supported. When authentication fails, the server enters the `needs-auth` state, with a 15-minute TTL cache to avoid repeated prompts.

### HTTP (Streamable HTTP)

HTTP streaming transport.

```json
{
  "my-http": {
    "type": "http",
    "url": "https://mcp.example.com/mcp",
    "headers": { "X-API-Key": "..." }
  }
}
```

Supports the same OAuth configuration as SSE.

### WebSocket

```json
{
  "my-ws": {
    "type": "ws",
    "url": "wss://mcp.example.com/ws"
  }
}
```

### IDE-specific types (internal)

`sse-ide` and `ws-ide` are types reserved for IDE extensions and are not configured directly by users.

- `sse-ide`: authenticates with a lockfile token
- `ws-ide`: uses the `X-Claude-Code-Ide-Authorization` header

### SDK type (internal)

`type: "sdk"` is passed in by IDE embedded mode and skips both the reserved-name check and the exclusive restriction of enterprise control.

### claude.ai proxy type (internal)

`type: "claudeai-proxy"` is used by connectors configured in the claude.ai web app. It authenticates with an OAuth bearer token and supports retry on 401.

## Configuration operations

### Adding an MCP server

Use the CLI command `claude mcp add` or the API call `addMcpConfig()`:

```bash
# Add to user config
claude mcp add my-server -s user -- npx @my-org/mcp-server

# Add to project config
claude mcp add my-server -s project -- npx @my-org/mcp-server

# Add an HTTP type
claude mcp add my-remote -s user -t http -u https://mcp.example.com/mcp
```

Validation when adding:

1. **Name check**: only letters, digits, hyphens, and underscores are allowed
2. **Reserved-name check**: `claude-in-chrome` and `computer-use` are reserved
3. **Enterprise control check**: adding is rejected in enterprise mode
4. **Schema validation**: Zod validates the config format
5. **Policy check**: denylist rejection, allowlist validation

### Removing an MCP server

```bash
claude mcp remove my-server -s user
```

### Listing MCP servers

```bash
claude mcp list
```

## Project config approval

Project configs in `.mcp.json` take effect only after explicit user approval:

```typescript
// config.ts:1166
const approvedProjectServers: Record<string, ScopedMcpServerConfig> = {}
for (const [name, config] of Object.entries(projectServers)) {
  if (getProjectMcpServerStatus(name) === 'approved') {
    approvedProjectServers[name] = config
  }
}
```

When a project is first opened, Claude Code prompts the user to approve each server in `.mcp.json`. The approval state is persisted in local config.

## Plugin MCP integration

Plugins declare MCP servers through a `.mcp.json` or `.mcpb` file in the manifest:

```typescript
// Plugin MCP loading flow
const pluginResult = await loadAllPluginsCacheOnly()
const pluginServerResults = await Promise.all(
  pluginResult.enabled.map(plugin => getPluginMcpServers(plugin, mcpErrors))
)
```

### Plugin namespace

Plugin MCP server names take the form `plugin:<pluginName>:<serverName>`, so they never collide with manually configured names.

### Deduplication

Plugin servers are deduplicated by content signature (`dedupPluginMcpServers`):

- **stdio type**: signature = `stdio:` + JSON.stringify([command, ...args])
- **URL type**: signature = `url:` + the original URL (unwrapping a CCR proxy URL)
- **sdk type**: the signature is null, so no deduplication

Deduplication rules:
1. Manual config takes precedence over plugin config
2. A plugin loaded earlier takes precedence over one loaded later
3. Suppressed plugin servers are flagged in the `/plugin` UI

### claude.ai connector deduplication

claude.ai connectors are deduplicated with the same content-signature mechanism (`dedupClaudeAiMcpServers`):
- Only enabled manual configs take part in deduplication (a disabled manual config should not suppress a connector)
- Connector names take the form `claude.ai <DisplayName>`

## Policy control

### Allowlist / Denylist

Enterprise policy controls which MCP servers are available through an allowlist and a denylist:

```typescript
// config.ts:1243 - final policy filter
for (const [name, serverConfig] of Object.entries(configs)) {
  if (!isMcpServerAllowedByPolicy(name, serverConfig)) {
    continue  // skip servers forbidden by policy
  }
  filtered[name] = serverConfig
}
```

The policy check considers:
- Server name matching
- command + args matching for the stdio type
- URL pattern matching for the URL type (wildcards supported)

### Plugin-only mode

When `isRestrictedToPluginOnly('mcp')` is enabled, only MCP servers provided by plugins are allowed, and user/project-level configs are ignored.

## Environment variable expansion

Environment variables in MCP config support `$VAR` and `${VAR}` expansion:

```json
{
  "my-server": {
    "command": "npx",
    "args": ["@my-org/mcp-server"],
    "env": {
      "API_KEY": "$MY_API_KEY",
      "DB_URL": "${DATABASE_URL}"
    }
  }
}
```

A variable that is missing during expansion produces a warning but does not block config loading.

## Built-in MCP dynamic registration

Built-in MCP servers inject their config dynamically during the `main.tsx` startup flow:

### Computer Use MCP

```typescript
// src/utils/computerUse/setup.ts
export function setupComputerUseMCP(): {
  mcpConfig: Record<string, ScopedMcpServerConfig>
  allowedTools: string[]
} {
  return {
    mcpConfig: {
      "computer-use": {
        type: "stdio",
        command: process.execPath,
        args: ["--computer-use-mcp"],
        scope: "dynamic",
      }
    },
    allowedTools: ["mcp__computer-use__screenshot", ...]
  }
}
```

Enabling conditions:
- The `CHICAGO_MCP` feature flag is on
- `getPlatform() !== "unknown"` (macOS/Windows/Linux)
- Not a non-interactive session
- The GrowthBook gate `getChicagoEnabled()` returns true

### Claude in Chrome MCP

```typescript
// Similar to Computer Use, registered in main.tsx
const { mcpConfig, allowedTools, systemPrompt } = setupClaudeInChrome()
dynamicMcpConfig = { ...dynamicMcpConfig, ...mcpConfig }
```

Enabling conditions:
- The `--chrome` argument or the `claudeInChromeDefaultEnabled` config
- The Chrome extension is installed

### VSCode SDK MCP

IDE embedded mode passes in a `type:'sdk'` config through the initialization message, and `setupVscodeSdkMcp()` sets up bidirectional notifications.

## Reserved names

The following MCP server names are reserved, and users cannot manually configure a server with the same name:

| Name | Purpose | Check condition |
|------|------|---------|
| `claude-in-chrome` | Chrome browser control | Always checked |
| `computer-use` | Desktop automation | Checked when the `CHICAGO_MCP` feature flag is on |
| `claude-vscode` | VSCode IDE integration | Passed in by the SDK; skips the name check |

The reserved-name check happens in two places:
1. `addMcpConfig()` (`config.ts:636-648`) — rejected at runtime
2. The `main.tsx` startup check (`main.tsx:2351-2368`) — exits at startup
