## One-line definition

Claude Code is an **agentic coding system that runs in your local terminal**. It is not a chatbot that offers suggestions: it reads code, edits files, runs commands and debugs programs directly in your project directory, with full shell capability.

## Technical positioning: a terminal-native agentic system

Three words are the key to understanding Claude Code:

| Positioning keyword | Meaning |
|-----------|------|
| **Terminal-native** | A native CLI application, not an IDE plugin, a web interface or an API wrapper |
| **Agentic** | The AI decides the tool-call chain on its own; it is not a one-question-one-answer chat mode |
| **Coding system** | Built for the whole software engineering workflow, not a general Q&A tool |

How it differs from similar tools at the **architecture level** (not a feature list):

| Tool | Architecture pattern | Where it runs | Tool execution |
|------|----------|----------|----------|
| **Claude Code** | Terminal-native agentic loop | Local process | Direct shell execution |
| Cursor / Copilot | IDE-integrated autocomplete + chat | Inside the IDE process | LSP / IDE API |
| Aider | CLI chat → git patch | Local process | Mostly file operations |
| ChatGPT / Claude.ai | Cloud chat + artifacts | Browser/cloud | Sandbox container |

The core difference: Claude Code has **full shell access**. It can do anything you can do in a terminal, but that also calls for matching safety mechanisms to constrain the power.

## End-to-end example: from input to output

When you type `bun run dev I have a TypeScript error, please fix it` in the terminal, what happens in the system?

```
┌─────────────────────────────────────────────────────────┐
│ 1. Entry layer (cli.tsx → main.tsx)                      │
│    feature() = false, MACRO injection, start Commander.js CLI │
├─────────────────────────────────────────────────────────┤
│ 2. Interaction layer (REPL.tsx — React/Ink)              │
│    PromptInput captures user input → UserMessage joins the session │
├─────────────────────────────────────────────────────────┤
│ 3. Orchestration layer (QueryEngine.ts)                  │
│    Manages turn lifecycle, token budget, compaction triggers │
├─────────────────────────────────────────────────────────┤
│ 4. Core loop (query.ts — Agentic Loop)                   │
│    Assemble context → call API → receive stream → parse tool calls │
│    → permission check → run tools → return results → call API again → loop │
├─────────────────────────────────────────────────────────┤
│ 5. Tool execution (BashTool.call / FileEditTool.call / ...) │
│    Actual work: read files, run commands, search code... │
├─────────────────────────────────────────────────────────┤
│ 6. Communication layer (claude.ts → Anthropic API)       │
│    Streaming HTTP, 7 providers incl. Bedrock/Vertex/Foundry │
└─────────────────────────────────────────────────────────┘
```

In this error-fixing scenario, a typical agentic loop may include several rounds of tool calls:

| Turn | AI decision | Tool call | Result |
|------|---------|----------|------|
| 1 | Look at the error first | `Bash("bun run dev 2>&1 | head -30")` | TypeScript error output |
| 2 | Locate the file | `Read("src/utils/foo.ts")` | Source contents |
| 3 | Search for related type definitions | `Grep("interface Foo", "src/")` | Where the type is defined |
| 4 | Fix the code | `FileEdit(old, new)` | Code modified |
| 5 | Verify the fix | `Bash("bun run dev 2>&1 | head -10")` | Compiles |

Every step is the AI's own decision: it chooses which tool to use, what arguments to pass, and when to stop. That is what "agentic" means.

## What it is not

- **Not an IDE plugin**: no graphical interface, no dependence on VS Code or any IDE
- **Not an API wrapper**: it has its own tool system, permission model, context engineering and session management
- **Not a chatbot**: its output is not plain text but actual file edits and command execution
- **Not a mindless executor**: every sensitive operation has a permission check and a user confirmation step

## Anatomy of the startup entry

The real code entry is `src/entrypoints/cli.tsx`, which does three key things:

```typescript
// 1. Inject a runtime polyfill: feature() always returns false
const feature = (_name: string) => false;

// 2. Inject build-time macros
globalThis.MACRO = { VERSION: "2.1.888", BUILD_TIME: ..., };

// 3. Declare the build target
globalThis.BUILD_TARGET = "external";  // external build (not Anthropic-internal)
globalThis.BUILD_ENV = "production";
globalThis.INTERFACE_TYPE = "stdio";   // standard I/O interaction
```

Control then passes to `src/main.tsx`:
1. Commander.js parses the command-line arguments
2. Initializes auth, telemetry, and policy limits
3. Loads the tool list (`getTools()`)
4. Starts the REPL (`launchRepl()`) or pipe mode (`-p`)

## Why the terminal

The terminal is not a limitation but a choice. It brings unique capabilities:

- **Full shell access**: it can run any command-line tool without writing a plugin for each capability
- **Project-native**: it works directly in the project directory and understands the filesystem structure and git state
- **Composability**: pipe mode (`echo "..." | claude -p`) allows embedding in CI/CD and automation
- **Low latency**: no Electron overhead, and the React/Ink TUI responds very fast

The cost is that users have to get used to a command-line interface, but that is also why it attracts developers who need **real control of their development environment**.
