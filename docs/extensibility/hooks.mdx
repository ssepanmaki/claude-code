## 6 hook types

Hooks can be configured to run in 6 ways, with the type definitions spread across 3 files:

- **Persistable types** (`command`, `prompt`, `agent`, `http`): Zod schemas defined in `src/schemas/hooks.ts`, declared via `z.discriminatedUnion('type', [...])`
- **callback type**: a TypeScript interface in `src/types/hooks.ts`, for internal JS functions registered by the SDK
- **function type**: defined in `src/utils/hooks/sessionHooks.ts`, for function hooks registered dynamically at runtime

| Type | How it runs | Use case |
|------|---------|---------|
| `command` | Shell command (bash/PowerShell) | General scripts, CI checks |
| `prompt` | Injected into the AI context | Code-style reminders |
| `agent` | Launches a sub-agent | Complex analysis tasks |
| `http` | HTTP request | Remote services, webhooks |
| `callback` | Internal JS function | Built-in system hooks |
| `function` | Function hook registered at runtime | Used inside agents/skills |

## Execution engine: execCommandHook

`execCommandHook()` (the `execCommandHook` function in `src/utils/hooks.ts`) is the core that runs command hooks:

```
execCommandHook(hook, hookEvent, hookName, jsonInput, signal)
  ├── Shell selection: hook.shell ?? DEFAULT_HOOK_SHELL
  │   ├── bash: spawn(cmd, [], { shell: gitBashPath | true })
  │   └── powershell: spawn(pwsh, ['-NoProfile', '-NonInteractive', '-Command', cmd])
  ├── Variable substitution
  │   ├── ${CLAUDE_PLUGIN_ROOT} → pluginRoot path
  │   ├── ${CLAUDE_PLUGIN_DATA} → plugin data directory
  │   └── ${user_config.X} → user config value
  ├── Environment variable injection
  │   ├── CLAUDE_PROJECT_DIR
  │   ├── CLAUDE_ENV_FILE (SessionStart/Setup/CwdChanged/FileChanged)
  │   └── CLAUDE_PLUGIN_OPTION_* (plugin options)
  ├── stdin write: jsonInput + '\n'
  ├── Timeout: hook.timeout * 1000 ?? 600000ms (10 minutes)
  └── Async detection: check whether the first stdout line is {"async":true}
```

### Async hook detection protocol

If the first line of a hook process's stdout is `{"async":true}`, the system turns it into a background task (detected by `isAsyncHookJSONOutput` and launched by `executeInBackground`):

```typescript
const firstLine = firstLineOf(stdout).trim()
if (isAsyncHookJSONOutput(parsed)) {
  executeInBackground({
    processId: `async_hook_${child.pid}`,
    asyncResponse: parsed,
    ...
  })
}
```

A background hook is registered in the `AsyncHookRegistry` through `registerPendingAsyncHook()`, and notifies the main thread through `enqueuePendingNotification()` when it finishes.

### asyncRewake: the hook wake-up model

Hooks in `asyncRewake` mode bypass the `AsyncHookRegistry`. When such a hook exits with code 2, a message is injected in `task-notification` mode through `enqueuePendingNotification()`, waking an idle model (via `useQueueProcessor`) or, if the model is busy, injecting a `queued_command` attachment.

## Hook output JSON schema

The output of a synchronous hook follows a strict Zod schema (`syncHookResponseSchema`, defined in `src/types/hooks.ts`; `hookJSONOutputSchema` is defined in `src/schemas/hooks.ts`):

```json
{
  "continue": false,                    // whether to keep going
  "suppressOutput": true,               // hide stdout
  "stopReason": "Security check failed", // reason when continue=false
  "decision": "approve" | "block",      // global decision
  "reason": "Explanation",              // reason for the decision
  "systemMessage": "Warning text",      // system message injected into the context
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "allow" | "deny" | "ask",
    "permissionDecisionReason": "Matched a security rule",
    "updatedInput": { ... },            // modified tool input
    "additionalContext": "Extra context" // injected into the conversation
  }
}
```

### hookSpecificOutput per event

| Event | Specific fields | Purpose |
|------|---------|------|
| `PreToolUse` | `permissionDecision`, `permissionDecisionReason`, `updatedInput`, `additionalContext` | Intercept/modify tool input |
| `PostToolUse` | `additionalContext`, `updatedMCPToolOutput` | Modify MCP tool output |
| `PostToolUseFailure` | `additionalContext` | Inject context after a failure |
| `UserPromptSubmit` | `additionalContext` | Inject extra context |
| `SessionStart` | `additionalContext`, `initialUserMessage`, `watchPaths` | Set the initial message and file watching |
| `PermissionRequest` | `decision` (with `allow`/`deny` sub-fields) | Hook decision for a permission request |
| `PermissionDenied` | `retry` | Whether to retry |
| `SubagentStart` | `additionalContext` | Inject context when a sub-agent starts |
| `Elicitation` | `action`, `content` | Control the user input dialog |
| `ElicitationResult` | `action`, `content` | Handle the elicitation result |
| `Notification` | `additionalContext` | Inject context for a notification event |
| `Setup` | `additionalContext` | Inject context during initialization |
| `CwdChanged` | `watchPaths` | Update watched paths after a directory change |
| `FileChanged` | `watchPaths` | Update watched paths after a file change |
| `WorktreeCreate` | `worktreePath` | Worktree creation notification |

## Hook matching: getMatchingHooks

`getMatchingHooks()` (the `getMatchingHooks` function in `src/utils/hooks.ts`) finds the matching hooks across all sources:

### Multi-source merging

```
getHooksConfig()
  ├── getHooksConfigFromSnapshot()    ← hooks in settings.json (user/project/local)
  ├── getRegisteredHooks()            ← callback hooks registered by the SDK
  ├── getSessionHooks()               ← session hooks registered up front by agents/skills
  └── getSessionFunctionHooks()       ← function hooks registered at runtime
```

### Matching rules

The `matcher` field supports three modes (the `matchesPattern()` function in `src/utils/hooks.ts`):

```
"Write"              → exact match
"Write|Edit"         → pipe-separated multi-value match
"^Bash(git.*)"       → regex match
"*" or ""            → wildcard (matches everything)
```

### `if` condition filtering

A hook can specify an `if` condition so it fires only for specific input. `prepareIfConditionMatcher()` (the `prepareIfConditionMatcher` function in `src/utils/hooks.ts`) precompiles the matcher:

```json
{
  "hooks": [{
    "command": "check-git-branch.sh",
    "if": "Bash(git push*)"
  }]
}
```

The `if` condition is parsed with `permissionRuleValueFromString` and supports the same syntax as permission rules (tool name + argument pattern). For the Bash tool, tree-sitter is also used for AST-level command parsing.

### Hook deduplication

The same hook command may appear more than once across config levels (user/project/local). The system deduplicates with a Map keyed on a four-part composite key, `${pluginRoot}\0${shell}\0${command}\0${ifCondition}` (built by `hookDedupKey()`), and keeps the **last merged level**.

## Workspace trust check

**All hooks require workspace trust** (the `shouldSkipHookDueToTrust()` function in `src/utils/hooks.ts`). This is a defense-in-depth measure: it stops a malicious repository's `.claude/settings.json` from running arbitrary commands before it has been trusted.

```typescript
// In interactive mode, all hooks require trust
const hasTrust = checkHasTrustDialogAccepted()
return !hasTrust
```

In SDK non-interactive mode trust is implicit (the check is skipped when `getIsNonInteractiveSession()` is true).

## Four hook capabilities mapped to the source

### 1. Intercepting operations (PreToolUse)

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny"
  }
}
```

`processHookJSONOutput()` maps `permissionDecision` to `result.permissionBehavior = 'deny'` and sets `blockingError`, which blocks the tool from running.

### 2. Modifying behavior (updatedInput / updatedMCPToolOutput)

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "updatedInput": { "command": "npm test -- --bail" }
  }
}
```

`updatedInput` replaces the original tool input; `updatedMCPToolOutput` (PostToolUse event) replaces the MCP tool's return value, which can be used to filter sensitive data.

### 3. Injecting context (additionalContext / systemMessage)

- `additionalContext` → injected as a user message through `createAttachmentMessage({ type: 'hook_additional_context' })`
- `systemMessage` → injected as a system warning and shown directly to the user

### 4. Controlling flow (continue / stopReason)

```json
{ "continue": false, "stopReason": "Build failed, stopping execution" }
```

`continue: false` sets `preventContinuation = true`, which stops the agent from taking further actions.

## Session hook lifecycle

Agent and skill frontmatter hooks are registered through `registerFrontmatterHooks()` (called from `packages/builtin-tools/src/tools/AgentTool/runAgent.ts`; defined in `src/utils/hooks/registerFrontmatterHooks.ts`) and bound to the agent's session ID. When the agent finishes they are cleaned up through `clearSessionHooks()` (defined in `src/utils/hooks/sessionHooks.ts`).

```typescript
// runAgent.ts — register the agent's frontmatter hooks
registerFrontmatterHooks(rootSetAppState, agentId, agentDefinition.hooks, ...)

// runAgent.ts — cleanup in the finally block
clearSessionHooks(rootSetAppState, agentId)
```

This ensures that Agent A's hooks never leak into Agent B's execution.
