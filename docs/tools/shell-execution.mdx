## Execution path overview

The complete path of a Bash command from the AI's decision to actual execution:

```
The AI generates tool_use: { command: "npm test" }
  ↓
BashTool.validateInput()         ← basic input validation
  ↓
BashTool.checkPermissions()      ← permission check (see the security chapter)
  ├── isReadOnly()? → auto allow (read-only commands skip approval)
  ├── bashToolHasPermission()    ← AST parsing + semantic checks + rule matching
  └── no match → confirmation dialog
  ↓
BashTool.call() → runShellCommand()
  ↓
shouldUseSandbox(input)          ← whether to wrap in a sandbox
  ↓
Shell.exec(command, { shouldUseSandbox, shouldAutoBackground })
  ↓
spawn(wrapped_command)           ← actual process creation
```

## Detecting read-only commands: why Read skips approval but Bash does not always

BashTool's `isReadOnly()` method (`packages/builtin-tools/src/tools/BashTool/BashTool.tsx:655`) decides whether a command is treated as "read-only":

```typescript
isReadOnly(input) {
  const compoundCommandHasCd = commandHasAnyCd(input.command)
  const result = checkReadOnlyConstraints(input, compoundCommandHasCd)
  return result.behavior === 'allow'
}
```

The logic is based on 4 command sets (`BashTool.tsx:120-166`):

| Set | Commands | Nature |
|------|------|------|
| `BASH_SEARCH_COMMANDS` | find, grep, rg, ag, ack, locate, which, whereis | Search |
| `BASH_READ_COMMANDS` | cat, head, tail, wc, stat, file, jq, awk, sort, uniq... | Read/analysis |
| `BASH_LIST_COMMANDS` | ls, tree, du | Listing |
| `BASH_SEMANTIC_NEUTRAL_COMMANDS` | echo, printf, true, false, : | Semantically neutral (does not affect the decision) |

For compound commands (`ls dir && echo "---" && ls dir2`), the system splits them and checks segment by segment: **every non-neutral segment must belong to the sets above** for the whole command to be treated as read-only.

```typescript
// BashTool.tsx — simplified decision logic
for (const part of partsWithOperators) {
  if (BASH_SEMANTIC_NEUTRAL_COMMANDS.has(baseCommand)) continue  // skip neutral segments
  if (!isPartSearch && !isPartRead && !isPartList) {
    return { isSearch: false, isRead: false, isList: false }  // any segment fails → not read-only
  }
}
```

## AST security parsing: tree-sitter bash parsing

`preparePermissionMatcher()` (`BashTool.tsx:663`) parses the command structure with `parseForSecurity()` before the permission check:

```typescript
async preparePermissionMatcher({ command }) {
  const parsed = await parseForSecurity(command)
  if (parsed.kind !== 'simple') {
    return () => true  // parse failed → fail-safe, trigger all hooks
  }
  // Extract the subcommand list, strip VAR=val prefixes
  const subcommands = parsed.commands.map(c => c.argv.join(' '))
  return pattern => {
    return subcommands.some(cmd => matchWildcardPattern(pattern, cmd))
  }
}
```

The key safety point: for a compound command `ls && git push`, parsing splits it into `["ls", "git push"]`, ensuring `git push` cannot bypass the permission check because its first half is a read-only command. When parsing fails the policy is fail-safe: assume unsafe and trigger all safety hooks.

## Timeout control: a tiered policy

```
User-specified timeout → used directly
  ↓ not specified
getDefaultTimeoutMs()
  ├── Default cap: 120,000ms (2 minutes)
  └── Maximum cap: 600,000ms (10 minutes, when explicitly set by the user)
```

After a timeout the system does not simply kill the process: `ShellCommand` (`src/utils/ShellCommand.ts:144`) notifies the caller through an `onTimeout` callback, and the caller decides whether to terminate or background it.

## Automatic backgrounding

A long-running command can be turned into a background task automatically so it does not block the AI's agentic loop:

```typescript
// BashTool.tsx:1158
const shouldAutoBackground = !isBackgroundTasksDisabled 
  && isAutobackgroundingAllowed(command)
```

The full automatic backgrounding path:

```
The command starts executing
  ↓ progress polling
Not finished within 15 seconds (ASSISTANT_BLOCKING_BUDGET_MS)
  ↓
Check isAutobackgroundingAllowed(command)
  ↓ allowed
Convert the foreground task into a background task (backgroundExistingForegroundTask)
  ↓
shellCommand.onTimeout → spawnBackgroundTask()
  ↓
Return a taskId to the AI, which can go on with other work
  ↓
When the background task finishes, the result is reported through the notification mechanism
```

The main-thread Agent has a 15-second blocking budget; beyond that the system backgrounds the command automatically. This prevents a single `npm install` from blocking the whole agentic loop for minutes.

## Output truncation strategy

When command output is too long it is truncated, to avoid stuffing huge logs into the AI's context window:

| Truncation point | Location | Behavior |
|--------|------|------|
| `maxResultSizeChars` | Tool level (usually 100K characters) | Over-long output is truncated before being written to the message |
| Progress polling truncation | `onProgress` callback | Only the last few lines are passed on for progress display |
| `totalBytes` marker | `isIncomplete` parameter | Tells the AI the output was truncated |

Truncation is not simply chopping the tail: the `isIncomplete` marker makes sure the AI knows the output is incomplete and can decide whether to fetch it again with a more precise command.

## Why dedicated tools rather than calling the shell directly

Claude Code provides dedicated tools (Read, Grep, Glob) for file reading/writing, code search and the like, instead of having the AI use shell commands such as `cat` and `grep`. This is more than a user-experience choice; it is an architectural design decision:

| Dimension | Dedicated tools | Bash commands |
|------|---------|----------|
| **Permission granularity** | `Read` is a read-only operation → allowed automatically | `Bash: cat file` needs approval of the whole command (cat is in the read-only set but goes through a different path) |
| **Structured output** | Returns structured data, the UI can render diffs and highlighting | Plain-text output, no rendering optimizations |
| **Performance** | File cache, pagination, token budget control | A new process every time, no cache |
| **Concurrency safety** | `isConcurrencySafe()` returns `true` → can run in parallel | Bash commands may have side effects, run serially |
| **Security audit** | The tool name exactly matches permission rules | The command structure must be AST-parsed before matching |

`isConcurrencySafe()` (`BashTool.tsx:652`) is an often-overlooked but important design: only read-only commands can run in parallel in the agentic loop, and commands with side effects must run serially to prevent race conditions.

## Streaming design of progress feedback

BashTool's command execution is streaming, pushing output line by line through the `onProgress` callback:

```
runShellCommand()
  ├── Shell.exec() starts the child process
  ├── Polls the output file every second
  ├── onProgress(lastLines, allLines, totalLines, totalBytes, isIncomplete)
  │   ├── Updates lastProgressOutput / fullOutput
  │   └── resolveProgress() → wakes the generator yield
  ├── yield { type: 'progress', output, fullOutput, elapsedTimeSeconds }
  └── return { code, stdout, interrupted, ... }
```

The UI layer shows command output in real time through the `useToolCallProgress` hook. The `resolveProgress()` signaling mechanism makes the generator yield only when there is new data, avoiding busy-waiting.
