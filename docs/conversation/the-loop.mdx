## What is the Agentic Loop

A traditional chatbot answers one question with one reply.
Claude Code is different: you state a goal, and it may run a dozen or more steps in a row before giving you the final result.

The mechanism behind this is called the **Agentic Loop**. The core implementation is the `queryLoop()` async generator function in `src/query.ts`. It is a `while(true)` loop, and each iteration is one "think → act → observe" cycle.

## Full structure of the loop

Each iteration of `queryLoop()` (the main `while(true)` loop in `src/query.ts`) contains the following phases:

### Phase 1: Context pre-processing (Pre-Processing Pipeline)

Before calling the API, five compaction/optimization steps run in order:

```
messagesForQuery (raw messages)
  ↓ applyToolResultBudget()    — truncate tool results to budget (by maxResultSizeChars)
  ↓ snipCompactIfNeeded()      — history Snip compaction (HISTORY_SNIP feature)
  ↓ microcompact()             — micro-compaction (summarize tool results)
  ↓ applyCollapsesIfNeeded()   — context collapse (CONTEXT_COLLAPSE feature)
  ↓ autocompact()              — auto-compaction (triggered when over the threshold)
messagesForQuery (processed messages) → sent to the API
```

The output of each step is the input of the next, forming a serial pipeline. The number of tokens freed by Snip and Microcompact is passed to the autocompact threshold calculation (`snipTokensFreed`) to avoid compacting twice.

### Phase 2: Streaming API call (Streaming Loop)

`deps.callModel()` issues the streaming request (inside the `attemptWithFallback` loop in `src/query.ts`) and returns an AsyncGenerator. During streaming:

- **AssistantMessage**s are collected into the `assistantMessages[]` array
- **tool_use blocks** are extracted into `toolUseBlocks[]`, and `needsFollowUp = true` is set
- **StreamingToolExecutor** starts executing tools in parallel while the stream is still running (it does not wait for the stream to end)
- Recoverable errors (prompt-too-long, max-output-tokens) are **withheld**, and recovery is attempted first

Key guards in the streaming callback:
- `backfillObservableInput()`: backfills observable fields on tool_use blocks (such as expanded file paths), but clones the message only when new fields were added, to avoid breaking the byte-for-byte consistency of the prompt cache
- Streaming fallback detection: if `streamingFallbackOccured` is set, the messages collected so far are marked as tombstones, cleared, and the request is retried

### Phase 3: Tool execution

If `needsFollowUp` is true, the loop does not terminate and executes tools instead:

```typescript
// Two tool executors (mutually exclusive)
const toolUpdates = streamingToolExecutor
  ? streamingToolExecutor.getRemainingResults()  // streaming: get finished + pending results
  : runTools(toolUseBlocks, assistantMessages, canUseTool, toolUseContext)
```

Tool results are normalized by `normalizeMessagesForAPI()`, merged with the original messages, and enter the **next loop iteration**.

### Phase 4: Terminate or continue

At the end of each iteration, conditions decide whether to `return` (terminate) or `continue`:

The loop has several termination paths, listed in the order they can fire:

|--------|----------|-----------|

## Continuation conditions (recovery paths)

The loop is more than a simple "continue if there is a tool_use". It also has several recovery/retry paths:

### 1. Normal tool loop (`next_turn`)
`needsFollowUp = true` → run tools → new messages appended to `messagesForQuery` → state reassigned → `continue`

### 2. max_output_tokens recovery (`max_output_tokens_escalate` / `max_output_tokens_recovery`)
When the AI output is truncated (`apiError === 'max_output_tokens'`), recovery has two stages:
- **Escalation stage** (`max_output_tokens_escalate`): on the first truncation, `maxOutputTokens` is raised from the default to `ESCALATED_MAX_TOKENS` (64K). The retry is silent and injects no meta message.
- **Recovery stage** (`max_output_tokens_recovery`): if the output is still truncated after escalation, a recovery message "Output token limit hit. Resume directly..." is injected, with at most `MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3` retries. Once recovery is exhausted, the withheld error message is released.

### 3. Prompt-too-long recovery (`collapse_drain_retry` / `reactive_compact_retry`)
On a 413 error, two compaction strategies are tried in priority order:
- **Context Collapse Drain** (`collapse_drain_retry`): commits all staged collapses to free space, then retries. If the previous iteration was already a `collapse_drain_retry`, it is skipped to avoid an infinite loop.
- **Reactive Compact** (`reactive_compact_retry`): if collapse drain cannot recover, an immediate compaction (reactive compact) is triggered, and the request is retried after a summary is generated. The `hasAttemptedReactiveCompact` flag prevents an infinite loop.

### 4. Stop hook blocking retry (`stop_hook_blocking`)
A Stop hook can inject a blocking error message that forces the AI to rethink. The new messages (containing the blocking error) are appended to the conversation, `stopHookActive = true`, and the next iteration begins.

### 5. Token budget continuation nudge (`token_budget_continuation`)
When the `TOKEN_BUDGET` feature is enabled and token consumption reaches the threshold without exceeding the budget, a nudge message is injected to make the AI wrap up faster, and the loop continues.

## Model fallback

When the main model is unavailable (`FallbackTriggeredError`, the catch branch of the `attemptWithFallback` loop in `src/query.ts`):

1. The collected `assistantMessages` are cleared, and tool_use blocks receive a synthetic tool_result: "Model fallback triggered"
2. Thinking signature blocks are removed (`stripSignatureBlocks`), because thinking signatures are bound to a model and replaying them across models returns a 400
3. The loop switches to `fallbackModel` and updates `toolUseContext.options.mainLoopModel`
4. A system message is generated: "Switched to {fallback} due to high demand for {original}"
5. The streaming request is issued again

## The state machine: the State object

State for each iteration is passed through the `State` type (type definition in `src/query.ts`):

```typescript
// src/query.ts — State type definition
type State = {
  messages: Message[]                        // current conversation messages
  toolUseContext: ToolUseContext              // tool context (including permissions)
  autoCompactTracking: AutoCompactTrackingState | undefined  // compaction tracking
  maxOutputTokensRecoveryCount: number       // output-truncation recovery count
  hasAttemptedReactiveCompact: boolean       // whether reactive compact was already tried
  maxOutputTokensOverride: number | undefined // output token limit override
  pendingToolUseSummary: Promise<...> | undefined  // async tool summary
  stopHookActive: boolean | undefined        // whether a Stop hook is active
  turnCount: number                          // turn count
  transition: Continue | undefined           // reason for the previous continue
}
```

Every `continue` creates a new State object (an immutable update) instead of mutating in place. The `transition` field records why the loop continued, which lets later iterations detect a specific recovery path (such as `collapse_drain_retry`) and avoid cycles.

## Token budget (experimental)

When the `TOKEN_BUDGET` feature is enabled (the budget-check logic inside the `!needsFollowUp` branch in `src/query.ts`), the loop checks token consumption before terminating:

- **continuation**: the budget has not been reached but the threshold is exceeded → inject a nudge message so the AI wraps up faster
- **diminishing_returns**: diminishing returns detected → terminate early
- Budget data comes from `createBudgetTracker()` and accumulates across iterations

## Why not "plan once, execute in batch"

<Note>
The source shows why Claude Code chooses a step-by-step loop:
</Note>

- **Every step produces real information**: the `toolResults` returned by `runTools()` cannot be known by the API in advance: command output, file contents, error messages
- **Dynamic context management**: before each iteration the compaction need is re-evaluated (autocompact → microcompact → snip) based on the latest token count
- **Immediate error recovery**: a failed tool does not force a restart, because a stop hook can inject a blocking error so the AI adjusts its strategy
- **User control**: `abortController.signal` is checked at several points in the loop (lines 1059, 1095, 1529), so pressing ESC interrupts gracefully
- **Cost control**: the Token Budget is checked before each termination to prevent pointless looping

## A complete iteration example

> User: "Find all unused import statements in the project and delete them"

```
Iteration 1: think → act
  Pre-processing pipeline: applyToolResultBudget → snipCompact(HISTORY_SNIP feature) → microcompact → applyCollapses(CONTEXT_COLLAPSE feature) → autocompact
    → Context is short, no compaction needed
  API call: returns tool_use(Glob, "**/*.ts")
  Tool execution: returns 42 file paths
  → needsFollowUp = true
  → transition: { reason: 'next_turn' }, continue

Iteration 2: think → act
  Pre-processing pipeline: the 42 file results are still within budget
  API call: returns tool_use(Grep, "import.*from")
  Tool execution: finds 120 imports across 15 files
  → needsFollowUp = true
  → transition: { reason: 'next_turn' }, continue

Iteration 3: think → act (multiple calls)
  Pre-processing pipeline: the 120 Grep results trigger microcompact → summarized
  API call: returns 3 tool_use(FileEdit, ...)
  Tool execution: deletes 5 unused imports
  → needsFollowUp = true
  → transition: { reason: 'next_turn' }, continue

Iteration 4: summary
  API call: returns plain text "Cleaned up 5 unused imports across 3 files"
  → needsFollowUp = false
  → Stop hooks pass
  → Token Budget check passes (if enabled)
  → return { reason: 'completed' }
```
