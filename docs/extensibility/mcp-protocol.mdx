## Architecture overview: from configuration to usable tools

```
Config layer (merged from several sources)
  ├── settings.json: { mcpServers: { "my-db": { command: "npx", args: [...] } } }   ← external
  ├── .mcp.json: project-level MCP config                                            ← external
  ├── plugin manifest (.mcp.json / .mcpb)                                            ← external (plugin)
  ├── claude.ai connectors                                                           ← external (remote)
  ├── enterprise managed-mcp.json                                                    ← external (enterprise-managed)
  ├── setupComputerUseMCP() / setupClaudeInChrome()                                  ← built-in (dynamic registration)
  └── passed in by the SDK (type:'sdk')                                              ← built-in (IDE embedding)
  ↓
getAllMcpConfigs()                    ← enterprise exclusive, or merge of user/project/local + plugin + claude.ai
  ↓
useManageMCPConnections()             ← React Hook managing the connection lifecycle
  ↓
connectToServer(name, config)         ← memoized (lodash memoize)
  ├── Decision: built-in MCP → InProcessTransport (same process)
  ├── Decision: external stdio → StdioClientTransport (child process)
  ├── Decision: remote SSE/HTTP/WS → network transport
  └── Returns MCPServerConnection     ← { connected | failed | needs-auth | pending | disabled }
  ↓
fetchToolsForClient(client)           ← LRU(20) cache
  ├── client.request({ method: 'tools/list' })
  └── Each tool is wrapped as an MCPTool  ← unified Tool interface
  ↓
assembleToolPool()                    ← merges built-in tools + MCP tools
  ↓
Tool name format: mcp__<serverName>__<toolName>  ← buildMcpToolName()
```

## Two MCP modes: built-in vs. external

Claude Code's MCP implementation distinguishes **built-in MCP servers** from **external MCP servers**. Both use the same client protocol and tool discovery mechanism, but they differ completely in how they connect, how their lifecycle is managed, and where their configuration comes from.

### Built-in MCP servers

Built-in MCP servers are provided by Claude Code itself and need no manual configuration. They are registered automatically at startup as `dynamic`-scope configs and run in the same process.

| Server | Name | Package path | Feature Flag | How it is enabled |
|--------|------|--------|-------------|---------|
| Computer Use | `computer-use` | `@ant/computer-use-mcp` | `CHICAGO_MCP` | GrowthBook gate + macOS + interactive |
| Claude in Chrome | `claude-in-chrome` | `@ant/claude-for-chrome-mcp` | — | `--chrome` flag or the `claudeInChromeDefaultEnabled` setting |
| VSCode SDK | `claude-vscode` | — | — | IDE embedded mode (type:`sdk`) |

#### InProcessTransport: zero-overhead same-process communication

Built-in servers run through `InProcessTransport` (`src/services/mcp/InProcessTransport.ts`) and **do not spawn a child process**:

```typescript
// Create a pair of linked transports — messages pass directly between the two ends
const [clientTransport, serverTransport] = createLinkedTransportPair()

// The server end connects to serverTransport
inProcessServer = createComputerUseMcpServerForCli()
await inProcessServer.connect(serverTransport)

// The client end uses clientTransport (same interface as an external MCP Client)
transport = clientTransport
```

Core design of `InProcessTransport`:
- `send()` delivers messages to the peer asynchronously via `queueMicrotask()`, avoiding stack-depth problems with synchronous request/response
- `close()` closes both directions, and closing either end triggers the `onclose` callback on both
- No network overhead, no IPC serialization, no process startup time

#### Dynamic registration flow

Built-in servers are registered in the startup flow of `main.tsx`, which injects `dynamicMcpConfig`:

```typescript
// main.tsx: dynamic registration of the Computer Use MCP
if (feature("CHICAGO_MCP") && getPlatform() !== "unknown" && !getIsNonInteractiveSession()) {
  const { getChicagoEnabled } = await import("src/utils/computerUse/gates.js")
  if (getChicagoEnabled()) {
    const { setupComputerUseMCP } = await import("src/utils/computerUse/setup.js")
    const { mcpConfig, allowedTools } = setupComputerUseMCP()
    dynamicMcpConfig = { ...dynamicMcpConfig, ...mcpConfig }
    allowedTools.push(...cuTools)
  }
}
```

The config returned by `setupComputerUseMCP()` (`src/utils/computerUse/setup.ts`):

```typescript
{
  "computer-use": {
    type: "stdio",           // typed as stdio (but client.ts intercepts it into an InProcessTransport)
    command: process.execPath,
    args: ["--computer-use-mcp"],
    scope: "dynamic",        // dynamic scope, not persisted
  }
}
```

#### Interception at connect time

`connectToServer()` intercepts built-in servers by name at `client.ts:906-944`:

```typescript
// Chrome MCP — runs in-process, avoiding a ~325MB child process
if (isClaudeInChromeMCPServer(name)) {
  const { createChromeContext } = await import('../../utils/claudeInChrome/mcpServer.js')
  const { createClaudeForChromeMcpServer } = await import('@ant/claude-for-chrome-mcp')
  const { createLinkedTransportPair } = await import('./InProcessTransport.js')
  const context = createChromeContext(config.env)
  inProcessServer = createClaudeForChromeMcpServer(context)
  const [clientTransport, serverTransport] = createLinkedTransportPair()
  await inProcessServer.connect(serverTransport)
  transport = clientTransport
}

// Computer Use MCP — likewise
if (feature('CHICAGO_MCP') && isComputerUseMCPServer(name)) {
  const { createComputerUseMcpServerForCli } = await import('../../utils/computerUse/mcpServer.js')
  const { createLinkedTransportPair } = await import('./InProcessTransport.js')
  inProcessServer = await createComputerUseMcpServerForCli()
  const [clientTransport, serverTransport] = createLinkedTransportPair()
  await inProcessServer.connect(serverTransport)
  transport = clientTransport
}
```

#### Reserved-name protection

Built-in server names are reserved, and users cannot add a config with the same name (`config.ts:636-648`):

```typescript
// Check for reserved names when adding an MCP config
if (isClaudeInChromeMCPServer(name)) {
  throw new Error(`Cannot add MCP server "${name}": this name is reserved.`)
}
if (feature('CHICAGO_MCP') && isComputerUseMCPServer(name)) {
  throw new Error(`Cannot add MCP server "${name}": this name is reserved.`)
}
```

There is also a global check at startup (`main.tsx:2351-2368`): if the user config contains a reserved name (and is not `type:'sdk'`), it calls `process.exit(1)` directly.

#### VSCode SDK MCP

The VSCode SDK MCP is a special built-in mode. An IDE (such as VS Code or JetBrains) launches Claude Code in embedded mode and passes in a `type:'sdk'` MCP config. Such configs:
- Skip the reserved-name check (the IDE may use any name)
- Do not take part in the exclusive control of enterprise MCP
- Connect through the VSCode SDK transport
- Support bidirectional notifications (such as `file_updated` and `experiment_gates`)

```typescript
// src/services/mcp/vscodeSdkMcp.ts
export function setupVscodeSdkMcp(sdkClients: MCPServerConnection[]): void {
  const client = sdkClients.find(client => client.name === 'claude-vscode')
  if (client && client.type === 'connected') {
    // Register the log_event notification handler
    client.client.setNotificationHandler(LogEventNotificationSchema(), ...)
    // Send experiment gates to VSCode
    client.client.notification({ method: 'experiment_gates', params: { gates } })
  }
}
```

### External MCP servers

External MCP servers are declared by the user in configuration files and run as child processes or over network connections.

#### Configuration sources

| Source | Scope | File location | Priority |
|------|-------|---------|--------|
| Project config | `project` | `<project>/.mcp.json` | Highest (overrides same-named entries) |
| Local config | `local` | `<project>/.claude/settings.local.json` | High |
| User config | `user` | `~/.claude/settings.json` | Medium |
| Plugin | `dynamic` | `.mcp.json` in the plugin manifest | Medium |
| claude.ai | `claudeai` | Fetched through the API | Low |
| Enterprise-managed | `enterprise` | System-managed path `managed-mcp.json` | Exclusive (overrides everything when present) |

#### Configuration example

```json
// MCP config in settings.json / .mcp.json
{
  "mcpServers": {
    // stdio type — spawns a child process
    "my-database": {
      "command": "npx",
      "args": ["@my-org/db-mcp-server"],
      "env": { "DB_URL": "postgres://..." }
    },

    // HTTP streaming type — remote server
    "remote-api": {
      "type": "http",
      "url": "https://api.example.com/mcp"
    },

    // SSE type — Server-Sent Events
    "realtime-feed": {
      "type": "sse",
      "url": "https://feed.example.com/sse"
    },

    // WebSocket type
    "ws-service": {
      "type": "ws",
      "url": "wss://ws.example.com/mcp"
    }
  }
}
```

#### Config merging and deduplication

`getAllMcpConfigs()` (`config.ts`) merges configs from multiple sources by priority:

1. If an enterprise-managed config exists, it is **returned exclusively** (all other sources are ignored)
2. Otherwise merge: user → project → local → plugin → claude.ai
3. Plugin vs. manual config dedup: `getMcpServerSignature()` produces a content signature (based on command/args/url), and a plugin config is suppressed by a manual config with the same signature
4. `addScopeToServers()` tags each config entry with its source scope

## 7 transport implementations

`connectToServer()` (`client.ts:596-1643`) dispatches to a different Transport implementation based on `config.type`:

| Transport type | Transport class | Use case | Authentication |
|----------|-------------|---------|---------|
| `stdio` (default) | `StdioClientTransport` | External local child process | None |
| `sse` | `SSEClientTransport` | Remote SSE service | `ClaudeAuthProvider` + OAuth |
| `http` | `StreamableHTTPClientTransport` | HTTP streaming | `ClaudeAuthProvider` + OAuth |
| `sse-ide` | `SSEClientTransport` | IDE integration | lockfile token |
| `ws-ide` | `WebSocketTransport` | IDE WebSocket | `X-Claude-Code-Ide-Authorization` |
| `ws` | `WebSocketTransport` | WebSocket service | session ingress token |
| `claudeai-proxy` | `StreamableHTTPClientTransport` | claude.ai proxy | OAuth bearer + 401 retry |
| InProcess (built-in) | `InProcessTransport` | Computer Use / Chrome | None (same process) |

### Process management for stdio transport

An MCP server of type stdio runs as a child process, and cleanup uses a **signal escalation strategy** (`client.ts:1431-1564`):

```
SIGINT (100ms) → SIGTERM (400ms) → SIGKILL
```

Total cleanup time is capped at 600ms, so a slow MCP server shutdown cannot block the CLI from exiting.

### Auth state machine for remote transports

SSE/HTTP types use `ClaudeAuthProvider` for the OAuth flow. When authentication fails the server enters the `needs-auth` state, and a cache file with a 15-minute TTL (`mcp-needs-auth-cache.json`) is written to avoid repeated auth prompts.

```
Connection attempt → 401 Unauthorized
  ↓
handleRemoteAuthFailure()
  ├── logEvent('tengu_mcp_server_needs_auth')
  ├── setMcpAuthCacheEntry(name)         ← writes the 15min TTL cache
  └── return { type: 'needs-auth' }      ← UI shows the auth prompt
```

## Connection caching and reconnection

`connectToServer` uses lodash `memoize` to cache connection objects, with the cache key `${name}-${JSON.stringify(config)}`.

### Cache invalidation triggers

When a connection closes (`client.onclose`), all related caches are cleared (`client.ts:1376-1404`):

```typescript
client.onclose = () => {
  const key = getServerCacheKey(name, serverRef)
  fetchToolsForClient.cache.delete(name)      // tools cache
  fetchResourcesForClient.cache.delete(name)  // resources cache
  fetchCommandsForClient.cache.delete(name)   // commands cache
  connectToServer.cache.delete(key)           // connection cache
}
```

### Connection degradation detection

Remote transports have a **consecutive error counter** (`client.ts:1229`):

```typescript
let consecutiveConnectionErrors = 0
const MAX_ERRORS_BEFORE_RECONNECT = 3
```

After 3 consecutive terminal errors (ECONNRESET, ETIMEDOUT, EPIPE, and so on), the transport is closed proactively to trigger a reconnect. For HTTP transport, session expiry is also detected (404 + JSON-RPC code -32001).

### Per-request timeout protection

Each HTTP request uses its own `setTimeout` timeout (`wrapFetchWithTimeout`, `client.ts:493`) instead of a shared `AbortSignal.timeout()`. The reason is that Bun's GC of AbortSignal.timeout is lazy: each request holds about 2.4KB of native memory, which is not reclaimed for 60s even if the request finishes in milliseconds.

```typescript
const controller = new AbortController()
const timer = setTimeout(c => c.abort(...), MCP_REQUEST_TIMEOUT_MS, controller)
timer.unref?.()  // does not keep the process alive
```

## Tool discovery: from MCP to the Tool interface

`fetchToolsForClient()` (`client.ts:1744-2000`) is cached with `memoizeWithLRU` (limit 100) and converts MCP tools into Claude Code's unified Tool interface:

```typescript
const fullyQualifiedName = buildMcpToolName(client.name, tool.name)
// Result: "mcp__my-database__query"
```

### Tool discovery for built-in MCP

Although built-in MCP servers use InProcessTransport, their tool discovery flow is identical to that of external servers:

- **Computer Use**: `createComputerUseMcpServerForCli()` in `src/utils/computerUse/mcpServer.ts` builds the MCP Server object and registers the `ListToolsRequestSchema` handler. Tool descriptions include a platform-specific list of installed apps (enumerated with a 1s timeout).
- **Claude in Chrome**: `createClaudeForChromeMcpServer()` in the `@ant/claude-for-chrome-mcp` package builds the Server and provides 17+ browser control tools.
- **VSCode SDK**: the tool list is provided by the IDE side and delivered through the SDK transport.

### Tool description truncation

MCP tool descriptions are capped at 2048 characters (`MAX_MCP_DESCRIPTION_LENGTH`). Descriptions of 15-60KB have been observed from OpenAPI-generated MCP servers.

### Tool capability annotations

Each MCP tool is annotated automatically from `tool.annotations`:

| Annotation | Maps to | Meaning |
|------|--------|------|
| `readOnlyHint` | `isReadOnly()` + `isConcurrencySafe()` | Read-only, can run in parallel |
| `destructiveHint` | `isDestructive()` | Destructive operation |
| `openWorldHint` | `isOpenWorld()` | Open world (not enumerable) |
| `title` | `userFacingName()` | Display name |

### Permission checks for MCP tools

MCP tools return `{ behavior: 'passthrough' }` by default (`client.ts:1816-1834`), which means they always enter the permission confirmation flow. Tool names are matched exactly against permission rules using the `mcp__` prefix.

Tools of built-in MCP servers are authorized automatically through the `allowedTools` list, which is added at startup in `main.tsx` and bypasses the normal permission prompt. For example, the `request_access` tool of Computer Use handles session-level approval itself.

## Execution path of an MCP tool

```
The AI emits tool_use: { name: "mcp__my-db__query", input: { sql: "..." } }
  ↓
MCPTool.call()                               ← client.ts:1835
  ├── ensureConnectedClient()                ← makes sure the connection is valid (reconnects)
  ├── callMCPToolWithUrlElicitationRetry()   ← with Elicitation retry
  │   ├── client.request({ method: 'tools/call' })
  │   ├── handle image results (resize + persist)
  │   └── content truncation (mcpContentNeedsTruncation)
  ├── McpSessionExpiredError → retry once
  └── returns { data: content, mcpMeta }
```

### Automatic retry on session expiry

An MCP session over HTTP transport can expire. When `McpSessionExpiredError` is detected, the call is retried once (`client.ts:1862`), because `ensureConnectedClient()` has already cleared the cache and established a new connection.

### Content truncation and persistence

Large MCP tool output is truncated by `truncateMcpContentIfNeeded`, and binary content (images) is written to a file by `persistBinaryContent` and replaced with the file path. Images are resized automatically (`maybeResizeAndDownsampleImageBuffer`).

## Concurrency control for MCP connections

```typescript
// Concurrent connections for local servers
getMcpServerConnectionBatchSize()    // default 3

// Concurrent connections for remote servers
getRemoteMcpServerConnectionBatchSize()  // default 20
```

Local MCP servers (stdio) are heavyweight child processes, so concurrent connections default to a limit of 3. Remote servers are lightweight HTTP requests, so 20 concurrent connections are allowed.

## Built-in vs. external MCP: summary

| Dimension | Built-in MCP | External MCP |
|------|---------|---------|
| **Transport** | `InProcessTransport` (same process) | stdio / SSE / HTTP / WebSocket |
| **Config source** | Dynamic registration via `setupComputerUseMCP()` / `setupClaudeInChrome()` and similar | settings.json / .mcp.json / plugin / claude.ai |
| **Scope** | `dynamic` | `user` / `project` / `local` / `enterprise` / `claudeai` |
| **Process model** | Same process, zero overhead | Child process (stdio) or network connection |
| **Name protection** | Reserved names; users cannot add the same name | Free naming (alphanumerics + `-_`) |
| **Lifecycle** | Starts and stops with the CLI | Connection cache + on-demand reconnect |
| **Permissions** | Auto-authorized via `allowedTools` | `passthrough` enters permission confirmation |
| **Feature Flag** | `CHICAGO_MCP` (Computer Use) and others | None (always available) |
| **Tool discovery** | Same as external (MCP protocol) | Standard MCP `tools/list` |
| **Cleanup** | `inProcessServer.close()` | Signal escalation SIGINT→SIGTERM→SIGKILL |
