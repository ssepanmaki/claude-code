## Why streaming is needed

Imagine the AI needs 30 seconds to generate a complete answer. If nothing were shown until the full answer arrived, the experience would be terrible.

Streaming lets the user **watch the AI's thinking in real time**:
- Text appears character by character, so the user can tell early whether the direction is right
- Tool call parameters can be previewed while they are still being generated
- Long-running tasks do not make the user feel the program has "frozen"

## Core `BetaRawMessageStreamEvent` event types

The streaming API returns a series of `BetaRawMessageStreamEvent`s. Each event type corresponds to a different stage of the streamed response (`src/services/api/claude.ts`):

```
message_start           ← message begins, carries model and initial usage
  ├── content_block_start   ← content block begins (text / tool_use / thinking)
  │   ├── content_block_delta  ← incremental data (text_delta / input_json_delta / thinking_delta)
  │   ├── content_block_delta  ← ... keeps arriving
  │   └── content_block_stop   ← content block ends, yield AssistantMessage
  ├── content_block_start   ← next content block...
  │   └── ...
  └── message_delta       ← stop_reason + final usage
message_stop            ← message ends
```

### The event-handling state machine

The event-handling loop in `queryModelWithStreaming()` in `src/services/api/claude.ts` implements a state machine built on `switch(part.type)`:

| Event type | Handling | State change |
|------------|----------|--------------|
| `message_start` | Initialize `partialMessage`, record TTFT (time to first token) | `usage` initialized |
| `content_block_start` | Create a content block of the matching type at `part.index` | `contentBlocks[index]` initialized |
| `content_block_delta` | Append data incrementally by subtype | text / thinking / input accumulate |
| `content_block_stop` | Build the full `AssistantMessage` and yield it | Message pushed into `newMessages` |
| `message_delta` | Update stop_reason and final usage | Written back to the last message |
| `message_stop` | No-op (end-of-stream marker) | — |

### Content block types and their deltas

The `content_block.type` in `content_block_start` decides how later deltas are handled:

| Content block type | Delta type | Accumulation logic |
|--------------------|------------|--------------------|
| `text` | `text_delta` | `text += delta.text` |
| `thinking` | `thinking_delta` + `signature_delta` | `thinking += delta.thinking`, `signature = delta.signature` |
| `tool_use` | `input_json_delta` | `input += delta.partial_json` (incremental concatenation of a JSON string) |
| `server_tool_use` | `input_json_delta` | Same as tool_use |
| `connector_text` | `connector_text_delta` | Special connector text (controlled by a feature flag) |

Key design point: on `content_block_start`, all text fields are initialized to empty strings and accumulate only through `content_block_delta`. This is because the SDK sometimes sends the same text in both the start and the delta events.

## Interleaving of text chunks and tool_use blocks

One AI response may contain multiple content blocks that alternate:

```
content_block_start (text, index=0)     "Let me help you fix this bug."
content_block_delta  (text_delta)       "First..."
content_block_stop  (index=0)
content_block_start (tool_use, index=1) { name: "Read", input: "..." }
content_block_delta  (input_json_delta) '{"file_p' → 'ath":' → '"src/foo.ts"}'
content_block_stop  (index=1)
content_block_start (text, index=2)     "I see where the problem is..."
content_block_stop  (index=2)
```

Each `content_block_stop` triggers a `yield` that pushes the complete AssistantMessage to the consumer. This means one AI response produces **multiple** `AssistantMessage`s, with text messages and tool call messages emitted alternately.

`stop_reason` is not known until `message_delta` (it may be `end_turn`, `tool_use`, `max_tokens`, and so on), so the last message's `stop_reason` is **written back** afterwards:

```typescript
// claude.ts — stop_reason write-back (direct property mutation, no object replacement)
// because the transcript write queue holds a reference to message.message
const lastMsg = newMessages.at(-1)
if (lastMsg) {
  lastMsg.message.usage = usage
  lastMsg.message.stop_reason = stopReason
}
```

## Error handling during streaming

### Network disconnects

The streaming connection relies on SSE (Server-Sent Events). When the connection breaks, the system has two layers of detection:

1. **Passive stall detection** (the stall logic in `src/services/api/claude.ts`): when the next event arrives, it computes the interval since the previous event. If the interval exceeds the threshold (30 seconds, `STALL_THRESHOLD_MS = 30_000`), it is recorded as a stall, the count is accumulated, and it is written to the telemetry log. This is passive detection: it fires only when the next chunk arrives and never interrupts the stream on its own.
2. **Active idle-timeout watchdog** (the `STREAM_IDLE_TIMEOUT_MS` watchdog logic in `src/services/api/claude.ts`): uses `setTimeout` to set a hard timeout of 90 seconds (overridable with the `CLAUDE_STREAM_IDLE_TIMEOUT_MS` environment variable). If no event arrives in that period, it aborts the stream and throws an error that enters the retry flow.
3. **Non-streaming fallback**: as a last resort, the `didFallBackToNonStreaming` flag is set, and the request falls back to a non-streaming one through `executeNonStreamingRequest()` (fetching the complete response in one go).

```typescript
// claude.ts — passive stall detection
const STALL_THRESHOLD_MS = 30_000  // 30 seconds without events counts as a stall
let totalStallTime = 0
let stallCount = 0

// claude.ts — active idle timeout
const STREAM_IDLE_TIMEOUT_MS =
  parseInt(process.env.CLAUDE_STREAM_IDLE_TIMEOUT_MS || '', 10) || 90_000
```

### API rate limiting

When the API returns a rate-limit error, the system retries with exponential backoff through the `withRetry` wrapper. The retry logic considers:
- Error type (429 rate limit vs. 500 server error)
- Maximum retry count
- Backoff interval

### Token limits exceeded

The two token-limit scenarios are handled differently:

| Scenario | stop_reason | Handling |
|----------|-------------|----------|
| **Output limit exceeded** | `max_tokens` | Generate an error message suggesting `CLAUDE_CODE_MAX_OUTPUT_TOKENS` |
| **Context window exceeded** | `model_context_window_exceeded` | Trigger compaction of the conversation history, then retry |

```typescript
// claude.ts — stop_reason handling
if (stopReason === 'max_tokens') {
  yield createAssistantAPIErrorMessage({ error: 'max_output_tokens', ... })
}
if (stopReason === 'model_context_window_exceeded') {
  // Reuse the max_output_tokens recovery path
  yield createAssistantAPIErrorMessage({ error: 'max_output_tokens', ... })
}
```

### Streaming stall detection

The system continuously monitors the interval between events to detect a "stall":

```typescript
// claude.ts — stall detection logic
const STALL_THRESHOLD_MS = 30_000  // 30 seconds without events counts as a stall
if (timeSinceLastEvent > STALL_THRESHOLD_MS) {
  stallCount++
  totalStallTime += timeSinceLastEvent
  logEvent('tengu_streaming_stall', { stall_duration_ms, stall_count, ... })
}
```

This is **passive detection**: the comparison happens only when the next chunk arrives. Its complement is the 90-second active idle-timeout watchdog (`STREAM_IDLE_TIMEOUT_MS`), which directly aborts a stream that has been silent for too long.

## Streaming feedback from tool execution

BashTool's command execution is also streamed. Output is pushed line by line through the `onProgress` callback:

```
BashTool.call() → runShellCommand() → AsyncGenerator
  ├── Poll the output file every second → onProgress(lastLines, allLines, ...)
  ├── yield { type: 'progress', output, fullOutput, elapsedTimeSeconds }
  └── return { code, stdout, interrupted, ... }
```

The UI layer shows command output in real time through the `useToolCallProgress` hook instead of waiting for the command to finish. Long-running commands can also be moved to the background automatically (`shouldAutoBackground`).

## Multi-provider adaptation

| Provider | Streaming protocol | Special handling |
|----------|--------------------|------------------|
| **firstParty** (Anthropic Direct) | Native SSE | Lowest latency, fastest TTFT |
| **AWS Bedrock** | AWS SDK streaming interface | Needs extra beta headers and authentication |
| **Google Vertex** | gRPC → event stream | Adapted through `getMergedBetas()` |
| **foundry** | Anthropic-compatible API | Internal deployment |
| **openai** | OpenAI stream adapter | Converted to the internal Anthropic format |
| **gemini** | Gemini stream adapter | Converted to the internal Anthropic format |
| **grok** (xAI) | Grok stream adapter | Converted to the internal Anthropic format |

All providers hide their differences behind a unified `Stream<BetaRawMessageStreamEvent>` abstraction. Upper-level code (QueryEngine, REPL) does not need to care which provider is underneath.

### Provider selection

`getAPIProvider()` in `src/utils/model/providers.ts` decides which provider to use based on configuration:

```typescript
// Chosen by the api_provider setting:
// "anthropic" → direct
// "bedrock"   → AWS SDK
// "vertex"    → Google SDK
// third-party base URL → auto-detected
```

The details each provider must adapt include authentication, beta headers, request parameter format and error code mapping, but these differences are handled uniformly in the `queryStream()` function in `claude.ts`.
