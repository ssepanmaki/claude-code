## When compaction triggers

Context compaction is not a single operation but a **three-layer escalating** strategy system, with different triggers and severity at each layer:

| Layer | Trigger | Implementation | Needs an API call |
|-------|---------|----------------|:---:|
| **MicroCompact** | A single tool output is too long | `microCompact.ts` | No |
| **Session Memory Compact** | Auto-compaction triggers (needs a feature flag) | `sessionMemoryCompact.ts` | No |
| **Traditional API summary** | Manual `/compact`, or automatic fallback when SM is unavailable | `compact.ts` | Yes |

### The priority chain at the compaction entry

Source path: `src/commands/compact/compact.ts`

When the user runs `/compact` or the system triggers auto-compaction, the compact command tries these in priority order:

```typescript
// compact.ts:55-99 — simplified priority chain
if (!customInstructions) {
  const sessionMemoryResult = await trySessionMemoryCompaction(messages, ...)
  if (sessionMemoryResult) return sessionMemoryResult      // first choice: SM compaction
}

if (reactiveCompact?.isReactiveOnlyMode()) {
  return await compactViaReactive(messages, ...)            // second choice: Reactive compaction
}

// Fallback: traditional API summary
const microcompactResult = await microcompactMessages(messages, context)
const messagesForCompact = microcompactResult.messages
// → call the AI model to generate a summary
```

Note: SM compaction does not support custom instructions (`/compact focus on the auth module`). With custom instructions it goes straight to the traditional path.

## Layer 1: MicroCompact — local compaction

Source path: `src/services/compact/microCompact.ts`

MicroCompact does not compress the whole conversation. It **clears the content of old tool outputs**. It keeps an allowlist:

```typescript
// src/services/compact/microCompact.ts:41-50
const COMPACTABLE_TOOLS = new Set([
  FILE_READ_TOOL_NAME,    // 'Read' - file reads
  ...SHELL_TOOL_NAMES,    // 'Bash' - command output
  GREP_TOOL_NAME,         // 'Grep' - search results
  GLOB_TOOL_NAME,         // 'Glob' - file lists
  WEB_SEARCH_TOOL_NAME,   // 'WebSearch' - search results
  WEB_FETCH_TOOL_NAME,    // 'WebFetch' - web page content
  FILE_EDIT_TOOL_NAME,    // 'Edit' - edit output
  FILE_WRITE_TOOL_NAME,   // 'Write' - write output
])
```

Replacement strategy: tool output content older than the time window is replaced with `[Old tool result content cleared]`. This is not simple truncation. The original content stays in the JSONL transcript and is just no longer sent to the API.

MicroCompact also has a **time-decay configuration** (`timeBasedMCConfig.ts`): the older a tool output is, the more likely it is to be cleared, while the most recent ones are kept first.

### Special handling for images and documents

```typescript
const IMAGE_MAX_TOKEN_SIZE = 2000
```

An image block whose estimated size exceeds 2000 tokens is also cleared by MicroCompact. PDF document blocks are treated the same way.

## Layer 2: Session Memory Compact — compaction without an API call

Source path: `src/services/compact/sessionMemoryCompact.ts`

When the `tengu_session_memory` + `tengu_sm_compact` feature flags are enabled, the system prefers Session Memory for compaction. **No summarization model call is needed**: the already-extracted Session Memory is used directly as the conversation summary.

### Computing the retention window

```typescript
// sessionMemoryCompact.ts:324-397
export function calculateMessagesToKeepIndex(messages, lastSummarizedIndex) {
  const config = getSessionMemoryCompactConfig()
  // Defaults: minTokens=10K, minTextBlockMessages=5, maxTokens=40K

  let startIndex = lastSummarizedIndex + 1
  // Expand backward from lastSummarizedIndex until both minimums are met or the cap is hit
  for (let i = startIndex - 1; i >= floor; i--) {
    totalTokens += estimateMessageTokens([msg])
    if (hasTextBlocks(msg)) textBlockMessageCount++
    startIndex = i
    if (totalTokens >= config.maxTokens) break
    if (totalTokens >= config.minTokens && textBlockMessageCount >= config.minTextBlockMessages) break
  }
  return adjustIndexToPreserveAPIInvariants(messages, startIndex)
}
```

This algorithm ensures the message window kept after compaction satisfies:
- At least 10,000 tokens (context depth)
- At least 5 messages containing text (conversational continuity)
- At most 40,000 tokens (not so large that it triggers the next compaction)

### Tool-pair integrity protection

`adjustIndexToPreserveAPIInvariants()` is a **key correctness guarantee** in compaction:

The API requires every `tool_result` to have a matching `tool_use`, and vice versa. If compaction cuts exactly at a `tool_result` message, the API returns an error.

```typescript
// sessionMemoryCompact.ts:232-314
// Step 1: scan backward to find every tool_use referenced by a tool_result in the kept messages
// Step 2: scan backward to find thinking blocks that share a message.id with a kept assistant message
// In both cases startIndex needs to move backward
```

Streaming splits one assistant message into several stored records (thinking, tool_use and so on each have their own uuid but share `message.id`), which adds edge-case complexity.

## Layer 3: traditional API summary compaction

Source path: `src/services/compact/compact.ts`

When SM compaction is unavailable, the system falls back to the traditional way: calling the AI model to generate a conversation summary.

### Pre-compaction processing

Before being sent to the summarization model, messages go through several layers of preprocessing:

```typescript
// compact.ts:147-202
const stripped = stripImagesFromMessages(messages)   // images → [image] text marker
const stripped2 = stripReinjectedAttachments(stripped) // remove attachments that will be re-injected
```

Images are replaced with an `[image]` marker so the summarization API call itself does not trigger a prompt-too-long error.

### Re-injection after compaction

After compaction the system **re-injects key context** alongside the summary:

```typescript
// compact.ts:126-134
export const POST_COMPACT_TOKEN_BUDGET = 50_000          // total budget
export const POST_COMPACT_MAX_FILES_TO_RESTORE = 5        // restore at most 5 files
export const POST_COMPACT_MAX_TOKENS_PER_FILE = 5_000     // 5K tokens per file
export const POST_COMPACT_MAX_TOKENS_PER_SKILL = 5_000    // 5K tokens per skill
export const POST_COMPACT_SKILLS_TOKEN_BUDGET = 25_000    // total skill budget of 25K
```

This 50K-token re-injection budget is used to:
1. Restore recently read file contents (at most 5 files, each truncated to 5K tokens)
2. Restore activated skill instructions (each skill truncated to 5K tokens, 25K in total)
3. Re-inject CLAUDE.md content
4. Restore MCP tool discovery results

## CompactBoundary: the boundary marker of compaction

Source path: `src/utils/messages.ts` (`createCompactBoundaryMessage`)

After each compaction, the system inserts a `SystemCompactBoundaryMessage` into the message stream:

```typescript
type SystemCompactBoundaryMessage = {
  type: 'system'
  message: {
    type: 'compact_boundary'
    compactMetadata: {
      compactType: 'auto' | 'manual' | 'micro'
      preCompactTokenCount: number
      lastUserMessageUuid: string
      preCompactDiscoveredTools?: string[]
    }
  }
}
```

All later operations only process messages **after the last boundary**:

```typescript
// messages.ts
export function getMessagesAfterCompactBoundary(messages: Message[]): Message[] {
  const lastBoundary = messages.findLastIndex(m => isCompactBoundaryMessage(m))
  return lastBoundary >= 0 ? messages.slice(lastBoundary + 1) : messages
}
```

### The Preserved Segment annotation

The boundary message also carries a `preservedSegment` annotation that records which messages were kept rather than compacted:

```typescript
// compact.ts — annotateBoundaryWithPreservedSegment
boundaryMarker.compactMetadata.preservedSegment = {
  summaryMessageUuid: string
  preservedMessageUuids: string[]
}
```

On session resume this helps the loader rebuild the message chain correctly and avoid compacting already-preserved messages again.

### Microcompact Boundary

Microcompact operations use a separate boundary type, different from the full compaction `compact_boundary`:

```typescript
// src/utils/messages.ts:4599-4614
type SystemMicrocompactBoundaryMessage = {
  type: 'system'
  subtype: 'microcompact_boundary'
  content: 'Context microcompacted'
  compactMetadata: {
    trigger: 'auto'              // Microcompact only triggers automatically
    preTokens: number            // token count before compaction
    tokensSaved: number          // tokens saved
    compactedToolIds: string[]   // IDs of the compacted tools
    clearedAttachmentUUIDs: string[] // UUIDs of the cleared attachments
  }
}
```

Differences from `compact_boundary`:
- **Original messages are kept**: Microcompact only clears tool output content and does not delete the messages themselves
- **Traceability**: `compactedToolIds` records which tool results were cleared
- **Lightweight**: no summary is generated and no API is called

## PTL emergency degradation: Prompt Too Long

When the result is still over the token limit after compaction (a `PROMPT_TOO_LONG` error), the system enters an emergency degradation path:

1. **Reactive Compact**: `reactiveCompactOnPromptTooLong()` attempts more aggressive compaction
2. **Truncate and retry**: if reactive also fails, `truncateHeadForPTLRetry()` simply truncates the earliest messages
3. Give up and report an error

Reactive Compact is currently a stub in the decompiled version (`isReactiveOnlyMode() → false`), which suggests it is an experimental feature internal to Anthropic.

## Compaction hooks

Custom hooks can run before and after compaction:

- **Pre-compact Hook** (`executePreCompactHooks`): runs before compaction and can inject "must keep" markers
- **Post-compact Hook** (`executePostCompactHooks`): runs after compaction and can verify that key information was kept
- **Session Start Hook** (`processSessionStartHooks('compact')`): SM compaction uses this hook to restore context such as CLAUDE.md

Hook results are attached to the compaction result as `HookResultMessage`s, so users' custom logic is respected during compaction.
