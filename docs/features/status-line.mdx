## Overview

StatusLine is a line of custom text shown at the bottom of the Claude Code REPL, rendered by a **user-provided shell command**. The main process packs runtime state (model, working directory, tokens, rate limits, session metadata, etc.) into JSON and feeds it to the script over stdin; the script prints one line of text to stdout, and the Ink side renders it into the footer using ANSI escapes.

Core design philosophy: **language-agnostic + process isolation + Unix pipes**. Users can write the script in bash / python / node / any language; a script crash does not affect the main process; input and output are plain text, so it can be tested offline (`echo '{...}' | ./script.sh`).

## Configuration

Add a `statusLine` field to `~/.claude/settings.json`:

```json
{
  "statusLine": {
    "type": "command",
    "command": "bash ~/.claude/statusline-command.sh",
    "refreshInterval": 1,
    "padding": 0
  }
}
```

| Field | Type | Purpose |
|------|------|------|
| `type` | `"command"` | Only the command type is currently supported |
| `command` | `string` | Shell command string; the main process runs it with the system shell |
| `refreshInterval` | `number` (seconds) | Periodic refresh interval; missing/0 means no periodic refresh |
| `padding` | `number` | Left/right padding, in Ink cells |

The schema is defined in `src/utils/settings/types.ts:550` (the `statusLine` Zod object).

## Rendering pipeline (overview)

```
┌─────────────────────── Ink side ─────────────────────┐     ┌──────── User side ─────┐
│                                                      │     │                        │
│  buildStatusLineCommandInput()  ──┐                  │     │  ~/.claude/            │
│     collect runtime state         │                  │     │   statusline-*.sh      │
│                                   ▼                  │     │                        │
│  executeStatusLineCommand()  ─── JSON via stdin ────────────►  jq '.model...'       │
│     execCommandHook() spawns shell                   │     │  compute, format       │
│                                   ▲                  │     │                        │
│     stdout ◄──────────────────── one line of text ───────── printf '...'             │
│                                   │                  │     │                        │
│  setAppState({ statusLineText }) ─┘                  │     └────────────────────────┘
│     zustand stores the field, component memo subscribes │
│                                                      │
│  <StatusLine /> → <Text><Ansi>{text}</Ansi></Text>   │
│                                                      │
└──────────────────────────────────────────────────────┘
```

## Input protocol: main process → script

The JSON object built by `buildStatusLineCommandInput` (`src/components/StatusLine.tsx:53`) has the fields below. **This is everything a script can read with `jq`**:

## Output protocol: script → main process

`executeStatusLineCommand` (`src/utils/hooks.ts:4752`) processes the script's stdout as follows:

1. `trim()` leading and trailing whitespace
2. Split on `\n` and `trim()` each line
3. Drop empty lines and rejoin the rest with `\n`

Multi-line output is **kept as multiple lines** (Ink's `<Text>` allows line breaks when rendering), but the design recommends a **single line** — multiple lines take up REPL height and in fullscreen mode may push out a ScrollBox row.

Exit status conventions:
- `exit 0` + non-empty stdout → displayed
- `exit 0` + empty stdout → clears the statusLine (shown empty)
- non-zero → ignored, last content kept; a warn-level log is written when `logResult=true`
- timeout (default 5000ms) → ignored
- cancelled by AbortController → ignored

ANSI colors work; Ink parses SGR sequences through the `<Ansi>{text}</Ansi>` component.

## Three trigger sources

Recomputing the StatusLine is driven by **three kinds of events**, all going through the same debounce queue:

### 1. Event-driven (`src/components/StatusLine.tsx:275`)

Watches these state changes and triggers `scheduleUpdate()`:

- `lastAssistantMessageId` — a new assistant reply appears
- `permissionMode` — `/mode` switches the permission mode
- `vimMode` — vim insert/normal toggle
- `mainLoopModel` — `/model` switch

### 2. Settings-driven (`src/components/StatusLine.tsx:294`)

When the `settings.statusLine.command` string changes (settings.json hot reload), the next result is marked for logging and `doUpdate()` runs immediately.

### 3. Time-driven (`src/components/StatusLine.tsx:292`, patched in this repository)

Reads `settings.statusLine.refreshInterval` (seconds), and `setInterval` calls `scheduleUpdate()` on every tick. When set to 0 or missing, no timer starts (zero overhead).

> **Historical gap in this repository**: the decompiled `StatusLine.tsx` originally had no Time-driven trigger path, and the `refreshInterval` field was not in the Zod schema. As a result, dynamic content such as TTL countdowns and clocks in a script would not refresh every second, and was recomputed only when an assistant reply appeared. This was filled in on 2026-05-06; see "Known gap and fix" below for details.

## Debounce + abort

All three trigger sources go through `scheduleUpdate` (`src/components/StatusLine.tsx:259`):

```
scheduleUpdate() → setTimeout(300ms) → doUpdate()
                   │
                   └─ scheduling again does clearTimeout on the previous one
```

The 300ms debounce merges jittery events (for example, switching vim/permission several times in a short period).

Inside `doUpdate()`:

```
abortControllerRef.current?.abort()   // cancel the previous in-flight shell
controller = new AbortController()
executeStatusLineCommand(..., controller.signal, ...)
```

**Single-flight semantics**: any new trigger aborts the previous unfinished shell call, so there is at most one child process at a time. This matters especially for `refreshInterval: 1` — if the script takes more than 1 second, the old process is killed when the next tick arrives, so they do not pile up.

## Security gates

`executeStatusLineCommand` (`src/utils/hooks.ts:4752`) applies **three layers of interception** before running:

1. `shouldDisableAllHooksIncludingManaged()` → returns immediately when managed settings disable hooks globally
2. `shouldSkipHookDueToTrust()` → **skipped when the workspace has not accepted the trust dialog**, to avoid running arbitrary shell commands when opening an unknown repository (RCE protection)
3. `shouldAllowManagedHooksOnly()` → when non-managed settings disable hooks but managed settings do not, only the statusLine from the policySettings source is read

On the component side (`src/components/StatusLine.tsx:318`): when trust has not been accepted, the notification center shows `"statusline skipped · restart to fix"`.

In addition, `statusLineShouldDisplay` (`src/components/StatusLine.tsx:46`) returns false directly in **Kairos assistant mode** — because the statusline fields then reflect the state of the REPL/daemon process, not what the agent subprocess is running, and showing them would mislead the user.

## Rendering details

### memo isolation

```tsx
export const StatusLine = memo(StatusLineInner)
```

The parent `PromptInputFooter` re-renders on every `setMessages`, but only `lastAssistantMessageId` changes in `StatusLine`'s props, and `memo` blocks pointless re-renders. Before (without memo) there were about 18 redundant renders in one session.

### Subscription granularity

```tsx
const statusLineText = useAppState(s => s.statusLineText)
```

`useAppState` is a selector subscription that re-renders only when the `statusLineText` field changes; `doUpdate()` also does an idempotency check (if `prev.statusLineText === text`, it returns the original state directly), so **when the text is unchanged, zustand is not updated** and not even a notify is sent.

### Fullscreen placeholder

```tsx
{statusLineText ? (
  <Text dimColor wrap="truncate"><Ansi>{statusLineText}</Ansi></Text>
) : isFullscreenEnvEnabled() ? (
  <Text> </Text>  // reserve one line
) : null}
```

In fullscreen mode the footer has `flexShrink:0`, and going from 0 to 1 statusline rows would push out one row of ScrollBox content and cause jitter. Before the script's first result returns, a text of spaces reserves one line of height, and it is replaced in place once the script returns.

## Built-in `/statusline` slash command

`src/commands/statusline.tsx` defines a **prompt-type command** that expands into a natural-language instruction fed to the main Agent:

```
Create an AgentTool with subagent_type "statusline-setup" and the prompt "<user-args>"
```

The default prompt is `"Configure my statusLine from my shell PS1 configuration"`. After receiving it, the main Agent calls the built-in sub-agent `statusline-setup`. This sub-agent has minimal permissions:

- **Tools**: only `Read` and `Edit`
- **Allowed paths**: `Read(~/**)`, `Edit(~/.claude/settings.json)`

That is, it **cannot Write new files and cannot run Bash**. Its typical job is to read the user's shell config, read/modify `settings.json`, and incrementally edit an existing statusline script.

## Tips for writing a custom script

1. **The script must be stateless** — on every tick the main process forks a new shell, and in-process variables are not kept across calls. State that must span ticks (last timestamp, last token count) should be persisted to a file such as `~/.claude/statusline-state/<hash>.state`.
2. **Isolate state files by hashing `session_id`** — with several sessions open at once, a shared state file gets crossed. A typical approach: `md5(session_id) | head -c 16` as the file name.
3. **Read defensively** — the state file may be corrupted/truncated; read line by line and validate fields (for numeric fields use `case "$var" in ''|*[!0-9]*) invalid ;;`).
4. **`refreshInterval` does not mean "the script is called every second"** — ticks and event triggers (new message, mode switch) go through the same debounce queue, so the actual call rate falls between "every N seconds" and "every N+0.3 seconds"; and under the abort mechanism, a run that has not finished is killed.
5. **Execution time budget** — the default timeout is 5000ms; to avoid frequent timeouts with `refreshInterval=1`, the script's hot path should finish within 100ms. Heavy computation (curl, git log fetches) needs caching.
6. **Use ANSI escapes for color** — do not depend on the TERM environment variable; Ink's `<Ansi>` component parses SGR independently.
7. **Do not output multiple lines** — single-line text only, otherwise it takes up REPL layout space.
8. **Handle `current_usage` being null** — before the first response, `context_window.current_usage` may be null, and the script should have a fallback (such as reading the last hit rate from state).

### Example: cache hit rate + TTL countdown

An example script `~/.claude/statusline-command.sh` (user side) prints the format `<dir> | <model> | ctx:N% | Cache 97% 59:43`:

- **Hit rate** = `cache_read / (input + cache_creation + cache_read)` (taken from `current_usage`)
- **TTL** counts down 60 minutes from the last response, **resetting the timestamp only when the token signature changes**, so that per-second ticks do not keep the TTL locked at 60:00
- **Color bands** — hit rate ≥50% green / <50% gray; TTL 0-20m green / 20-40m yellow / 40-55m red / last 5m flashing red / expired `exp` gray
- **Per-session state** — `~/.claude/statusline-state/<md5(session_id)[:16]>.state`, three lines (signature, timestamp, hit), with numeric validation before reading
- **Fallback** — when `current_usage` is null, read the state and show the last hit rate

> With `refreshInterval: 1` this script refreshes the TTL every second, provided the `refreshInterval` trigger path is implemented (see the next section).

## Known gap and fix (this repository)

The decompiled `StatusLine.tsx` had one functional gap:

| Item | Official Claude Code | This repo originally | This repo now |
|----|-----------------|-----------|-----------|
| `refreshInterval` Zod field | ✅ present | ❌ missing | ✅ added |
| Time-driven `setInterval` trigger | ✅ present | ❌ missing | ✅ added |
| Event-driven trigger | ✅ present | ✅ present | — |
| Settings-driven trigger | ✅ present | ✅ present | — |
| Debounce + Abort | ✅ present | ✅ present | — |
| Trust gate | ✅ present | ✅ present | — |

Fix (2026-05-06):

**1. `src/utils/settings/types.ts:554`** — the statusLine schema gains `refreshInterval: z.number().optional()`, so the field enters the type system instead of being ignored as an unknown key.

**2. `src/components/StatusLine.tsx:292`** — a new Time-driven useEffect:

```tsx
const refreshIntervalMs = (settings?.statusLine?.refreshInterval ?? 0) * 1000;
useEffect(() => {
  if (refreshIntervalMs <= 0) return;
  const id = setInterval(() => scheduleUpdate(), refreshIntervalMs);
  return () => clearInterval(id);
}, [refreshIntervalMs, scheduleUpdate]);
```

Key points:
- It goes through `scheduleUpdate` (not `doUpdate`) to reuse the 300ms debounce, so interval + event double triggers do not run twice
- When `refreshIntervalMs <= 0` no timer starts, with zero overhead for users who do not use the field
- The dependency array includes `refreshIntervalMs`, so a settings hot reload automatically clears the old interval and builds a new one

**Silent-failure signature**: before the fix, writing `refreshInterval: 1` in settings.json produced no error — JSON parsing passed, the Zod schema strips extra fields by default, and the official docs say the field is supported, so users easily assumed it worked and did not realize TTL/clock-style output was never refreshed every second. This is a typical decompiled-version case of "docs and implementation disagree".
